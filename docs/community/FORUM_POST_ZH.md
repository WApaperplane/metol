## 正文

### 先说结论

三星 NX500（固件 1.12）的 DRIMe5 图像处理器，把 3D LUT 放在内存里的 42 个槽位中，并且**每次装载都重新读一次代码段里的小登记表**。

于是换表的最小闭环是：

```
改 1 个 4 字节的登记表项
写 19,712 字节进一个空闲槽
半按一次快门
```

取景器立刻渲染新表。不刷固件、不改 p7 代码、不用 CMA、不抢时序。

再进一步：**取景和成片是两张独立的登记表**。你可以让取景器显示 A 表、让 JPEG 用 B 表。

---

### 一、这台机器里到底有两个 CPU

很多人以为相机只有一个处理器。NX500 有两个，分工完全不同：

| | AP | p7 |
|---|---|---|
| 系统 | Tizen 2.2 | T-Kernel 2.01.03（实时系统） |
| 干什么 | 界面、菜单、存文件（`di-camera-app`） | 图像处理：去马赛克、降噪、色彩、3D LUT |
| 固件在哪 | rootfs（eMMC 一个分区） | **独立分区**，不在 rootfs 里 |

色彩相关的代码全在 p7 里。p7 的固件是扁平映射 —— `VA = 0x80000000 + 文件偏移` —— 这对静态分析非常友好。

### 二、LUT 表的格式

从固件逆出来，并用 42 个槽逐字节比对确认：

```
4,913 项（17 × 17 × 17）× 4 字节 {R, G, B, pad=0}
索引 = ((B × 17 + G) × 17 + R) × 4
单槽 = 19,652 字节数据 + 60 字节填充 = 19,712 字节
槽间隔 = 0x4D00
```

开机时 p7 把镜像里 4,097,216 字节整段拷进内存：

```
镜像文件 [0x79BDC0, 0xB84280)  →  装载到 0x8079BDC0
  复制 0x3E84C0 字节           →  运行区 [0x81006000, 0x813EE4C0)
runtime = 0x80000000 + 文件偏移 + 0x86A240
```

这块区域里就是 42 个 LUT 槽（一块 20 个，另一块 22 个）。

**这条发现推翻了一个旧结论。** 早先我们判断「固件里没有填充这些表的代码」，因为找不到按槽写入的例程。实际上有——它是一次开机 `memcpy`，不是逐个槽初始化。负证据用错了方法。

### 三、「用哪张表」这件事记在哪

代码段里三张静态表：

| 表 | 地址 | 项数 | 谁用 |
|---|---|---|---|
| `View4` | `0x803837F0` | 4 | 取景 |
| `Still6` | `0x80382C5C` | 6 | 成片 |
| `BV12` | `0x80382B00` | 12 | 按亮度值索引 |

每项是个结构体，`+0x00C` 是**装载源地址**，`+0x010` 是**保存地址**。注意：它们不是「被反复轮询的指针」，只在装载那一刻读。

动手之前先验了两件事：

1. 含这三张表的 16 KB 页，运行时与固件镜像**逐字节相同**（22/22 项对上，16 KB diff = 0）⇒ `VA = 0x80000000 + 偏移` 在这块区域成立，开机没被改写。
2. 这一页**可写**（`/dev/mem` + `O_RDWR` + `PROT_WRITE`），空写回首值后窗口内 stray = 0。

### 四、实验过程（含一次「看起来失败」）

先测出厂状态：**取景链的装载源是 `0x81115200`（A17 槽，一张肤色表），不是「标准」槽。**

这一条直接作废了更早的一次实验 —— 当时把负片表写进标准槽，画面毫无变化，被记成「机制不通」。其实是**打错靶**。

| 步 | 动作 | 机器判据 |
|---|---|---|
| 0 | 基线 | `VIEW4 = 810fd100 81101e00 81106b00 81115200`，`load=0x81115200` |
| 1 | 空写回 | 回读一致，stray = 0 |
| 2 | `View4[3]` → A18 | 字内 1 字节变化，stray = 0 |
| 3 | 半按 | `load_addr → 0x81119F00`，**画面看不出变化** |
| 4 | `View4[3]` → A12 | 字内 1 字节变化，stray = 0 |
| 5 | 半按 | `load_addr → 0x810FD100`，画面「整体变亮偏凉」，但说不清有没有偏色 |
| 6 | 往 A18 写负片表（19,712 B，先备份） | 回读 mismatch = 0 |
| 7 | `View4[3]` → A18 | 字内 2 字节变化，stray = 0 |
| 8 | 半按 | **取景器明显负片** |
| 9 | 双向回滚 | 登记表回 A17，槽 mismatch = 0 |

**第 3 步为什么看不出**，值得单说。各槽与 A17 的差异：

| 槽 | 差异字节 | 占比 | 最大偏差（级） |
|---|---:|---:|---:|
| A12 标准 | 13,801 | 70.0 % | 97 |
| A14 电影 | 13,810 | 70.1 % | 97 |
| A13 黑白 | 7,792 | 39.5 % | 29 |
| **A18** | **806** | **4.1 %** | **8** |

A18 和 A17 几乎同一张表。**换过去看不见，不是硬件没消费，是判据选错了表。**

第 5 步那种「说不清的偏色」也不能当证据。所以直接换成无歧义的判据：把 4,913 项全部反相（`255 − R/G/B`）。负片骗不了眼睛。

### 五、最有价值的一条：两条链路是分开的

成片链有自己的一张六项登记表。把六项**全部**指向同一张负片表，同时让 `View4[3]` 继续指原厂 A17，然后拍一张：

**取景器完全正常，成片是负片。**

结论：取景和成片可以分别重定向。想「预览一个风格、成片另一个风格」，或者「取景器挂便宜近似表、成片挂精确表」，都成立。

这也重新解释了一个旧负结果：早前把表放进 **LUT1**，成片没跟随。那不是「成片不能换表」，而是「成片的 `_load` 用 `sel=0`，只读 LUT0」。

### 六、配置位（这条害我们得出过反向结论）

| 位 | 含义 |
|---|---|
| `[1:0]` | `SelCbCr` |
| `[5:4]` | **`SelLUT`** |
| `8` | LUT0 格式位 |
| `12` | LUT1 格式位 |

`0x100` 和 `0x1100` 都是 `SelLUT = 0`，只有 `0x1110` 才是 1。把 bit12 当成选择位，会非常有信心地得出「成片用 LUT1」—— 而且完全错。**要读字段，不要读标志位。**

### 七、机身直接转 `.cube`

相机 rootfs 里没有 Python，所以写了个纯 ARM 独立二进制 `cube2lut`（不依赖 libc / libm / libgcc）。把 Adobe `.cube` 丢进 SD 卡：

```sh
/opt/usr/nx-ks/cube2lut.arm /mnt/mmc/looks/portra400.cube /mnt/mmc/looks/portra400.bin
```

重采样到 17³ 网格（`{0,16,…,240,255}`），输出 19,712 字节槽表。

本来以为定点实现要对齐半天，结果三份 17³ 测试 cube 在相机上和 PC 上转出来的结果**逐字节相同** —— 因为参考实现也是先量化到 8 bit 再写，舍入差异活不下来。

（真实的 film cube 多数是 13³ 或 33³。重采样到 17³ 网格后，与 PC 参考最多差 **1 级** —— 那是网格插值的残差，不是 bug。）

它对不合规的输入是**直接报错**，不猜：`DOMAIN_MIN != 0` / `DOMAIN_MAX != 1`、节点数不是 `N³`、1D LUT，一律退出。轴序或 domain 读错时，转换照样成功，产出的是「看起来合理但是错的」表 —— 而画面上的错很难识别，报错一眼就能看见。

**还有一个差点混过去的 bug，值得写出来。** 第一版数字解析不支持科学记数法。G'MIC 把接近黑的值写成 `2.2439395252149552e-05`；解析器读到 `e` 返回 0，而且**没有推进指针** —— 后面每一个值都读成 0。节点计数器照旧自增到 `N³`，于是「是不是读了 4,913 个值」的检查**假通过**。工具退出码是成功，产出的表 93 % 为零。

18 张真实 film cube 里 12 张中招。我们当时用的三张测试表（identity / 反相 / warm）恰好都不含 `e` 记法，所以测试全绿 —— **那不是没问题，是没覆盖**。修法：支持 `e±NN`，解析不了就报 `bad number at value index…`，全零表直接拒绝。

### 八、一个你现在就能用的检验方法：灰轴最大落差

下载过 LUT 包的人大概都遇到过：同一套里有几张在你的机器上偏色到没法看。这里有个与场景无关的筛法。

把中性输入 `(v, v, v)`（v = 0..255）喂进 cube，逐级算：

```
cast(v) = max(R,G,B) − min(R,G,B)     # 8 bit 级
分数    = cast(v) 的最大值
```

中性进就该中性出。偏离多少就是偏色多少。它不看画面、不看光线、不看场景。

| 分数 | 判定 |
|---|---|
| ≤ 12 | 安全 |
| 13 – 25 | 轻微 |
| 26 – 50 | 明显 |
| > 50 | 极端 |

拿 296 张社区 Film-Luts 跑了一遍：

- 安全 157 / 轻微 62 / 明显 28 / 极端 49
- 有个分类叫 `instant_consumer`，54 张里只有 4 张安全 —— 基本全废
- 25 张黑白全部安全

**偏色不是转换 bug。** 用轴序矩阵验了 18 张，全部对角占优，说明通道映射是对的，偏色在源数据里。

### 九、明确没验的部分

写清楚，因为这类帖子最容易在这里吹过头：

- **持久性**：全部是内存操作，断电回原状。要做到「开机即生效」，仍然得改固件镜像。
- **重载触发条件**：半按一定能触发。切档、切模式、休眠唤醒是否也触发，未测。
- **多槽并发**：两张表分别有 4 项和 6 项，能不能同时指向四张不同的自定义表（等于一个 LUT 转盘），未测。
- **其它固件**：全部在 1.12 + 某个确定的 p7 版本上验的。
- **其它表格式**：只验了 4913×4B。16 bit、4:2:2 未测。

### 十、一条安全提醒（会咬人）

你也可以自己写 `+0x00C` 再脉冲一下配置寄存器来强制重载。**别这么干。** 那样 ISP 会读到一串在原厂时序里从未出现过的地址组合，结果是严重偏色花屏。

唯一安全的重载，是让相机自己走完选表复位：**半按快门**。我们的写入/还原脚本都刻意**不**自动重载。

回滚是完整验过的：槽的写入前备份与固件镜像切片逐字节相同（`md5 4c0cc78c…`），登记表和槽内容都能双向干净还原。

## 评论区预案

| 会被问 | 回答 |
|---|---|
| 我的 NX1 / NX300 能用吗 | NX1 同代 DRIMe5，p7 很可能同源但**未验**；NX300 是 DRIMe4，别假设 |
| 会变砖吗 | 全程内存操作，断电即回原状；不写分区、不刷固件。前提是已有 mod 的 telnet 权限 |
| 对画质有损吗 | 表是 17³ 网格 + 硬件插值，本来就是这个 ISP 的工作方式。损失来自「你选的表」，不是这条通路 |
| 能实时切 LUT 吗 | 目前靠半按触发重载。真正的多档热切换未验 |
| 这和 log / HDR 是一回事吗 | 不是。它换的是成片前的色彩查找表，不增加动态范围 |
| 为什么不干脆刷固件 | 刷机能做到开机即生效，但每次改表都要重刷。运行态换表可以反复试，且不承担刷机风险 |
