## 1. 项目目标

将 FilmLab 的 PW 配方和 3D LUT 整合为一个原生影像预设系统：用户通过三星原生菜单、滚轮或触摸选择预设，确认一次即可应用，并能准确知道效果作用于取景预览还是拍摄成片。预设可以仅包含 PW 参数、仅包含 LUT，或包含经过验证的二者组合；共用名称、收藏、状态反馈和恢复入口。

交互层复用 `di-camera-app` 的菜单、控件与状态机；数据层管理配方和 LUT 资产；能力层分别适配 PW 参数应用与 LUT 表装载。长期目标是在正常拍摄流程中稳定保留 LUT 效果，使导入和切换 LUT 成为日常操作。增加一个新 LUT 不应要求用户重新刷写固件。

第一版以“原生选择、确认应用、如实显示能力、关闭后恢复原厂行为”为目标。预览可用与成片可用分别交付；原生界面显示成功的依据是实际完成状态，不能由菜单改名、软件记账、返回码或参数回读替代。

## 3. 统一设计

预设以稳定 ID 关联显示名、PW参数、LUT资产及能力说明；LUT资产记录来源、内容哈希、表格式和输入色彩条件。三个原厂自定义槽可以作为快捷映射，但配方库规模不与原厂槽枚举绑定。当前三槽改名样机只证明文案工艺，不能宣告三槽内容一致性已经完成。

原生选择事件进入统一应用控制器，再由 PW 与 LUT 适配器执行。第一版移动焦点只改变选择，确认后应用；滚轮停留即预览、强度调节等功能后置。UI线程不执行耗时加载或同步 shell，工作完成后再更新原生界面。

统一状态至少区分“已选择、应用中、仅预览生效、拍摄效果已验证、失败、已被原厂操作修改”。同一组合中 PW 成功而 LUT 失败时，必须显示部分成功并提供恢复；不得把二者包装为没有依据的原子事务。PW与LUT的应用顺序需通过实机确定，不能假定参数提交不会触发P7重新配置。

“关闭 LUT”定义为停止相关守护并恢复已确认的原厂选表及配置，不以加载数学 identity 代替关闭。若要恢复整个组合预设，还需处理PW状态；具体恢复步骤应在对应后端中验证。

## 4. LUT 技术路线

| 路线         | 定位                 | 推进条件                                       |
| ---------- | ------------------ | ------------------------------------------ |
| LUT1 + 守护  | 保留为预览和诊断后端         | 回归已有E1/E3；不承诺拍照时稳定生效，不通过提高轮询频率掩盖成片问题       |
| C1 静态池最小替换 | 验证P7究竟消费哪张表的实验手段   | 先完成来源/消费者映射，再设计一槽改动、原字节核验、差异清单和恢复方案        |
| C3 受控运行时换表 | 长期候选主线，使日常导入无需反复刷机 | 证明目标缓冲所有权、重载路径、写入时机、数据与缓存同步、失败恢复及实际拍摄效果    |
| C2 既有调试写通道 | 条件候选，不作为承诺交付能力     | 先确认是否支持所需写入及长度、权限和同步语义，不能仅凭命令存在推断可用        |
| 软件后处理      | 成片的独立备选能力          | 现有引擎可复用，但任意外部`.cube`及与硬件预览的一致性须另验，不能直接承诺等效 |

正式研究重点是让P7正常选表/重载路径使用我们的表，而不长期依靠外部进程与P7竞争。C1用于验证机制，C3是否采用以及补丁规模由证据决定；A2的标量写入成功不直接证明约20KB表更新同样安全有效。CMA此刻全零也不代表已取得长期独占权。

以下为待执行任务，不把已有设计件视为新功能完成。

| 优先级 / ID | 任务                   | 产物与完成标准                                                  |
| -------- | -------------------- | -------------------------------------------------------- |
| P0 / T1  | 统一证据和LUT基础语义         | 更新能力矩阵；校验全表identity、槽边界、轴序和长度；明确恢复原厂与identity测试的区别       |
| P0 / T2  | 定义统一预设与适配器协议         | 形成预设格式、能力标记、状态机及接口；模拟后端覆盖成功、部分失败、取消和外部改参                 |
| P1 / T3  | 原生UI最小接入             | 复用既有菜单链与`.mo`资产；先验证一个入口和一个预设的选择、确认、返回与状态，不新增独立全屏窗口       |
| P1 / T4  | P7表来源与消费路径补证         | 带地址的源表/复制或生成/运行时缓冲/装载图；标明View、Still、模式、格式及重载条件；未知项不补猜测   |
| P2 / T5  | LUT预览后端产品化           | 已有LUT1能力回归；关闭/恢复、切换、负载和失效状态可靠；可被统一控制器调用                  |
| P2 / T6  | C1一槽机制实验设计及验证        | 离线产物保留A2既有改动；精确差异、原字节和SLP校验齐备；实机判定该表是否同时被预览/成片消费         |
| P3 / T7  | 依据T4/T6选择运行时方案       | 接口包含目标、长度、格式、校验与提交语义；QEMU验证代码边界，真机验证缓存/重载/效果；不预定补丁仅需几十字节 |
| P3 / T8  | FilmLab + LUT原生端到端验收 | 同一原生入口选择PW、LUT及组合；预览/JPEG分别验收；半按、全按、连续切换和正常关开机后状态正确      |

依赖关系：T1/T2可先离线完成；T3与T4分别推进。T5基于已有预览机制回归，T6依赖T4的消费者证据，T7由T4/T6结果裁决。原生UI和预设模型不必等待成片通道突破，但成片功能不能提前标记完成。

## 6. 验证与交付标准

QEMU用于转换、数据协议、真字节补丁分支和可模拟启动流程；记录所有替换桩。真实硬件缓存、P7重载、UI手感和画面效果必须实机验证。选用原厂对照表、数学identity及明显诊断表分别测试；identity仅作诊断，不规定它必须呈现“原厂中性”。外部LUT的Log/Rec.709/sRGB等输入条件需标明，未经色彩条件验证的文件不能宣称即导即用。

每项实机验收同时记录操作过程与实际效果：原生入口、滚轮/触摸、返回、关闭恢复；固定场景的预览与JPEG对比；半按、全按、切模式和休眠/正常关开机后的状态。RAW本体不默认承诺被LUT烘焙，视频另列能力。网络未上线、进程存活和画面正常分别记录，不相互替代。

最终交付分级：先交付“原生入口 + PW + 明确标注的LUT预览”，再在成片链实证通过后交付“原生组合预设 + 稳定JPEG效果”。导入库、更多预设列表和收藏在同一模型上扩展；动态名称、强度和连续预览以明确的后续任务推进。

首批工作为T1证据收口、T2接口设计、T3最小原生入口设计和T4定向补证。只复用和补充已有逆向成果，不重跑整个App静态，也不直接替换全部候选表。
