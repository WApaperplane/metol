**发现 1：人脸 AF 有明确的获得/丢失等待机制**

p7 `0x002f6c48` 是最值得继续逆向的函数之一。当前机器码在 `0x002f6c88` 比较状态字节是否为 2，随后分别选择等待量 `0` 或 `0x320`（800）。同一函数包含：

- `FD DETECTED: WAIT STABLE TIME`；
- `FD LOST: WAIT STABLE TIME`；
- `FD LOST: ACCEPTED`；
- `UPDATE FD AREA`。

代码既会延迟接受刚出现的人脸，也会在人脸暂时消失后保留已有区域。它不是“没有防抖/防丢脸策略”，而是已经有一套带等待时间的策略。计时函数 `0x004dd064` 调用底层计数读取并按 1000 缩放；本次未独立确认硬件计数单位，因此不把 800 直接写成已实测的 800 ms，也不把状态值 2 猜成某个具体 AF 模式。

优化方向：分开处理“新脸确认”“已选人脸短暂丢失”“同一个人重新出现”，使进入和退出阈值不必相同；可结合目标位移、框大小变化与连续成功次数。移动人像可能需要更快接纳，遮挡场景可能需要更长保持。统一缩短等待时间会增加误认和换人，不能只追求响应数字更小。

人脸区调整函数位于 `0x002f6ae0`，完整区域更新还有 `0x002f763c`；AF 锁定和等待拍摄的路径会跳过区域更新。修改时必须保留这些语义，否则可能出现用户已锁焦、程序仍移动对焦区的问题。

证据：`out/p7_002f6c48.asm`、`p7_002f6ae0.asm`、`p7_002f763c.asm`、`p7_004dd064.asm` 及对应历史伪代码。

**发现 2：对象追踪与人脸检测存在仲裁限制**

p7 `0x000fc7ac` 的执行路径检查对象追踪状态；在相关状态为 2/3 的分支，会调用人脸停止/清理路径，并输出：`FD is not working because Object Tracking Enable`。该字符串的实际加载指令在 `0x000fcac0`，不是仅有一个未使用的残留日志。

因此，不能简单设想“同时打开人脸和对象追踪”就能得到现代相机式自动接力。当前实现中，至少这条运行路径会暂停人脸检测。

有价值的扩展是：人脸优先 → 人脸暂失时以原目标区域启动对象保持 → 条件满足后重新检测并接回原人脸。它需要确认两类任务能否分时运行、帧缓存与任务锁如何使用、检测结果怎样关联。强行跳过停止分支，可能遇到共享状态或处理资源冲突；静态上还不能认定它只是产品限制。

证据：`out/p7_000fc7ac.asm` 及对应历史伪代码。

**发现 3：目标框已有滑动平均，可研究响应与稳定性的折中**

`CObjectTrackingIf::Segment` 对应 p7 `0x0013fee4`。初始化与持续跟踪走不同状态；持续跟踪调用 `0x00178a84`，后者再调用 `0x003e4a60`。

在满足特定标志与状态条件时，`0x0013fee4` 会对四条边分别执行环形缓冲更新：从累计和减去旧样本，加上新样本，再除以窗口长度。`0x00140410` 起的机器码可直接看到窗口长度、旧样本、累计和及除法。另一些分支直接使用新检测框。因此“所有模式都强制平均”的说法也不成立。

优化方向：小位移使用更强平滑，大位移或快速运动时减弱平滑；预测中心位置，而不是只平均过去坐标；对框大小和中心分别处理；丢失后区分短暂低置信度与明确换目标。必须继续确认该框在各模式下如何进入实际 AF 区域，不能把框的显示延迟自动等同于镜头伺服延迟。本次未确认运行时窗口长度，不能量化可减少多少帧延迟。

底层 `0x003e4838` / `0x003e4a60` 还出现 720×480 与 384×288 等坐标/缩放路径。外挂识别如要回写 ROI，必须处理取景分辨率、裁切、屏幕翻转及边界，不能直接把新算法像素坐标塞进 AF 参数。

证据：`out/p7_0013fee4.asm`、`p7_00178a84.asm`、`p7_003e4838.asm`、`p7_003e4a60.asm`。

**发现 4：存在可配置的追踪停止与重启计数**

p7 `0x002f9700` 是 AF 调试解析器中的一条路径。帮助串包含 `af multi algo tracking ng small ok`，输出描述了三项参数：连续 NG 几次停止、小目标抖动计数、连续 OK 几次开始下一次追踪。解析器会将输入写到同一状态对象的 `+0x44`、`+0x48`、`+0x4c`；日志读取的也正是这三个字段。

这是目前比泛泛“重写追焦算法”更具体的调参入口。不过它属于 AF multi 算法的追踪控制，不能未经调用链确认就当成触屏对象追踪器的全部阈值。当前值、有效范围、更新时机、是否被模式切换覆盖均未测。

本报告只记录静态帮助串和字段，不提供一组猜测的可执行写入命令。证据：`out/p7_002f9700.asm`，尤其 `0x002fa0ac` 起的读取分支及参数解析后的三次字段写入。

**发现 5：运动预测已存在，重点应是启用路径、时间和异常数据**

已定位：

| p7 文件偏移 | 可确认的职责 |
|---|---|
| `0x0036e7bc` | 计算预测时间，包含帧率/状态与延迟补偿项 |
| `0x0036ea08` | 两个时间及位置/距离样本的线性外推；存在 `LINEA PREDICT`、速度和预测距离日志 |
| `0x0036ecc4` | 三样本二阶外推实现；存在 `SECOND PREDICT`、加速度日志 |
| `0x0036f4f0` | 一条预测调度路径；样本不足时走回退，有效时调用线性外推及后续修正 |

关键限制：已确认的 `0x0036f4f0` 调度路径调用的是 `0x0036ea08`，不是 `0x0036ecc4`。不能看到二阶预测函数就声称它正在 NX500 实拍中启用，也不能推断切换过去必然更好。

软件优化更可能来自：让预测对应真正曝光时刻；拒绝目标切换时的错误历史样本；针对镜头驱动迟滞修正；按速度/加速度置信度选择模型。线性与二阶模型各有噪声和过冲代价。当前没有实拍误差分布，无法判断哪项是主要瓶颈。

镜头接口还包含 `GetSpecificFocusingSpeed`、`GetSpecificFocusBackLash`、远近限位和光圈/焦距属性。由此可以确认实现会考虑镜头差异；不能把某支镜头上的参数普遍应用到所有镜头。

证据：上述地址的 `.asm` 和 `*_historical.c`，及 `out/af.tsv`。

**发现 6：视频 AF 已有两套不同参数；现有 mod 的“对焦速度”含义不同**

历史 `st cap iqr` 记录中：

| 历史 IQ 序号 | 字段 | 静态枚举 |
|---|---|---|
| 32 | `eIQ_ID_AF_MOVIE_SPEED` | FAST / NORMAL / SLOW |
| 33 | `eIQ_ID_AF_MOVIE_SENSITIVITY` | LEV1…LEV5 |

App 同时包含 `menu_dep1_af_shift_speed`、`menu_dep1_af_responsiveness` 及对应菜单数据；历史 prefman 表也记录了 `APPPREF_MOV_AF_RESPONSIVENESS` 和 `APPPREF_MOV_AF_SHIFT_SPEED`。这些是已有参数，不是本次新发现的隐藏功能。

可优先做“人像保持 / 快速换焦 / 平缓过渡”之类的场景配置，并复用原厂参数范围。实际含义与镜头支持范围应沿用原厂菜单，后续再验证配置是否持久、哪些模式覆盖这些值。

工作区 `scripts/fpspeed.sh` 设置的是供 `focus_buttons` 等工具使用的 `fps` 环境变量。`focus_buttons` 的二进制字符串显示它通过 `st cap iq af mv 255 ...` 拉动镜头，`focus_stack` 也直接移动焦点。因此该滑块不能作为“已经提高原厂追焦速度”的证据；手动拉焦速度、视频 AF 换焦速度、AF 换目标响应是不同参数。

**眼部 AF、人脸身份和其他现代识别功能的边界**

确实找到 `CEyeDetectionIf`、`EyeDetection Error`，以及 Linux `mcbtest` 对 `Detect_Face_Eye`、`SDIC_FaceDetectionRotate`、`SDIC_FaceTracking` 的导入。第二轮已确认同一双眼定位算法同时进入实时 Smile/Wink 与拍后处理路径，并恢复部分结果布局；只有把检测结果连到选眼、AF 区域、相位/反差测量和镜头循环，才能证明眼部 AF。

当前确认的 AF 链路主要围绕脸框、多区与主区域。可考虑在已选脸内增加轻量眼部定位，再把可靠眼位置转换为 ROI；低置信度回退到脸部。还必须检查小脸的像素数、相位点覆盖、近眼/远眼选择、闭眼、侧脸、镜片反光、与脸框抖动的关系。仅把 AF 区域上移到脸框上部，是几何启发式，不应宣传成眼部识别。

固件同时有 `CFaceRecognitionIf` 与 `CFaceRecognitionStubIf` 名称。它们既不能证明有可用的人脸身份识别，也不能单凭 Stub 名称认定所有识别都不存在。识别人脸位置与记住某个人是两件事。人脸注册、跨画面身份保持、跨遮挡重识别，都需要另外确认特征表示和目标关联链路。

人体、动物、车辆等语义检测可在原则上接入现有 ROI/AF 后端，但目前尚未确认可部署的模型运行时、可用算力预算、取景帧获取成本和延迟。不能在未测量前承诺实时 AI，也不能仅凭机龄断言小模型绝对跑不了。

若要进入实现，第一轮应先定义及记录目标框、主脸、AF 模式、ROI、镜头位置、追踪结果和帧/时间戳，分别观察人像横移、前后移动、短时遮挡、双人交叉、弱光和录像。衡量合焦率、错误换人率、重新合焦时间及拉风箱次数。不能只用框是否更跟手判断成功，也不能只用清晰的静止场景验证追焦。

硬件边界仍然存在：软件无法增加传感器物理相位检测点，也无法消除传感器读出、曝光时序与镜头机械响应的下限。更好的目标选择和控制策略可以减少错误与浪费，收益需要结合具体场景测量。
