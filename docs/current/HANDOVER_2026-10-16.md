## 3. ★★ 今日核心：P5 交付机制被真机证伪

> 完整证据链：`raw8/gates/dicam/u1_p5_failure_2026-10-16.md`；SOP §3 已加 ⛔ 预警块。

### 3.1 现象

用户「正常关机 → 开机」后按 SOP §3 验证，**判据 5-7 全灭**：

| 判据 | 实测 |
|---|---|
| bind-mount 在位 | 无（`mount \| grep -E 'di-camera-app\|LC_MESSAGES'` 空） |
| `/tmp/dicam_p5_mount.log` | 不存在 |
| App 实际运行体 | **官方件 `ae44293e969101d1cf0a93cbe9b99f75`**（从 App 进程自身视图 `/proc/247/root/...` 读出） |

### 3.2 根因（6 项排除法）

决定性一条：**`systemctl show di-camera-app` 里连 `ExecStartPre` 条目都不存在**（不是"执行失败"——失败也会列条目、`start_time=[n/a]`，同机 `ac.service` 就是那样）。其余排除：

- unit 文件本体**正确**：md5 `b227c619f4220ed6f30dcca62ae1a4ab`、无 CR、行尾 `\n`、`/bin/bash` 在
- **PID 1 / App / shell 三方视图 md5 全同** ⇒ 非命名空间/overlay 问题
- `stat`：**ctime == mtime == 18:07:40**（ctime 不可被 `cp -p` 保留）⇒ 文件自 18:07 起未被写过
- `systemctl daemon-reload`（安全，无 restart）后该行**立刻出现** ⇒ 只可能是 **systemd 内存里那份 unit 是旧的**

同时反向确认：**App 是 boot+12.2s 被重新 exec 的**（`ExecStart` 记录 `pid=247`；`/proc/247/stat` starttime=1224 拍=12.24s；`UserspaceTimestampMonotonic=1.43s`）。

### 3.3 机制结论

本机 = **内核冷启 + 用户态恢复**：

| 证据 | 值 |
|---|---|
| `/proc/cmdline` | `… hibernate=nocompress … noresume …` |
| `/sys/power/bootmode` | `2`（`hibernation.sh` 中 `4` = bootshell cold-boot） |
| `/etc/snapshot` | 存在（4B 标记） |
| `/usr/bin/hibernation.sh` | **p9 当 swap 装镜像**（`mkswap /dev/mmcblk0p9`）+ zram + 末尾 `mount -o ro,remount /` |
| 恢复作业组 | `/usr/bin/hib_exjob`、`hib_tool`、`hib_tmp.sh`、`/usr/sbin/hib_gui.raw` |
| `/tmp/.hib_ready` / `.hib_post` | 前者 mtime 2016-03-30；**`.hib_post` = 本次开机 19:04 产生** |
| 时钟 | 开机早期读数 **2016-03-30 17:08:38**，开机中才校正（解释所有 2016 时间戳） |

**⇒ PID 1 的内存状态（含已解析 unit 表）被继承 ⇒ systemd 不重读 unit 文件。**

### 3.4 波及面与交付候选（★ 待裁）

**凡"改 unit / 依赖 systemd 每次开机重读配置"的投递方式，在本机不成立**（P1/P2 早已排除，**P5 今日阵亡** ⇒ T2_DELIVERY_REVISION_2026-10-15 §3 的裁决 a 作废）。

| 候选 | 可行性（已实测核对） | 代价 / 权衡 |
|---|---|---|
| ① **就地落盘** | App 二进制在 **p10**（dev `179:10`，4,773,516B，**余量仅 23MB / 96% 已用**）⇒ 直接替换即可；**每次上电 App 都重新 exec ⇒ 换文件即生效**。M2 的 `.mo` 在 p10 上的 **squashfs 文件** `/usr/share/usr_share_locale.squash`（挂载于 `/usr/share/locale`，loop0）⇒ 不能挂载点内写，但可**离线重建该 squash 后替换文件本体** | 会被"刷任何官方 SLP"覆盖（P5+bind 的本意正是 p14 刷机不丢）；p10 空间紧 |

## 8. 死路与教训（10-15 版 18 条 + 今日新增）

- **沿用**：10-12 版 15 条死路 + 10-15 版 D-16（SLP 整包不能进 git）/ D-17（"未上线"先排 4min 窗口）/ D-18（A1 已证 p7 可行 ⇒ A2 失败先查字节）。
- **今日新增**：
  - **D-19（★ 最重要）**：**"改 unit + `ExecStartPre`"的投递方式在本机不成立** —— 本机是「内核冷启 + 用户态恢复」，systemd 不重读 unit。判别口诀：`systemctl show <unit> | grep -c ExecStartPre`；若为 0 而文件里有 ⇒ 就是这条。
  - **D-20**：**离线模拟后端测不出"真机落点/路径"缺陷** —— T5 后端的 `lutload` 落点（工具在 SD 而非 `/opt`）只有上机 `probe` 才暴露，且会让 `rollback`（关闭语义）在关键时刻失效。凡"脚本内硬编码路径"的部件，上机第一步必跑 `probe`。
  - **D-21**：**路径两侧口径不同**（telnet 绝对 / FTP chroot 相对）+ **SD exFAT 目录项延迟导致 RETR 550** ⇒ 工具必须内建 `sync` + 退避重试（`nx-fetch`/`nx-probe` 已修）。
  - **D-22**：**长命令勿经 telnet 直跑**（会话超时截断输出，表现为"只回第一行"）⇒ 一律 `setsid` + 落盘轮询。
  - **D-23**：**门控必须在"小A 克隆"跑**（Codex 克隆缺 `.uploads/` 会给出 G4 假 FAIL）—— 本次同时验证：同一提交在两份克隆可给出不同的门控结论。
  - **D-24**：`.mo` 真机件**无 header 元数据**（无 charset 声明）⇒ glibc 用原字节（相机中文正常即证）；Python `gettext` 对该类文件不可用属固有性质。
