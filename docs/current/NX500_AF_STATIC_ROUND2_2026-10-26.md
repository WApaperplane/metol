**主脸选择：明确的中心与面积打分，而非身份保持**

当前机器码确认两层处理：

1. `0x1438d8` 对当前脸框与历史脸框做几何比较。包括约 0.78～1.22 的宽高相似度范围、中心位移阈值，以及沿用旧框或取平均的分支。随后在 `0x143ca4` 尾调用 `0x143740`。
2. `0x143740` 才是主脸打分函数。它针对每张脸计算面积 `width*height`，以及脸中心到画面中心的距离平方；调用 `0x14360c` 分别生成名次。

名次按“越靠近中心越高”“面积越大越高”排列。实际选择规则为：

```text
score(face) = 6 × 中心接近度名次 + 3 × 面积名次
main_face = 得分最高的脸；相同得分保留较早的索引
```

这是名次加权，不是把像素距离和面积直接按 2:1 相加。机器码 `0x143894..0x14389c` 完成两项权重组合，`0x1438c4` 写入主脸索引。

该评分函数没有读入“用户先前选中的人”“上一次主脸身份”或人脸特征。现有几何匹配使脸框更稳，但不能自动等同于跨遮挡身份识别。当两个人的位置、大小名次改变时，评分可能选到另一个人；这是静态推导出的失效条件，尚未通过实拍确认其发生频率。

更合适的优化不是单纯把中心权重调小，而是为已选主体加入保持条件：先按位置、大小、历史运动做同一目标关联，再决定是否允许其他脸替换；短暂丢失与明确换人应使用不同条件。近邻双人交叉仍可能使仅用几何的关联出错。

证据：`test_server/af_static/out/p7_00143740.asm`、`p7_0014360c.asm`、`p7_001438d8.asm`。

**实时双眼路径已接通到现有取景任务**

第一轮只确认了眼部处理与拍后美颜的联系。本轮继续追踪后确认，实时任务也会调用同一套双眼算法：

```text
0x1441dc  CFDTask::EventHandler
    └─ 0x143d30  取景人脸检测、框处理、主脸选择
    └─ 模式 3 → 0x1430ec  SmileDetection
       模式 4 → 0x143230  WinkDetection
                     └─ 0x177da0
                          └─ 0x1ec3cc
                               └─ 0x3dc910  双眼定位
```

`0x1442e8` 是人脸检测调用，`0x1444ec` / `0x1444bc` 分别通往 Smile/Wink。任务使用 `this+0x18` 的图像缓冲和 `this+0x2e/+0x30` 的尺寸。Smile/Wink 两条路径均把 `this+0x54` 的脸信息缓冲传给眼部算法。这已经是取景任务中的调用关系，不再只是名字或未使用的 EyeDetection 日志。

眼部计算与自动拍摄触发的分支是分开的：

| CFDTask 字段 | 已观察到的用途 |
|---|---|
| `this+0x918` | 选择任务模式；3 分支调用 Smile，4 分支调用 Wink |
| `this+0x945` | Smile 路径的启用检查 |
| `this+0x946` | Wink 路径的启用检查 |
| `this+0x947` | Smile 计算之后的拍摄通知阻止条件 |
| `this+0x948` | Wink 计算之后的拍摄通知阻止条件 |

例如 Smile 在 `0x143134` 先调用双眼定位，再执行表情计算，随后 `0x14314c` 才检查拍摄通知条件；Wink 对应 `0x143274` 和 `0x14328c`。这说明可以在设计上复用双眼计算，而不必把“笑脸/眨眼自动拍摄”作为眼部 AF 的前提。本文没有改变这些字段，也不把修改字段当成已经验证的控制方案。

尚未确认的是双眼定位在普通人脸模式下能稳定运行到什么帧率、侧脸和小脸可靠性如何，以及它与其他图像任务的预算。现有算法“用于实时任务”不等于现代眼部 AF 所要求的精度、延迟与覆盖范围已经达标。

**部分脸信息布局已恢复，可直接用于下一轮数据流分析**

当前代码使用的脸信息载荷为 `0x444` 字节；最多 10 个条目，每个矩形记录步长 `0x14`。

| 载荷内偏移 | 观察到的内容 |
|---|---|
| `0x000 + i*0x14` | 第 i 张脸的 x、y、宽、高，分别在 +0、+4、+8、+0xc |
| `0x0c8 + i*0x14` | 眼 A 的矩形；+0x10 为有效标志字节 |
| `0x190 + i*0x14` | 眼 B 的矩形；+0x10 为有效标志字节 |
| `0x258 + i*4` | 第 i 张脸的方向/角度信息；眼部处理据此旋转坐标 |
| `0x398` | 主脸索引 |
| `0x39c` | 人脸数量 |

双眼结果的关键写入位于 `0x3dcc48..0x3dcc68`。基本人脸结果整理函数 `0x3d4f44` 会先清掉两眼的有效标志；所以不能仅因为载荷中有眼框数组，就假设普通人脸模式每帧都带有有效双眼结果。

上述是已观察到的部分布局，不是完整公开 ABI。眼 A/B 的人体左右、屏幕镜像后的左右，以及所有模式中的坐标域仍待确认。

**眼部结果与 AF 之间，已定位到具体的连接位置**

第一轮中的间接虚函数调用已通过构造器和当前样本的 vtable 解出：

```text
0x2c01bc 获取系统数据接口
    vptr = 0x805de008，RTTI 名称 CIQ_SysDataIF_NX1
    slot +0x244 → 0x2c150c → 0x14201c：有效人脸数量
    slot +0x240 → 0x2c13b8 → 0x141a80：主脸区域
                                 ↓
                       0x2f6c48 人脸获得/丢失策略
                                 ↓
                       0x2f6ae0 / 0x2f763c AF 区域更新
```

`0x141a80` 读取 `0x398` 的主脸索引，再复制脸矩形，而非眼 A/B。它返回的区域包含六个字：x、y、宽、高、源宽、源高；方向与人脸数量从另外的输出指针返回。`0x2c13b8` 在调用之后还检查区域及源尺寸是否为正。

因此眼部 AF 的静态设计已能收窄为：

1. 在取景任务中对已选主脸执行现有双眼定位，保留时间/帧对应关系。
2. 在进入 AF 的区域封装中，可靠眼框存在时生成眼部 ROI；无效、过小或过期时回退到脸部区域。
3. 保留原厂坐标域、源尺寸、边界和锁焦规则；眼框大小必须与实际 AF 测量能力匹配。

应优先研究 AF 使用的区域副本，避免直接改共享脸矩形，否则可能同时影响脸部曝光、框显示或表情判断。该连接方案仍是设计候选，未编译、未部署；也尚未确认共享结果的锁、发布时刻及缓存生命周期。

**追踪计数：8/4/4 初值与实际消费者**

构造/初始化函数 `0x29b4e4` 使用基址 `0x81550220`。加上内部偏移后，正好落到 GAF 的三项字段：

| 参数 | 初始化基址偏移 | 等价 GAF 偏移 | 静态初值 | 后续处理对象字段 |
|---|---|---|---:|---|
| 连续 NG 停止阈值 | `+0x22c` | `+0x44` | 8 | `+0x150` |
| 小目标抖动参数 | `+0x230` | `+0x48` | 4 | `+0x158` |
| 连续 OK 启动阈值 | `+0x234` | `+0x4c` | 4 | `+0x154` |

初始化写入分别在 `0x29b56c`、`0x29b500`、`0x29b504`。这些是启动代码中的初值，不证明机身运行时仍保持它们。

`0x34e9c8` 将参数复制到多区 AF 处理对象；在 GAF 内部阶段小于 4 且 `GAF[3]&0x20` 为零时使用上述配置，否则改为 NG=`0x1e8480`（2,000,000）、OK=0、small=0。可见参数是否生效受执行阶段和标志控制。

已确认的消费者：

- `0x3514a0` 在相应 AF 模式及状态下累加计数，并在 `0x35158c..0x35159c` 与对象 `+0x150` 比较，达到阈值后走重置/重选路径。
- `0x351034` 在状态值 2 持续出现时累加另一计数；`0x35127c..0x35128c` 读取对象 `+0x154`，满足条件后调用后续转换处理。
- small 已确认从 GAF 复制到对象 `+0x158`，本轮尚未找到它的明确实际读取链。暂不把它当成已确认有效的调参旋钮。

另一个补丁设计细节：small 和 OK 的初始化共用 `0x29b4f8` 的同一条 `MOV #4`。直接修改这条常量会同时改两项，不能把它当成仅修改 OK 的独立位置。

GAF `+0x5c` 是内部执行阶段，已确认的写入包括：

**高速连拍预测：算法选择值已追到上游调用者**

现在确认的路径是：

```text
0x33bfcc ExecuteExposurePredictContiH
    0x33bff0：r1 = 1
    0x33bff8：调用 0x36f634
        selector=1 → 0x36f4f0 → 线性预测 + 修正
        selector=0 → 0x36f13c
                         样本 <2：最近位置
                         样本 =2：线性预测
                         样本 ≥3：0x36ecc4 二阶预测
```

在已扫描的 A32 直接调用范围内，分派器 `0x36f634` 只找到上述调用者，且传入 1。不能将这个结论扩展为“任何间接路径都绝不使用算法 0”，但已足以说明：二阶算法虽然存在，当前确认的 Conti-H 入口不会选择它。

把常量 1 改成 0 并不是已验证的优化。两个入口还使用不同的数据整理/有效性处理，二阶模型会放大样本噪声，必须先恢复样本选择和历史清空规则。本轮只记录原始指令 `0110a0e3`，不产生修改后的二进制。

**据本轮证据调整优先级**

| 顺序 | 候选改进 | 现在已有的具体依据 |
|---|---|---|
| 1 | 主脸保持、显式选人、降低多人场景误切换 | 现有几何匹配与主脸名次打分均已定位 |
| 2 | NG/OK 阈值与人脸进入/退出策略分开调节 | 有初值、消费者及执行条件 |
| 3 | 复用取景任务中的眼部定位，接入 AF 专用 ROI | 有实时调用链、结果布局与 AF 区域封装 |
| 4 | 人脸/对象追踪接力与遮挡重捕获 | 仍需解决第一轮发现的任务仲裁与目标关联 |
| 5 | 预测模型及曝光时刻补偿 | 已确认选择器，但样本筛选、误差和镜头差异仍未完整恢复 |

眼部 AF 现在可以按“复用现有实时算法、补 AF 闭环”继续研究，而不必预设从零训练。它依然不是一个已经找到开关的隐藏成品功能。
