## 主错误在生成器与加载器的接口

1. [`gen_luts.py`](../../tools/lutgen/gen_luts.py) 文件头明确把槽三个分量解释为 RGB；`build()` 第 467 行起枚举 RGB 网格，直接写 `apply_film()` 的 RGB 输出，没有 CrCbY 输入坐标转换和输出编码。
2. [`lut.sh`](../../scripts/lut.sh) 第 135 行起：`.bin` 分支直接交给写槽工具；只有 `.cube` 分支才调用转换器。因此新生成的 `.bin` 绕过了 19 日已修正的转换器。
3. [`cube2lut.c`](../../test_server/lutpipe/cube2lut.c) 现在的默认转换实际是 **CrCbY → RGB → RGB LUT → CrCbY**，并保留 `--legacy-rgb` 仅供历史复现。
4. [`19 日修复记录`](LUT_CRCBY_FIX_2026-10-19.md) 不只有文字：目录 `raw8/gates/lut/cube_regression_2026-10-19/` 保存了中性灰、色度方向、HP5、Fuji400H 的用户回答和实机导出。用户当时确认 HP5 为正常黑白、Fuji400H 严重偏色消失。

原生布局的工作约定为：

```text
输入坐标：Cr, Cb, Y
索引：((Y_index * 17 + Cb_index) * 17 + Cr_index) * 4
输出字节：Cr, Cb, Y, 0
格点：0,16,32,...,240,255
无彩色：Cr = Cb = 128；Y 可以变化
长度：19652 B + 末项重复 3 次 + 48 个 0 = 19712 B
```

本轮重跑 `audit_lut_coordinates.py`：原厂 A13、A17、A18 的 `(axis0=8,axis1=8,axis2=k)` 都 **17/17** 精确等于 `(128,128,level(k))`；A13/A18 历史实机快照与镜像逐字节相等。把三个字节命名为 RGB 后得出的“原厂蓝角点、白点、暗部色温”不能当 RGB 标定数据。

### 为什么 identity 正常而其他表全部怪

恒等表 `T(a,b,c)=(a,b,c)` 无论三个坐标叫什么都会返回输入。因此 `identity17` 正常不能证明它们是 RGB，轴方向各自只改变对应字节也不能证明它们是 RGB。

假设一张 RGB 设计对三通道都施加曲线 `f`，却被 CrCbY 引擎消费，那么实际变成：

```text
Cr_out = f(Cr_in)
Cb_out = f(Cb_in)
Y_out  = f(Y_in)
```

对中性输入，Cr/Cb 本应始终在 128。曲线只要把 128 提到 139，就把两条色度都推成正值，画面变品红；将 128 压到约 98，就使两条色度变负，画面变绿。**这不需要自动白平衡参与。**

同理，今天的 Bhalf 在错误坐标下减半的是第三分量 Y，因此主要降亮度；`R=G=B` 的所谓黑白表则把 Cr、Cb 和 Y 绑成同值，不能保证无彩色，还会把亮度范围压窄。这与实机描述一致。

## 不能继续沿用的排除方法与标定

- **“机端文件/槽回读一致，所以表没问题”不成立。** 哈希证明字节送达，不证明字节的色彩语义正确。
- **“R=G=B，所以只能是 LUT 后段偏色”不成立。** 仅对 RGB 输出成立；CrCbY 黑白应固定前两分量为 128。
- 今天 [`mk_ycc.py`](../../tools/lutgen/mk_ycc.py) 只逐项转换输出，输入索引仍保持 RGB；且只提供 YCrCb/Y CbCr 两种排列，均非 19 日确认的 **CrCbY**。两张失败不能排除正确的 CrCbY 编译方式。
- 用 `preview_photos.py` 按 RGB 读取 `.bin`，展示的是设计意图，不是相机消费该文件的结果。对这种预览做 dHue、dSat、Lab 统计，不能直接证明实机色彩正确。
- 用 RGB 解释原生三星表来拟合 `sat_env`、`bconv`、蓝区上限等，坐标前提无效。恢复编码后应重新评估这些补丁，不能宣布它们是三星色彩特征。
- sRGB/AdobeRGB 是输出色彩空间设置，不等于 ISP 内部 LUT 三轴就是 RGB。OLED 也会影响选表分支；目前证据不能确定其完整后段变换顺序。
- PW 七维需先固定，否则与 LUT 叠加；但它不是上述坐标错误的替代解释。
- 另有一个较小的导出错误：旧 `write_cube()` 把硬件的非均匀 `0,16,...,255` 节点直接写成标准 `.cube`。标准 `.cube` 节点应为 `i/(N-1)`；不能把两种采样网格混用。本轮候选配套 `.cube` 已按均匀 33³ 重采样。

## 最短的实机验收顺序

1. 固定 M 档曝光、ISO、白平衡、场景和照明；记录 PW 实际七维、输出色彩空间、OLED 状态及实际选中槽。先验证参数在半按/切档后没有回到旧槽，不能只看 prefman 存储值。
2. 同一场景依次比较 off → `c00_native_identity` → `c01_native_mono` → `c02_native_luma75` → off，每次按既有正常半按加载流程，记录实际槽字节和原始 JPEG。不要用裸 MMIO reload。
3. 原生 mono 应保持黑白；luma75 应降低亮度而灰阶中性。若仍偏色，继续定位现用配置、输入格式和后段变换，不能再通过修改胶片参数遮盖。
4. 比较 `c03_native_yellow`、`c04_native_blue` 的方向，确认黄色与蓝色可独立控制，然后只先验 Portra、Pentax Gold、Classic Chrome 三张恢复候选。
5. 成片和取景器分开核对，不能由 LCD 或 liveview 的单一现象推断 JPEG。记录成片哈希、曝光/WB、表哈希、原生中性轴，再评价方案本身。

**下一步生产修复应把 RGB 设计、原生编译、原生验收分成明确格式接口，并使生成器只通过同一个正确编译器输出机端 `.bin`。** 原厂 `.bin` 不得再次按 RGB 重新解释；未标编码的历史表不应自动批量转换。当前独立恢复包让这个改动已有可复现、可审查的候选，不需要继续让用户盲测几十张表。
