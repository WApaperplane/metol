# 17³ 能否扩到 33³（2026-10-31）

> 问题（木一）：**有没有可能把 17³ 扩大到现在比较主流的 33³。**
> 两条腿分开答：**硬件能不能**（静态证据）、**扩了值不值**（数值实测）。

---

## 0. 结论

| # | 命题 | 强度 |
|---|---|---|
| 1 | **硬件不可扩**：表长由 EP 的 DMA 控制器硬连线，p7 只写地址+脉冲，不写长度，也没有长度常量 | ★★★ |
| 2 | 槽池的几何本身反证 17³：103 个槽 × `0x4D00`，42 个槽各自是完整独立的表 | ★★★ |
| 3 | **对我们现有 12 张主表，33³ 的收益小于噪声**：均值 0.78–1.98 级，p95 1.8–5.4 | ★★★ 实测 |
| 4 | 对**强色相选择性**的表（导入的 Hasselblad 风格），17³ 损失达均值 7.7、p95 42，这时 33³ 才有意义 | ★★★ 实测 |
| 5 | 真需要 33³ 时，唯一路径是**成片后处理**（RAW → 33³ → JPEG），不是机内硬件 | ★★ |

## 1. 硬件：为什么扩不了

### 1.1 固件里没有任何"尺寸"概念

对 `p7_a2.bin`（12,075,648 B）做小端字面量全扫：

| 常量 | 含义 | 命中 |
|---|---|---:|
| `19652` | 17³ × 4B 表长 | **0** |
| `4913` | 17³ 节点数 | 9（全在 `0x94011c` 一带，非 3DLUT 区，且 0x1331 是常见指令立即数） |
| `35937` | 33³ 节点数 | **0** |
| `143748` | 33³ × 4B | **0** |
| `215622` | 33³ × 6B | **0** |

⇒ **p7 连自己搬多大的表都不知道。** 它只写 `+0x00c` 地址 + `+0x008` bit8 脉冲，长度由 EP 硬件的 DMA 控制器决定。

### 1.2 API 层也没有长度参数

```c
int d5_ep_3dl_load_lut(unsigned *addr, int sel, int fmt, int timeout);
```

四个参数，无 size、无 width/height。`d5_ep_lut_op_info_st` 里只有 `sel` / `fmt` / `cbcr_ch` / `bypass`。

### 1.3 寄存器块只有五个

全镜像 grep `0x2082b`：

```
+0x000 OnOff   +0x004 Cfg   +0x008 Pulse   +0x00c LUT0 addr   +0x010 LUT1 addr
```

没有尺寸、没有步长、没有第二级。

### 1.4 槽池几何反证

- 槽步长 `0x4D00` = 19,712 B
- 表有效 19,652 B + 尾部 60 B 指纹
- T1 实测：42 个槽**逐个都能完整读出**，每个槽尾部指纹都对得上
- 若硬件按 33³ 读（143,748 B），一个槽要吃掉 7.3 个槽位，42 个槽根本不成立；而且写 19.7 KB 后必然读到相邻槽的垃圾，画面会崩

**而实测写入 19,712 B 后，负片表渲染精确正确**（10-18 §1 第 8 步）。这是最硬的反证：硬件读的就是 19,652 B。

⇒ **17³ 是硬连线的。改 p7 也没用（它没有长度概念），只能改硬件。**

## 2. 数值：扩到 33³ 值不值

### 2.1 方法

同一张 33³ 设计 → 编译到 17³ native 格点 → 用 `native_codec.sample_rgb` 走完整硬件路径（RGB→YCbCr→节点查表→RGB）→ 与 33³ 插值结果在 20,000 个随机色点上比较。

（**不**拿 `looks/*.bin` 直接比，因为那些表经过 `balance_neutral_axis` + `stretch_levels` 后处理，与 `rgb_design_cubes` 不是同一映射——第一次跑出 37 级的差异就是踩了这个坑。）

### 2.2 我们自己的表

| 表 | mean | p50 | p95 | p99 | max |
|---|---:|---:|---:|---:|---:|
| kodak_portra400 | **0.95** | 0.71 | 2.53 | 4.50 | 7.8 |
| fuji_velvia50 | **1.98** | 1.43 | 5.35 | 7.80 | 20.9 |
| fuji_classicchrome | **0.78** | 0.63 | 1.83 | 3.47 | 10.7 |
| pentax_gold | **0.86** | 0.66 | 2.21 | 4.49 | 8.3 |

**均值不到 2 级，p95 在 2–5 级。** 参考量级：NX500 的传感器噪声在中间调约 2–3 级，JPEG 量化在平滑区也在这个量级。⇒ **对这批表，33³ 的收益被噪声吃掉，不值得。**

### 2.3 导入的强风格表（对照组）

`_lutweb` 里的 33³ 公开胶片 CLUT：

| 表 | 性质 | mean | p95 | max |
|---|---|---:|---:|---:|
| S5IIS2V | 线性→Log（近可分离） | **0.40** | 0.95 | 3.1 |
| L-Log_to_Natural_VLog | log→log 曲线 | 2.73 | 10.7 | 45 |
| HBNat / hb_std | 强风格胶片 | **7.3–7.7** | 40 | 147 |

⇒ **损失完全由表的"色相选择性"决定**：平滑的曲线/矩阵映射在 17³ 上几乎无损（0.4 级），强色相旋转 + 局部饱和压缩在 17³ 上会丢 7–8 级。

### 2.4 判据

要判断一张表需不需要 33³，跑一遍 `res_native.py`：

- `mean < 2` 且 `p95 < 6` ⇒ 17³ 够用
- `mean > 3` 或 `p95 > 10` ⇒ 33³ 有实际收益

## 3. 真要 33³，怎么走

| 路径 | 可行性 | 说明 |
|---|---|---|
| 改 EP 硬件尺寸 | ✗ | 无公开手册，无寄存器，API 无字段 |
| 改 p7 让其搬 33³ | ✗ | p7 没有长度概念，改了也没处写 |
| 双 LUT 串联模拟 33³ | ✗ | 上一轮已证硬件只有一级且串联有损 |
| **成片后处理（RAW → 33³ → JPEG）** | ✅ | `ksfilm.arm` 在相机侧跑，或 PC 侧；非实时 |
| 预览用 17³、成片用 33³ | ✅ | 与「双槽分发」天然契合 |

**最后一条是唯一有产品意义的组合**：取景器 17³ 够看（误差 1–2 级肉眼难辨），成片用 33³ 后处理拿满精度。前提是拍 RAW（SRW），否则二次 JPEG 处理会叠加压缩损失。
