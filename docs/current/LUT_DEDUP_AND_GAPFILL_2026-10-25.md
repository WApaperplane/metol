## 先记一笔：Codex 修正了我的方法

上一轮我用"沿灰轴投影"处理越界格点。Codex 在 33³ = 35937 个**合法** RGB 输入上
跑完整插值链，实测：

| 恒等表编译方法 | 最大通道误差（8bit） |
|---|---:|
| 直接原生恒等 | 0.886 |
| RGB 逐通道裁切（旧） | 7.597 |
| **WorkBuddy 灰轴投影（我的）** | **41.018** |
| 边界单元线性外推（Codex） | 0.886 |

它的批评成立：我用"越界节点占 80.5%"论证严重性，但越界比例不等于合法输入的
误差；投影虽保持了仿射恒等，却不能保证任意非线性外推正确。合法 RGB 上的 41 LSB
是硬伤。同时它指出"固定 Lab 明度压色度会在高亮黄色附近造成急剧漂白"——这是它
自己初稿踩的坑，也说明这类变换在该色域角落都危险。

**结论**：我接受这条修正。物理链本身（光谱 H&D + 染料密度）仍然成立，但**边界处理
必须用 Codex 的线性外推**，不是我的灰轴投影。后续若回到物理链，须改用该方法。

## 同质化：不是"有点重复"，是三分之二冗余

90 张表、4005 对，用与 Codex 去重门槛相同的口径度量（12 色相 × 2 饱和 × 3 亮度
= 72 探针 + 21 灰阶 + 8 实景色，取两表间的**中位 CIEDE2000**）：

```
p10  2.53    p25  3.96    p50  6.41    p75  9.75    p90 13.65
两两 < 1.0 （分不出）      0.5%
两两 < 2.3 （JND 边缘）     7.8%
两两 < 3.112（项目门槛）   16.0%
```

单链接聚类在 3.112 下把 72 张连成一簇——那是链式效应（A≈B、B≈C 不代表 A≈C），
没有意义。换**完整链接**（保证簇内任意两张都在阈值内）：

| 阈值 | 簇数 | 可删 | 清理后 |
|---|---:|---:|---:|
| 1.5（几乎相同） | 61 | 27 | 90 → 63 |
| 2.3（JND） | 40 | 48 | 90 → 42 |
| 3.112（项目门槛） | 32 | **58** | 90 → 32 |

**90 张表实际只有 32 种可区分的外观。** 用户的感受是对的，而且比感受更严重。

最终按 1.5 保守清理，人工裁定保留项（算法用"名字短优先"曾想删 Kodak Portra 400
留 Leica M9、删 Kodak Gold 200 留 Agfa Vista 200，这类必须人工纠正）：

- 本地 `looks/` 102 → **75** 张，27 张移入 `_lut_dedup_20261025/archived_redundant/`
- 机端 72 → **54** 张（18 张重叠），移入 `/mnt/mmc/lut/archive_20261025_dedup/`
- 两处都是移动而非删除，`encoding.json` 同步移除条目

清理后：

| 指标 | 清理前 | 清理后 |
|---|---:|---:|
| 表数 | 90 | 75 |
| 中位 dE00 | 6.41 | **8.94** |
| p10 | 2.53 | **3.70** |
| JND 内 | 7.8% | **2.6%** |
| < 3.112 | 16.0% | **6.6%** |

剩下最近的只有 `identity17/samsung_a02` 0.486 和 `samsung_a00/a01` 0.876——
全是必须存在的基准表。

## 库的形状：一条窄带

只看重复还不够，得看**覆盖**。六个可解释轴（`coverage.py`）：

| 轴 | 现有 90 张的范围 | 含义 |
|---|---|---|
| warmth（平均 b\*） | 0.4 ~ 11.8 | **没有一张整体偏冷** |
| saturation（平均 C\*） | 33.7 ~ 56.2 | 没有一张真正高饱和 |
| contrast（灰阶中段斜率） | 0.62 ~ 1.38 | 既不平也不硬 |
| black_lift（黑位 L\*） | 0 ~ 17.1 | 没有真正的抬黑 |
| white_level（白点 L\*） | 96.6 ~ 107 | **没有一张压白点** |
| shadow/high tint | −14.6 ~ 9.4 | 分离色调幅度都很小 |

这不是"风格不够多"，是**每一张都落在同一个舒适区**。所以第三件事不是继续加，
而是去填空的坐标。

## 一个必须说明的上限

`chrome_vivid` 初版 sat=2.55，实机上**橙色箱子（约 230,120,40）变成了洋红**。
原因不是调参失手，是色域：橙色在增饱和时 B 先归零，之后只剩 G 可以继续压，于是
色相被推向红/品红。实测：

| sat | 实测饱和 | 橙 (230,120,40) → |
|---:|---:|---|
| 1.60 | 54.7 | 251/87/0 |
| 1.95 | 58.8 | 253/63/1 |
| 2.20 | 61.3 | 254/46/7 |

取 sat=1.75（实测约 57，刚超过原库上限 56.2），橙色保住。**"超高饱和"这个象限在
17³ + 8bit 上是部分不可达的**，不是没做够，是做不上去。凡是靠堆饱和做"浓艳"的方案
都会在暖色区先崩，这正是"偏品红"抱怨的另一种成因。
