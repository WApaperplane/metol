## 4. ★ 裁决建议：是否转「UI 级修改」

用户问：「讨论有没有必要直接进行 UI 级修改。」

### 4.1 结论（建议）

> **暂不动 UI 级。先根因 A2（§3）。** UI 级修改是更重、更危险的变更，且解决的是「功能如何被菜单触达」，而非「p7 管线能否算出效果」——二者是不同问题。

### 4.2 论据

1. **p7 通道已被 A1 实机证明可行**：A1（p7 灰度补丁）刷后 `a1_verify` 三判据全 PASS ⇒ p7 补丁这条路本身走得通。A2 失败 ≠ p7 不行，只说明「这一版 A2 补丁」有问题。
2. **UI 级风险更高**：UI 级 = 动 `di-camera-app` 渲染/菜单。已知该机型有 hibernation 联锁，`restart di-camera-app` 实测 ⇒ 整机卡死须物理重启；且 App 生命周期对 mod 极敏感。**在根因未明时叠加 UI 级改动，会把两个变量搅在一起，无法定位。**
3. **既有「内存注入」近路未穷尽**：`poker <pid> <addr:value>` 已存在（`a_init.sh` 用 `pgrep di-camera-app` 打 9 组补丁），属「App 启动后注入」通道，比改 `di-camera-app.service` 本体更轻、可逆。UI 级诉求（让功能在菜单可见/可触发）可先在这条通道上验证，不必先动 UI 源码。
4. **A2 的「档位池直写」本质是 p7 数据通路**，失败点在补丁字节或刷写，不在 UI 呈现。

### 4.3 触发「转 UI 级」的条件

当且仅当根因排查得到以下结论之一，才建议启动 UI 级：
- H1/H2 证明 A2 补丁在 p7 层因**架构性限制**无法承载（而非单纯字节 bug）；**且** poker 内存注入也无法绕过。
- 业务目标本身要求「在机身菜单原生呈现」（而非靠 `st app`/`poker` 脚本触发）。

→ 若走到这一步，起点文档是 `docs/current/UI0_HOST_FEASIBILITY_2026-10-13.md`（已论证 P1 drop-in 在「每次开机」场景是死路，改走 P5 改 service 本体或 poker 注入）。
