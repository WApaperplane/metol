# 机身 .cube 转换器 cube2lut（2026-10-18）

> **2026-10-25 作废声明**：本文描述的"已修成 CrCbY"从未真正发布多时——release ≤10 的包内
> 仍是 RGB 直通的 8,880 B 旧二进制，而源码树里那个版本又因钳位把 80% 越界格点压平、连恒等
> 都做不对。现已重写边界处理并重编（`b798964d…`），机端实跑恒等逐字节 0 差。**以
> [转换器修正](CUBE2LUT_NATIVE_FIX_2026-10-25.md) 为准**，下文仅作历史记录。

> **最新修复已安装**：默认转换现在是 RGB cube → CrCbY 输入/输出坐标，HP5、Fuji400H 候选实机正常，36 张可追溯导入表已重建。下文为旧 RGB 实现的历史记录；最新行为、验证和回退见 [CrCbY 修复](LUT_CRCBY_FIX_2026-10-19.md)。旧输出可用 `--legacy-rgb` 复现。

> **2026-10-19 证据边界修正**：下文验证的是 ARM 与 PC 的 RGB 重采样一致性，不代表与相机 LUT 的色彩坐标一致。原厂中性轴强烈支持 C1/C2/Y 解释；当前转换器在输入、输出两侧均按 RGB，见 [色彩坐标审计](LUT_COLORSPACE_AUDIT_2026-10-19.md)。下文“半按后画面/成片生效”不能作为任意 `.cube` 的通用验收结论。

> **一句话**：把 Adobe `.cube` 丢进 SD 卡，在相机上一条命令转成 19,712 字节的槽表，不需要 PC。ARM 定点输出与 PC 浮点参考**逐字节相同**。

## 0. 为什么放在机身上

相机 rootfs 没有 Python，`test_server/isp/nx3dlut.py` 只能在 PC 跑。导入一个 look 若要"拷卡 → 上机 → 生效"闭环，转换就必须在机上完成。本工具即为此实现，无 libc / libm / libgcc 依赖。

## 1. 用法

```sh
# 相机端（路径须绝对；FTP 已 chroot，telnet 侧 CWD 不是 /mnt/mmc）
/opt/usr/nx-ks/cube2lut.arm /mnt/mmc/looks/portra400.cube /mnt/mmc/looks/portra400.bin
```

输出 = 槽表本体 19,652 B + 60 B 零填充 = **19,712 B**，可直接交给 `nx_slotwrite.arm` 写入任意空闲槽。

```sh
# 完整导入链（以 A18 为例）
nx_slotwrite.arm commit 0x81119F00 /mnt/mmc/looks/portra400.bin /mnt/mmc/looks/a18_orig.bin
nx_regtabwrite.arm patch        # 或 patch12 / still-set，取决于要改 View 还是 Still
# 半按一次触发重载 → 画面/成片生效
```

## 2. 格式契约

| 项 | 规定 |
|---|---|
| 输入 | `LUT_3D_SIZE N`，`N≥2`，节点数必须恰为 N³ |
| 轴序 | **R 变化最快**（Adobe 规范）。非规范文件（如本仓 `_luttest/identity33.cube` 实为 bgr）**不会**被自动纠正 —— PC 版有 `detect_order`，ARM 版没有 |
| DOMAIN | 只接受 `0..1`。`DOMAIN_MIN` 非 0 或 `DOMAIN_MAX` 非 1 直接报错退出，不猜 |
| 1D cube | 不支持，明确报错 |
| 输出 | 4,913 项 × `{R,G,B,0}`，索引 `((B·17+G)·17+R)·4`，网格 `{0,16,…,240,255}` |

**为什么拒绝而不是兼容**：domain 或轴序读错时，转换会成功并产出一张"看起来合理但是错的"表。这种错误在画面上很难识别，而报错一眼可见。

## 3. 验证（上机实证）

三份 cube 分别在相机和 PC 上转换，结果逐字节比对：

| 用例 | 规模 | 差异字节 | 最大差 |
|---|---|---:|---:|
| `identity17`（恒等） | 17³ = 4,913 节点 | **0** | 0 |
| `invert17`（255−x 反相） | 17³ | **0** | 0 |
| `warm33`（R×1.15 截断、B×0.85） | 33³ = 35,937 节点 | **0** | 0 |

`warm33` 是关键用例：它检验的是 **33³ → 17³ 的三线性重采样**，而不只是格式搬运。

附加断言（`test_cube2lut.py`，9/9 PASS）：
- `identity17` 输出 == 解析预期的硬件网格（逐项）
- `invert17` 输出 == `identity17` 的逐字节补码（pad 字节除外）
- 尾部 60 B 全零、每项 pad 字节恒 0
- 源码内无浮点、无 `atof`；domain 与 1D 的拒绝路径存在

## 4. 实现要点

- **全定点 Q16**：`.cube` 的浮点文本按 4 位小数解析为 Q16（`fp*65536/10000`，常数除法由编译器转成乘法），插值全程整数，避免 soft-float 调用 libgcc
- **无 64 位除法**：只有 64 位乘法（`smull`），除法全部是常数
- **内存**：输入整文件 mmap 匿名区（上限 16 MB），节点表 `N³×3×4 B`（65³ 时约 3.3 MB），不占栈
- 二进制 7,864 B，`-nostdlib -static -O0 -marm -mfloat-abi=soft`

## 5. 边界

1. 非规范轴序不纠正（PC 版会）
2. log/其他 domain 不支持（需先在 PC 归一化）
3. 1D LUT 不支持
4. 未做黑点/白点归一化以外的任何色彩管理，输入输出都是同一条 R/G/B 轴
5. 转换本身不碰相机寄存器，只写文件

### 7.3 真正的产品化入口：`/mnt/mmc/lut/lut.sh`

工具三件套本来就已落在 `/mnt/mmc/lut/`（与本地 build 同 md5），上层封装是 `lut.sh`：

```sh
/mnt/mmc/looks/                    # ★ 滤镜库：放 .cube 或 .bin，二选一即可
sh /mnt/mmc/lut/lut.sh list        # 列出库里的 look
sh /mnt/mmc/lut/lut.sh begin       # 取还原点（只读，不写寄存器）
sh /mnt/mmc/lut/lut.sh apply <名>  # .cube 自动机端转换 → 写 A18 → View4[3]+Still6 同时指向 A18
#   → 半按一次快门生效（面板不会关）
sh /mnt/mmc/lut/lut.sh off         # 还原（登记表回原厂 + A18 回备份）
sh /mnt/mmc/lut/lut.sh status      # 当前 look / 备份状态 / 登记表前两项
```

库名不带扩展名。同名同时存在 `.cube` 与 `.bin` 时，`apply` 优先 `.cube`。

### 7.4 `look2slot.sh`（批量预转，只写文件）

`lut.sh apply` 是"转一张用一张"。若要**先批量转好再挑**（或想在不动寄存器的前提下检查
一批 cube 的网格规格），用新增的 `look2slot.sh`：

```sh
/opt/usr/nx-ks/look2slot.sh        # 扫指定目录，.cube → 同名 .bin（跳过已最新）
/opt/usr/nx-ks/look2slot.sh -f     # 强制重转
```

- 只写文件，不碰寄存器、不碰 `/dev/mem`
- 单文件失败不影响同批，末尾给 `converted/skipped/failed` 计数
- 转换日志留 `<name>.conv.log`（含 `GRID n`）

### 7.5 旧表兼容性（已实测）

`/mnt/mmc/filmlab/luts/*.bin` 共 10 张（Kodak Portra 160/400/800、Ektachrome 100VS、
Elite Chrome 400、Kodachrome 64、A00/A01/A02、_identity）**全部恰为 19,712 字节**，
即已经是槽格式，可直接 `cp` 进 `/mnt/mmc/looks/` 后 `lut.sh apply`，无需重转。

**一处瑕疵**：抽样 `Kodak_Portra_400.bin`，表本体（19,652 B）内 pad 字节全零 ✅，
但**尾部 60 B 有 9 个非零字节**（PC 版 `nx3dlut.py` 在该区写了元数据）。
这 60 B 是槽间填充，p7 不读，**功能上无害**；要整洁就在写入前清零 `[19652:19712]`。

### 7.6 ★ 禁区：不要从 ARM 侧强制 reload

`nx_regtabwrite.arm reload <addr>` 虽然存在，但**不要用**。裸写 `+0x00c` 加脉冲会让
ISP 读到"口袋体系"外的地址组合，表现为严重偏色花屏，且只能靠半按快门让 p7 自己走完
选表流程才能复位。`lut.sh apply`／`off` 都刻意**不自动 reload**，正是这个原因。

⇒ 生效方式只有一种：**半按快门**（或切档/拍照，凡触发 p7 自身 Load 的动作）。



## 8. ★ 科学计数法 bug 与修复（2026-10-18 12:0x）

### 8.1 现象

用 G'MIC Film-Luts 仓库（296 张，全部 13³）实测时发现：**转换"成功"但输出 93% 是零**。

```
GRID n = 13
NODES parsed = 2197      ← 计数正确
OUTPUT bytes = 19712
last entry  R = 0        ← 应该是 248
```

实测 `portra400`：4,913 项里 **4,569 项是 (0,0,0)**，只有 R 轴前 17 项（= 第一行）正确。

### 8.2 根因

G'MIC 把极暗的值写成科学计数法：`2.2439395252149552e-05`。旧 `fixed16()`：

```c
while (is_digit(*s)) { ip = ...; ++s; }   /* 读成 2 */
if (*s == '.') { ... }                    /* 读 .2439 */
*pp = s;                                  /* s 停在 'e' */
return ip * 65536u + ...;                 /* 返回 2×Q16 */
```

下一个值从 `'e'` 开始：不是空格、不是数字、不是点 ⇒ **返回 0 且 `*pp` 不前移**。
于是此后 6,000 多次调用全部返回 0，而 `rows_seen` 仍按 `i % 3 == 2` 递增到 2,197，
`rows_seen != nodes_count` 的检查**通过**。

⇒ 这是一个"静默产出黑表"的故障，正是文档 §2 里说要避免的那类错误。

### 8.3 影响面

| 来源 | 18 张里含科学计数法 |
|---|---:|
| G'MIC Film-Luts | **12** |
| 自造测试用例（identity17 / invert17 / warm33） | **0** |

旧证据包全绿，是因为三个用例的值都落在 0.01 以上，**从未触发该分支**。
这不是"测试通过所以没问题"，是"测试没覆盖"。

### 8.4 修复

1. `fixed16()` 支持 `e±NN`（含正负号、指数夹到 40 以内防溢出）
2. 解析失败**返回 -1 并报 `FAIL bad number at value index = N`**，不再静默给 0
3. 解析完成后若整表全零，报 `FAIL parsed table is all zeros` 并拒绝写出
4. 支持前导 `+`/`-`；负值一律夹到 0（槽表是 0..255）

新二进制 8,880 B，md5 **`582b12f0cc9f04ca765a8989d664b580`**（旧 `7cd4adff…`）。

### 8.5 回归

| 用例 | 结论 |
|---|---|
| `identity17`（17³，无科学计数法） | 仍与旧证据**逐字节相同**（`f5b22a81…`），改动未破坏原路径 |
| `portra400`（13³，含 2 处 `e-05`） | 与 PC 浮点参考差 320 B / 19,652 B，**最大 1 LSB**；末项 (248,249,248) ✅ |
| `px70` / `velvia50` / `kodachrome64` | 同上，差 293–315 B，最大 1 LSB |

13³ → 17³ 是**升采样**，与 17³（零重采样）、33³（降采样）走的是不同分支，本次一并验过。

测试 `test_cube2lut.py` 扩到 **14 项**：新增 `ScientificNotationRegression` 三例 +
源码守卫两例（`*s == 'e'` 分支、失败报错串）。
证据：`raw8/gates/lut/cube2lut_2026-10-18/portra400_sci{,_arm,_pc}.*`
