## 一句话结论

第六轮悬着的「6 个块是干什么的」有答案了，同时得到一个更要紧的负结果：**`0x30006` / `0x30007` / `0x60084` / `0x1001e` 这类 `0xNNNNN` 形式的 ID 属于一个和第七轮那 184 个槽位完全无关的第二套命名空间。** 用第七轮的字段表去读它们，会得到一整套看起来合理、实际错位的名字。

第二套空间叫 **`CAFData`**：一个静态 hub（`0x816d2ce0`）下挂 **6 个块 + 1 个短数组**，共计 330 个 `u32` 条目，`id = 块号 << 16 | 下标`。六个块全部具名：`LensSpec`(39)、`Ae`(18)、`UserData`(11)、`State`(37)、`Debug`(61)、`Sequence`(164)。

## 一、hub 与它的六个块

```
0x336e7c  hub_get_singleton()          → 0x816d2ce0（守卫字在 0x816d2cc0+0x18 bit0）
0x336c5c  hub_ctor(hub)                构造成员
0x33273c  hub_set(hub, id, value)      块号跳表 → 尾调 CAFData::SetData
0x332948  hub_get(hub, id)             同上 → 尾调 CAFData::GetData
0x3b53c8  CAFData::SetData(this, id, v)
0x3b546c  CAFData::GetData(this, id)
0x3b5348  CAFData::CAFData(this, count, block_id)   ← 各块初始化器共用
0x335330  hub+0x34 短数组，id <= 0xa 走这条
```

构造函数 `0x336c5c` 的动作可以直接照抄出来：六次 `malloc(0x18)` → 六次块初始化 → 六次 `str r5,[r4,#slot]`。

| 块号 | 名称 | 条目 | 基址 ID | hub 偏移 | 初始化器 | vtable |
|---|---|---|---|---|---|---|
| 1 | `LensSpec` | 39 | `0x10000` | `+0x08` | `0x3b676c` | `0x8063b958` |
| 2 | `Ae` | 18 | `0x20000` | `+0x0c` | `0x3b5c6c` | `0x8063b8c8` |
| 3 | **`UserData`** | 11 | `0x30000` | `+0x10` | `0x33a40c` | `0x80624e90` |
| 4 | `State` | 37 | `0x40000` | `+0x14` | `0x33a168` | `0x80624e50` |
| 5 | `Debug` | 61 | `0x50000` | `+0x18` | `0x3b5d18` | `0x8063b908` |
| 6 | `Sequence` | 164 | `0x60000` | `+0x1c` | `0x339ffc` | `0x80624e10` |

名称不是猜的：每个初始化器在末尾用 `movw/movt` 把字符串地址写进 `obj+0x10`，而 `CAFData::GetData` 的越界日志就是 `"  [CAFData:%s]::GetData Out of range id[%d]"`——`%s` 正是这个 `+0x10`。类名、字段布局、越界行为三者互相咬合。

块布局（`0x3b5348` 建立，`0x3b53c8/0x3b546c` 使用）：

```
+0x00  vptr
+0x08  count            ← 越界判据：index >= count 就写日志返回 0
+0x10  tag 字符串        ← 日志里的 %s
+0x14  u32 array         ← malloc(count*4)
```

## 二、这次普查怎么做才算对

前几轮只扫 `0x33273c`（hub 中介），漏了直接调用 `CAFData` 的那一半。四个入口合起来才是完整的数据面：

| 入口 | 调用点 | 常量 ID 复原 | 未复原 |
|---|---|---|---|
| `hub_set` `0x33273c` | 711 | 678 | 33 |
| `hub_get` `0x332948` | 1395 | 1333 | 62 |
| `SetData` `0x3b53c8` | 141 | 137 | 4 |
| `GetData` `0x3b546c` | 3 | 2 | 1 |

复原出 **297 个不同 ID**（未复原的是 ID 由寄存器算出来的点，静态看不到）。全量结果在 `out/round8/id_census.tsv`，列：`id / block / index / block_tag / reads / writes / via_hub / via_direct`。

**一个必须记住的坑**：ID 复原不能简单地把「最近的 `mov r1`」和「最近的 `movt r1`」拼起来。跨越了一次 `bl` 就会拼出假 ID——第一版脚本因此凭空造出 `0x70000`（读 8 次，永远是 0），第二版把它当成「固件里的空块」差点写进报告。正确做法是回扫一遇到分支就停。修掉之后假 ID 全部消失。

## 三、条目数六连中：`max(used_index) == count - 1`

这是本轮最硬的旁证。每个块实际被访问到的最大下标，恰好等于它的 `count - 1`：

| 块 | count | 使用到的槽 | 最大下标 | count−1 |
|---|---|---|---|---|
| `LensSpec` | 39 | 39（全覆盖） | 38 | 38 ✓ |
| `Ae` | 18 | 17 | 17 | 17 ✓ |
| `UserData` | 11 | 10 | 10 | 10 ✓ |
| `State` | 37 | 36 | 36 | 36 ✓ |
| `Debug` | 61 | 52 | 60 | 60 ✓ |
| `Sequence` | 164 | 139 | 163 | 163 ✓ |

六个独立数字全部落在边界上，说明 `count` 不是别的什么东西，就是数组长度，而且这套 ID 编码在整镜像里被一致使用。

## 四、和第七轮那 184 个槽位的关系：没有关系

| | `CIQ_SysDataIF_NX1` 数组 | `CAFData` hub |
|---|---|---|
| 单例 | `0x81561cf4` | `0x816d2ce0` |
| 容量 | 184 个 `u32`（对象内 `+0x04..+0x2e3`） | 330 个 `u32`（6 块，各自 `malloc`） |
| ID 形式 | `0..183` | `块号<<16 \| 下标` |
| 地址规则 | `obj + 4 + 4*id` | `block->array[idx]`，带边界检查 |
| 写入口 | 虚函数槽 `0x014` `SetParameter(id,value)` | `CAFData::SetData` |

三条理由说明它们不可能是同一块内存：容量 184 vs 330 无法调和；块数组是构造时 `malloc` 的，184 槽在 IQ 单例对象体内；`0x30007` 若按 IQ 数组解释是偏移 `0x1c`，按块解释是「第 3 块第 7 项」（该块只有 11 项），两者数值空间完全不同。

> **所以：`0x30006` 不等于第七轮表里的 `eIQ_ID_AF_FOCUS_LIMIT_STATUS`（id 6），`0x1001e` 不等于那个表里的任何一项。** 第七轮的 184 行表只在「ID 是 0..183 的纯整数」时才成立。

顺带排掉第三个诱饵：镜像里另有一张**至少 75 项**的字段打印名表（`0x2d15ec`–`0x2d1714`，下标 0 = `.AEMode`、1 = `.Meter`、12 = `.AFMode`、13 = `.AFArea`、74 = `.SVMinSet`）。它不属于任何一个 `CAFData` 块（没有任何块是 75 项），是第三个对象的参数枚举。它的存在正好解释了为什么「11 个 AE 风格的名字」看起来能和 `UserData` 的 11 项对上——那是巧合，`UserData` 的 11 项语义要另找依据。

## 五、AF 拍摄模式三元组：`0x30006` / `0x30007` / `0x30008`

三个 ID 同属 `UserData`（块 3），由**同一个函数**一次刷新：

```c
// 0x2f3b6c(this) —— 常量 ID 扫描下块 3 下标 6/7/8 的唯一写入者
a = this->vtable[0x204] 派生值;    // 0x2f3a2c
b = <AF_AREA 查表>;                // 0x2f399c
c = 0x2aa0c8(0x815502a8);          // 镜头接口管理器
hub_set(this->hub, 0x30006, a);
hub_set(this->hub, 0x30007, b);
hub_set(this->hub, 0x30008, c);
```

**`0x30006` = AF 拍摄模式类**（值 0..6）。来源是 IQ 槽 `0x1e8`（= `+0x1c0`，`eIQ_ID_APP_MODE`），`sxtb` 之后走 **23 项跳表**（`0x2f3a5c`）：

| APP_MODE | 0x30006 |
|---|---|
| 0 | 2 |
| 14 | 1 |
| 20 | 5 |
| 21 | 4（受 GAF 字节 bit2 门控） |
| 22（`0x16`，视频） | 0 |
| 2–13、15–19（默认） | 3 |
| **1 且 `SMART_PRO_MODE==1`** | **6** |
| 1 且 `SMART_PRO_MODE!=1` | 3 |

`SMART_PRO_MODE` 来自 IQ 槽 `0x254`（= `+0x274`，`eIQ_ID_SMART_PRO_MODE`）。⇒ **6 这个值只有一条路可达**：APP_MODE 为 1 且智能专业模式取 1。

**`0x30007` = AF 区域类**（值 0..2）。来源是 IQ 槽 `0x204`（= `+0xc`，`eIQ_ID_AF_AREA`），`(v-1) <= 3` 后查 4 项表（`0x805e6040+0x1dc` = `{0,1,2,2}`），越界取 1：

| AF_AREA | 1 | 2 | 3 | 4 | 其它 |
|---|---|---|---|---|---|
| 0x30007 | 0 | 1 | 2 | 2 | 1 |

**`0x30008`** = `0x2aa0c8(0x815502a8)`，镜头接口管理器的派生值（与第四轮 `0x31e784` 那一路是同一个单例）。

读写热度：`0x30006` **17 读 1 写**；`0x30007` 1 读 1 写；`0x30008` 5 读 2 写。`0x30006` 是这三个里唯一被大范围消费的，读它的包括 `0x2f0ce4`（相位许可链）、`0x3358a0`（状态跃迁）、`0x336bb8`、`0x3397a4`、`0x33d134`、`0x33fd14`、`0x34fe3c`、`0x363f20`、`0x3686e8` 等。

## 六、对前几轮的更正

| 轮次 | 原文 | 本轮结论 |
|---|---|---|
| 第四轮 | `get(0x30006) == 6` 是「对焦限位状态」判断 | 它是**拍摄模式类**判断：仅当 APP_MODE 为 1 且智能专业模式为 1 时才为 6。语义从「镜头状态」变成「应用模式」，这条门的物理含义变了 |
| 第四轮 | `get(0x1001e)` 是「数据项」门 | `0x1001e` = `LensSpec[30]`，镜头规格块里的第 30 项，3 读 1 写 |
| 第五轮 | `0x30007` 由「3 项表」派生，行标签 `eFOCUS_MODE_*` | 输入是 **AF 区域**，输出才是 3 个值（表 `{0,1,2,2}`）。标签对焦模式是错的 |
| 第五轮 | `IQ+0xc = eFOCUS_MODE` | 本轮再次反证：IQ 槽 `0x204` 明确把 `+0xc` 当 `(v-1)<=3` 的 4 值量用，和 AF 区域一致；第七轮判 `AF_AREA` 是对的 |
| 第六轮 | 「6 个块未定名」 | 六个块全部具名，见第一节 |
| 第七轮 | 184 项表可作字段字典 | 只在纯整数 ID 下成立，**不能套到 `0xNNNNN` 块 ID 上** |

第六轮把 `0x60084` 定性为「GAF 状态位合成 + 启动快照」，本轮不推翻，只补一句：它落在 `Sequence[132]`，而 `Sequence` 有 164 项、139 项被使用，是这套总线里最大的一块，语义上更接近「时序/流程变量」而不是「参数」。

## 七、一个小的实现瑕疵（只记录，不影响结论）

短数组 `/hub+0x34` 是 `malloc(0x2c)` = **11 个 u32**，但构造时只清 `0x28` = 10 个；而 `hub_set` 的短 ID 分支判据是 `cmp r1, #0xa`（允许下标 10）。也就是第 11 格被分配、被允许写、却从未在构造时清零。

实际无害：本镜像里下标 0xa 有 2 个常量写点、**0 个常量读点**（整个短数组臂只有 `0x3`/`0x4`/`0x9`/`0xa` 四个写点，全部只写不读）。但如果有第三方代码在下标 10 上「先读后写」，读到的是堆残留。
