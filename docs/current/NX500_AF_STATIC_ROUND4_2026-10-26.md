**1. `0x60084` 的完整形式**

第二轮给出六个输入，第三轮补了 `0x60084` 的读取层覆盖。本轮把剩下的两条补上，并修正一条描述：

```c
// 概念重写，不是原厂源码。函数 0x2f0ce4。
if (controller->byte[0x110] == 0)                     return 0;  // 控制对象许可
if (lens_mount_flag_0xecc == 0)                       return 0;  // 本轮新增：镜头挂载状态
if (lens_classification_0x31e784() == 0)              return 0;  // 本轮定性
if (get(controller->data, 0x1001e) != 0)              return 0;
if (get(controller->data, 0x30006) == 6)              return 0;  // 本轮解剖
if (GAF->dword[0xc98] > 1)                            return 1;
if (GAF->dword[0xc98] == 1)                           return 1;  // 见第 3 节：0x60083 恒 0
return 0;
```

三处修正：

- **“全局许可字节”其实是镜头挂载状态，不是构建/校准标志。** `0x31e754` 读 `0x816CAE7C`（结构基址 `0x816CA5B0` + `0xecc`）。同一模块里的 `0x31e7a0` 是镜头变更检测：把当前镜头 ID（由 `0x2ffa10` 取出，写栈后 16 位）与缓存值 `+0xece` 比较，**一旦不同，立即把 `+0xecc` 和 `+0xecd` 两个字节清零**（`0x31e7e4`、`0x31e7e8`），查询成功后才把新 ID 写回 `+0xece`（`0x31e834`）。所以这个字节的含义是“本次挂载已经校验过”，换镜头后必然回到 0，直到重新校验。
- **`0x31e784` 的判据已坐实。** 该 stub 是 `movw r0,#0x2a8 ; movt r0,#0x8155 ; bl 0x2ac16c ; adds r0,r0,#1 ; movne r0,#1`，即 `0x2ac16c(0x815502A8) != -1`。第三轮把它称作“镜头分类映射结果不为 -1”是准确的，但当时没有给出这个 stub 的实体；`0x815502A8` 就是镜头接口管理器的单例地址，与 `0x2ff954` 里 `0x815502a8`、`0x2f3b6c` 里 `0x815502a8` 是同一个对象。
- **`0x60083` 不是独立策略输入，在当前固件里是常量。** 见第 3 节。

**2. `0x60084` 是 AF 启动时算一次，不是每次决策重算**

`0x2f2118` 是 AF 启动/初始化路径：

```text
0x2f216c  mov r0, r4
0x2f2170  bl  #0x2f0ce4          ← 调用许可计算
0x2f2174  mov r1, #0x84
0x2f217c  movt r1, #6            ← 数据项 0x60084
0x2f2188  bl  #0x33273c          ← 存入
0x2f218c  cmp r5, #0
0x2f2190  bne #0x2f21e0
```

存入之后的分支在 `r5 == 0` 时清 `this->[0xe4]`、置 `this->[0xe5]`，走无相位路径。

这一点有实操意义：**`0x60084` 是启动快照。** 想改变相位可用性，改动必须发生在这次计算之前（控制对象 `+0x110`、镜头挂载校验、`0x1001e`、`0x30006` 的生产者），或者在 `0x2f0ce4` 内部；事后改 `0x60084` 的存储值虽然能被读到，但会和同一路径上的其他状态字段（`+0xe4`、`+0xe5`）不一致，因为那些字段是在 `0x60084` 判定为 0 时一并写入的。

另外确认：全固件里 `0x60084` 只有一处写入（`0x2f2174`→`0x2f2188`）。其余构造点 `0x2f4228`、`0x2f7fac`、`0x347820`、`0x347d10`、`0x348b08`、`0x367ca0`、`0x332958`、`0x3329a4` 全部是 `bl 0x332948`（读取）。

**3. `GAF+0xc98` 是几何派生的块计数，不是策略参数**

`0x334394` 是全固件唯一写 `GAF+0xc98` 的指令：

```text
0x334300  ldr r5, =0x81550408            ← GAF
0x334370  ldrb r2, [sp, #0x84]           ← 缩放输出结构的两个字节
0x334374  ldrb r3, [sp, #0x85]
0x33437C  smulbb r3, r2, r3              ← 相乘
0x334394  str r3, [r5, #0xc98]           ← 写 0xc98
0x334398  bl #0x33273c                   ← set(0x5000a, (value-1)>>1)
0x3343BC  str r1, [r5, #0xc94]           ← 0xc94 = 3 或 0xc98
```

两个输入字节来自 `0x333f60` 填出的结构。`0x333f60` 读源结构 `+0x00/+0x04/+0x08/+0x0c/+0x10/+0x18/+0x20/+0x21`，做 `mul`/`sdiv` 比例换算后写目标结构 `+0x10/+0x14/+0x18/+0x1c`。也就是说 `sp+0x84`、`sp+0x85` 是**缩放换算的输出量**（目标结构 `+0x20`、`+0x21`），不是任何用户参数。

由此：

- `GAF+0xc98` 是**每帧/每次 AF 区域配置由成像几何算出的块计数**。门控条件 `> 1` 的实际含义是“AF 区域网格超过一格”，不是“相位权重超过阈值”。
- **调整 `0xc98` 不是可用的优化手段。** 它没有独立的写入路径，任何改动都会被下一次区域配置覆盖，且改它不会影响同一函数写入的 `0x5000a` 与 `0xc94`，造成三者不一致。
- `GAF+0xc94` 同样只有一处写入（`0x3343bc`），值为 `3`（`r6 == 2` 时）或 `0xc98`。

**`0x60083` 是常量。** 全镜像里构造 `0x60083` 这个 ID 的位置只有两处：`0x2f0d68`（`0x2f0ce4` 内的读取）和 `0x338498`（另一函数的读取）。两处后面跟的都是 `bl 0x332948`（getter）。**p7 中不存在 `set(0x60083, …)`。** 因此 `0xc98 == 1` 时 `0x60083 == 0` 的条件成立，门控退化为 `0xc98 >= 1`。

需要保留的边界：数据项容器是否在初始化时给 `0x60083` 预置非零值，以及是否有 p7 之外的进程写它，静态范围无法证明。这里只能说 p7 自身没有写入点。

**4. `0x30006` 是 AF 工作模式压缩码，值域 0..6**

唯一写者是 `0x2f3b6c`，一次刷新三个数据项：

```text
0x2f3b78  bl #0x2f3a2c   →  r8  →  set(0x30006, r8)   0x2f3bb4
0x2f3b88  bl #0x2f399c   →  r7  →  set(0x30007, r7)   0x2f3bc8
0x2f3b9c  bl #0x2aa0c8(0x815502a8)  →  r6  →  set(0x30008, r6)   0x2f3bdc
```

`0x2f3a2c` 的派生规则已经完整恢复。它 `bl 0x2c01bc` 取 IQ 单例、读 vtable `+0x1e8`、对返回值 `sxtb`、与 `0x16` 比较后走 23 项跳表（表基址 `0x2f3a5c`）：

| `IQ+0x1c0` | 次级条件 | → `0x30006` | 分支地址 |
|---|---|---|---|
| 0 | — | **2** | 0x2f3b24 |
| 1 | 次级 = 0 | **1** | 0x2f3b0c |
| 1 | 次级 ∈ {2,3} | **4** | 0x2f3ab8 |
| 1 | 次级 = 1 | **6** | 0x2f3b60 |
| 1 | 次级 其他 | **3** | 0x2f3b1c |
| 14 | — | **1** | 0x2f3b0c |
| 20 | — | **5** | 0x2f3b2c |
| **21** | — | **4** | 0x2f3ab8 |
| **22** | — | **0** | 0x2f3b14 |
| 2..13、15..19 | — | **3** | 0x2f3b1c |

次级值来自 `0x2f3a2c` 内对 vtable `+0x254` 的再次调用：`0x2c15c8` 读 `+0x274`，值在 `1..15` 时查 `pool+0xd0` 的 15 项表，越界返回 `-1`。

**注意 idx 21 和 22 这两个尾部项**：它们直接给 4 和 0，不经过次级查询。前一轮表格若只写到 20 就会漏掉这两条。

三个消费者把语义定住了：

| 消费者 | 对 `0x30006` 的处理 | 含义边界 |
|---|---|---|
| `0x2f0ce4` | `== 6` 直接否决相位 | 6 是相位禁用档 |
| `0x3356b4`（经 `0x3358a0`） | 只对 **0 / 2 / 4** 特判，输出 `0x40009 ∈ {0,1,2,3}` | 0/2/4 是 AF 策略分档；1/3/5/6 走同一路径 |
| `0x33fd14` | `== 5` 时取 `GAF+0xc94` 作第 5 参数调 `0x352c8c`，并更新 `0x60050` | 5 与分块统计绑定 |
| `0x2f3bf0` | `== 4` 单独分支 | 4 有专属处理 |

`0x30007` 只有一个额外读者（`0x3358a0` 传给 `0x3356b4`）；`0x30008` 的额外读者在 `0x9bbd8`、`0x9bd70`，判据是 `== 1 || == 3`。

**没有做的事**：`IQ+0x1c0` 的 23 值枚举没有映射到用户菜单项。上表的 0..22 是索引，不是名字。第三轮报告里“AF-S/AF-C 菜单值映射”仍然未完成，本轮只是把它的上游从“未知字段”变成了“已知字段位置 + 已知压缩规则”。

**5. 宿主已具名：`CIQ_SysDataIF_NX1`**

`0x2c01bc` 是懒加载单例 getter（全局 `0x81561cf0` 为 once 结构，实例在 `0x81561cf4`，构造 `0x2c0128`，vptr literal 在 `0x2c01b8` = `0x805DE008`）。该 vtable 的 RTTI 名字是 **`17CIQ_SysDataIF_NX1`**。

| 槽 | 目标 | 行为 |
|---|---|---|
| `0x1e8` | `0x2c1048` | `return *(this + 0x1c0)` —— `0x30006` 的源头 |
| `0x1d8` | `0x2c0ffc` | 同样读 `+0x1c0` 并 `cmp #0x16` 后跳表，与本轮的 23 项分派同构 |

`+0x1c0` 有两个独立消费者（vtable 槽 `0x1e8` 与 `0x1d8`），都按 `0..0x16` 的枚举处理，这是它是枚举字段而不是普通计数的最硬证据。

**6. 附带确认：`0x2ff954` 是 `GetSpecificLensTypeAFActuator`**

该函数的错误路径直接引用字符串 literal `LENS IF ERR : GetSpecificLensTypeAFActuator`（`0x2ff9f4` → pool `0x2ffa0c` → `0x80746F90`）。这给第三轮的 `0x10004 = LensActuatorType` 提供了函数名级证据，而不只是数据流推断。

成功条件也被恢复：`0x234834(...)` 返回 `0x2002` 时走 `0x2fe260` 填充调用者的输出缓冲区并 `return 1`；其他返回值写 `0x40017` 错误码（`0xb6`、`0x1ba`、`0x2b4` 三种）并 `return 0`。`0x10004` 只在这条成功路径上被写入。

**对 EF 转接方案的意义**（附注，未验证）：如果转接环不实现这个查询，`0x10004` 拿不到 `0x2002` 成功返回，`+0x10c`（`m_bPhaseAfOnlyPossibleLens`）就是 0。但它只是许可链的一环，`0x60084` 另有五项条件，因此不能据此断言“转接镜头一定用不上相位”。
