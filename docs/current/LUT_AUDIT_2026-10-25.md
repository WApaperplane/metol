## 二、方法

### 结构口径（纯格点，不需照片）

九项指标，阈值全部对 `identity17` 校准 —— **identity 必须九项归零**，
否则说明判据本身错了。首版就翻过车：暗部统计误用了格点序号而不是数值，
把 identity 判成 16.6% 压死。

| 指标 | 含义 | 阈值 |
|---|---|---|
| mono | 灰轴 / R 轴 luma 下降沿数 | >0 即硬伤 |
| black_luma | 输出 (0,0,0) 的 luma | >30 灰雾 |
| crush% | 输入三通道全 >0（且亮度≥20%）但输出某通道 =0 的比例 | >3% |
| white% | 输入三通道全 <255 但输出某通道 =255 的比例 | >3% |
| jump | 相邻格点输出最大分量差 ÷ 16 | >5.5 |
| gray | 17 个灰点输出的 max-min | >30（暖调表豁免） |
| dr | 灰轴 0→255 的 luma 落差 | <205 |
| hue | 六主色格最大色相偏移 | >45° |
| warm_r | 暖区格点 R/G 比值变化（参考值，不判定） | — |

### 观感口径（真实照片，16 张）

**判"偏红"必须看色相位移 dHue，不能看 R/G。** 这是本次最重要的方法修正：

| 表 | dRG | dHue | 真实性质 |
|---|---|---|---|
| `fuji_velvia50` | +0.27 | **-1.8°** | 只是更饱和，色相没动 |
| `kodak_kchrome25` | +0.34 | **-7.6°** | 真把肤色推红了 |

两者 dRG 同量级。任何 `sat > 1.0` 的表都会在暖色像素上抬高 R/G，那是"更饱和"。
判据：hue∈[0,60]∪[330,360]、s_in∈[0.25,0.85]、亮度>30，且**输出饱和度至少保留
输入的 55%**（否则去饱和表的 hue 抖动会被误记成偏红），取 16 张照片的中位数。

## 五、根因：warm_guard 削不动肤色

`gen_luts.py` 第 8 步的暖色保护：

```python
if s > 0.30 and v > 0.14 and (h <= 50 or h >= 330):
    w = ((s - 0.30) / 0.70) ** 0.7
    r -= (r - g) * wg * w
```

在典型肤色 `(200,150,130)` 上算：s=0.35、h=17°。

- `w = ((0.35-0.30)/0.70)^0.7 = 0.146`
- `wg = 0.30` ⇒ 实际只削 `0.196 × 0.30 × 0.146 = 0.0086` ≈ **2.2 级**
- 要把 -7.6° 修到 -3°，需要削 **21 级**

**差一个数量级。** 门槛从 s=0.30 起算，而肤色正好卡在这个门槛上 ——
真实照片里占面积最大的暖色区，恰恰是保护最弱的地方。

参数扫描（真实照片实测）：

| 设置 | kchrome64 的 dHue | 饱和增益 dSat |
|---|---|---|
| 现状 wg=0.30 | -3.17° | +0.176 |
| wg=0.45 | -0.85° | +0.157 |
| wg=0.60 | +1.79° | +0.136 |
| wg=0.90 | +11.15° | +0.061 |

wg=0.45 对 kchrome64 / xpro / rsx200 有效（拉到 ±1.6°），但对 kchrome25、velvia50
几乎无效 —— 因为这两张表的暖色区 `r-g` 超量大，被削幅上限挡住，且饱和结构不同。

**提高 wg 会带来副作用**：旧版 `h<=50 or h>=330` 是硬判，边界处 R 一步跳变。
wg=0.45 时全部表的相邻格点跳变从 4.5 涨到 6.7，部分表变非单调。
必须先改成平滑窗口才能提强度（已在 `gen_luts.py` 里备好参数开关，默认关闭）。

## 九、第二轮：暖色保护重做 + 全量重建

第一轮定位到根因（§五）后，本轮把 `gen_luts.py` 第 8 步的暖色保护重写并全量重建，
**94 张里 57 张受管表全部重新生成**（37 张冻结字节表未动）。

### 9.1 改了什么

| 参数 | 旧 | 新 | 作用 |
|---|---|---|---|
| `warm_huew` | 0（硬判 `h≤50 \|\| h≥330`） | **60**（余弦淡出） | 边界不再一步跳变 —— 这是 wg 能提上去的前置条件 |
| `warm_vsoft` | False | **True** | 权重 ×min(1,v/0.14)，消除「(32,0,0) 不削、(48,0,0) 削」的红轴亮度倒挂 |
| `warm_cut` | 1.0（不封顶） | **0.15** | 封顶改按**该点 R 的比例**，不按绝对量；绝对量在低亮度处会压平红轴 → 非单调 |
| `WARM_GUARD` | 0.30 | **0.45** | 全局强度 |

5 张重灾表单独拉满 —— `warm_guard 0.90 / smin 0.15 / pow 0.45 / huew 70 / cut 0.35`：
`kodak_kchrome25`、`kodak_kchrome64`、`fuji_classicchrome`、`agfa_rsx200`、`ricoh_xpro`。

### 9.2 结果：dHue 全部进 ±3°

16 张真实照片、暖色区中位（负 = 偏红；>±3° 可辨，>±5° 明显）：

| 表 | dHue 前 → 后 | dSat 前 → 后 | 暖区亮度 dY 前 → 后 |
|---|---|---|---|
| `kodak_kchrome25` | **-7.57° → -2.33°** | +0.141 → +0.120 | -0.295 → -0.332 |
| `kodak_kchrome64` | **-4.70° → +0.66°** | +0.092 → +0.049 | -0.190 → -0.213 |
| `ricoh_xpro` | **-6.33° → +0.79°** | +0.062 → +0.021 | -0.162 → -0.217 |
| `fuji_classicchrome` | **-3.80° → +1.69°** | -0.172 → -0.190 | +0.085 → +0.059 |
| `agfa_rsx200` | **-3.46° → +2.19°** | -0.072 → -0.112 | -0.044 → -0.077 |

**代价**：暖区饱和度少收 2-4 个百分点，亮度再暗 2-6 个百分点（表右列）。
这是「削 R 换色相」的固有成本 —— 对正片/克罗姆这类本来就厚的片子，方向是对的。

### 9.3 试过但否掉的方案：`warm_lift`（还 G 保亮度）

数学上更优：削掉的 R 按 `.299/.587 ≈ 0.51` 还给 G，ΔY ≈ 0，亮度完全守恒。
**但色相是 r、g 的比值函数，还 G 的杠杆效应太大**：`kodak_kchrome25` 从 -2.33° 直接冲到
**+12.64°**（约 29°/单位 lift），红翻成黄绿；要压回中性得把 wg 降到 1/3，饱和白丢。
参数保留（默认 0），代码里带削幅上限 `cut ≤ (r-g)/(1+lift)` 防越过中性，
将来给「绝对不能变暗」的表单独开。

### 9.4 纠错：`samsung_a00/a01/a02` 不是垃圾表

上一轮体检把它们按 look 口径判成「非单调 + 动态范围 180-200」，
本轮核对 `LUT_UI_2026-10-18` §8.5：它们与机身原厂槽 A00/A01/A02
**md5 完全一致**（`134909c7` / `69a4ac46` / `3ac93837`），用途是「对照原厂风格」。
低反差、灰轴微非单调都是原厂冷调设计。`audit.py` 新增 **REF 档位**：
只核 black/crush/jump，不判 mono/dr/gray/white/hue。

同理 `warm_sepia` 的 `hue_err 168°` 是棕调表的必然结果，已随 `warm_*` 一起豁免。
