## 一句话结论

前六轮一直找不到 `IQ+0x1c0`、`IQ+0x2e4` 的写入者，**不是搜索不够深，而是搜索方法对这个对象根本不成立**：这 184 个字段只有一条通用写入口——虚函数 `SetParameter(id, value)`，存储地址由 id 算出来。所有针对 `str rX, [rY, #0x1c0]` 的逐偏移扫描，永远命中不了。

同时，**类身份被 RTTI 直接读出来了**：我一直叫「IQ」的那个类，真名是 `CIQ_SysDataIF_NX1`；它的对象体就是 `vptr + u32 slot[184] + 元数据块`，而 `0x5758e0` 那张 184 条的 `eIQ_ID_*` 名表**就是这张数组的枚举名**——第六轮判它「全镜像无引用、只能当标签」是错的，绑定不靠引用，靠下标顺序。

## 一、类的真实身份

| vtable | typeinfo | 类名 | 槽数 | 代码范围 |
|---|---|---|---|---|
| `0x805de008` | `0x805de2c4` | **`CIQ_SysDataIF_NX1`** | 166 | `0x2bff08–0x2c17fc` |
| `0x805dea00` | `0x805dea48` | **`CIQ_ParamInfo_NX1`** | 13 | 部分落在 `0x2c4xxx` / `0x3b1xxx` |
| — | `0x805de9ec` | `CIQ_Thread_IPC` | — | typeinfo 里记录了基类指针 → `0x805dea48`，但这条链 5 个字长、解码不干净，继承关系仍待定 |

命名方式：Itanium ABI，`vptr[-4]` 是 typeinfo，typeinfo`+4` 是长度前缀的名字串（`"17CIQ_SysDataIF_NX1"` = 17 字符 + 名字）。

`CIQ_SysDataIF_NX1` 这个名字第四轮已经从同一处 RTTI 读出过，第六轮却退回用「IQ」称呼把它埋了；本轮把它当正式名字用，并补上第二个类的名字 `CIQ_ParamInfo_NX1`。

**这个类就是第六轮里的「hub 提供者」**：`0x332948(hub, id)` 那条「块号<<16 | 下标」的路子是它的另一套取值接口，和本文这条 184 槽数组是同一件事的两个入口。

单例：`0x81561cf4`，惰性构造，访问器 `0x2c01bc`（双检锁，守卫字 `0x81561cf0`）。构造函数还会把 `&slot[0]`（即 `this+4`）写进全局 `0x815502ac`，作为数组快速指针。

## 二、对象布局

```
+0x000            vptr  = 0x805de008
+0x004 .. +0x2e3   u32 slot[184]        ← 184 * 4 = 0x2e0
+0x2e4 .. +0x318   metadata[14]         ← 构造函数逐字段写的默认值
```

三条独立证据把这个边界钉死：

1. 构造函数 `0x2c0128` 在 `0x2c0198` 调 `0x50a114(dst = this+4, 0, 0x2e0)`，**长度恰好 0x2e0 = 184×4**，从 `+4` 起，到 `+0x2e3` 止。
2. 取值函数的越界判据是 `cmp r1, #0xb7`，即 **183 = 184−1**。
3. `4 + 184*4 = 0x2e4`，正好是第一个元数据字段。

构造函数默认值（`0x2c0128` 内直接读出，非推断）：

| 字段 | 默认 | 字段 | 默认 | 字段 | 默认 |
|---|---|---|---|---|---|
| `+0x2e4` | 0 | `+0x2e8` | 0 | `+0x2ec` | **1** |
| `+0x2f0` | 0 | `+0x2f4` | **0x40** | `+0x2f8` | **0x70** |
| `+0x2fc` | 0 | `+0x300` | **0x50** | `+0x304` | **0xa0** |
| `+0x308` | 0 | `+0x30c` | 0 | `+0x310` | 0 |
| `+0x314` | 0 | `+0x318` | **0x6e** | `+0xf4`（数组内 id 60） | **−1** |

## 三、三个虚函数——本轮的核心

| 槽 | 地址 | 语义 |
|---|---|---|
| `0x000` | `0x2bff08` | `str <vptr>, [r0]; bx lr` — vptr 安装器 |
| `0x00c` | `0x2bff1c` | `GetParameter(id)`：`id > 0xb7 ? −1 : this[id+1]` |
| `0x010` | `0x2bff30` | `GetParameter(id, out*)`：同上，写入 `*out`，返回 1 / −1 |
| `0x014` | `0x2bff4c` | `SetParameter(id, value)`：`this[id+1] = value`，然后跑副作用 |

`SetParameter` 的三条分支（`0x2bff70` 起）：

- `id ∈ {0, 2}`（`AF_MODE` / `AF_AREA`）→ 调 `0x2ac660(global, 1)`
- `id == 5`（`AF_LOCK_STATUS`）→ 最重的一条：两行日志（`SET AF LOCK STATUS (%d)` / group 变体）、对 AF 状态字节 `0x81550408` 做 bit5 更新、相位为 3 时再调 `0x2c311c` / `0x2c3198`
- `value == 3` 且 AF 状态 bit5 为 0 且相位 3 → 走 `0x34ca08` 打日志

> `SetParameter` 这个名字不是我起的：`0x805de2a0` 处就有字符串 `"SetParameter"`，紧邻 `"17CIQ_SysDataIF_NX1"`。

### 为什么第五、六轮注定失败

第六轮把类范围定成 `0x2c0000–0x2c2000` 去扫 `str`。而 **`GetParameter` / `GetOut` / `SetParameter` / vptr 安装器全部落在 `0x2bff08–0x2bff4c`**，即扫描窗口下沿之外。更关键的是：即使窗口开对了，逐偏移扫也不会命中——写入口只有一个，地址是 `r0 + id*4 + 4`。

**这一条直接作废「`+0x1c0` 没有生产者」的结论：它有生产者，只是走通用入口。**

### 命名正确的五个旁证

**0. 五个连续槽 ↔ 连续五个字段（最硬的一条）**

| 槽 | 实现 | 读的字段 | 该字段 = |
|---|---|---|---|
| `0x1fc` | `0x2c1084` | `+0x04` | `AF_MODE`（id 0） |
| `0x200` | `0x2c10a4` | `+0x08` | `AF_MOVIE_MODE`（1） |
| `0x204` | `0x2c10c8` | `+0x0c` | `AF_AREA`（2） |
| `0x208` | `0x2c10ec` | `+0x10` | `AF_MF_ASSIST_MODE`（3） |
| `0x20c` | `0x2c10f4` | `+0x14` | `AF_ASSIST_LAMP`（4） |

槽步长 4、字段步长 4，五个槽严格按顺序读五个相邻字段。只要有任何一个 id 错位，这五连就不会齐。

1. **白平衡有专用访问器对**：槽 `0x1b4/0x1b8/0x1bc` 是 `CWB_R/B/G` 的 getter，槽 `0x1c0/0x1c4/0x1c8` 是对应的 setter，两组槽位相隔 0xc、字段顺序一致。这种「专槽专字段」只有在名字对得上时才会成立。
2. **槽 `0x020`** 用 `+0x94`，而 `+0x94` = id 36 = `METERING_MODE`。
3. **槽 `0x028`** 是 `+0x2e4 ? +0x2f4 : +0x108`，而 `+0x108` = id 65 = `AV_SETTING`——手动覆盖块的例子恰好落在「AV」上，构造函数给的默认 `0x40` 也因此读作「默认 AV 值」。
4. **`0x383380`** 把常量 `0x6f`（111）放进 `r1`，走槽 `0x010` 取出来，再和 1 比较——独立于类的实现，用同一个 id 读同一个语义。

## 五、第六轮结论的更正

| 第六轮结论 | 第七轮更正 |
|---|---|
| `+0x1c0` 是「未知的模式索引，值域 1..0x1a，28 项分派」 | **`eIQ_ID_APP_MODE`（id 111）**。`0x2c0220` 就是「按 APP_MODE 分派」；它还把 `AUTOSHUTTER_SUBMODE`(172) 读进 `r1`、`3D_MODE`(122) 读进 `r2` 供分支使用 |
| `+0x1ec` 是「唯一能整体翻转分派输出的二值开关」 | **`eIQ_ID_3D_MODE`（id 122）**，`+0x1f0` 是 `eIQ_ID_3D_AUTO_MODE`（123）。四处 `== 1` 全是**3D 模式门** |
| `0x5758e0` 的 184 条名表「全镜像 0 引用，只能当标签，不能绑字段」 | **能绑，而且绑得很硬**：数组 184 项、越界判据 0xb7、名表 184 条且顺序与字符串一致 ⇒ `id i` ↔ `偏移 4+4i`。名表不需要 xref，它不是分派表，是枚举名列表 |
| `+0x2e4` 族「覆盖字段共 10 个」 | 仍然成立，但语义更清楚：`+0x2e4` 是布尔开关，置位后 10 个 getter 从「实时槽值」切到「影子值」（例：`+0x2f4` 顶替 `AV_SETTING`）。写入者仍只有构造函数与槽 `0x0c4`，所以**覆盖块在本版是休眠的**——这一条不用改 |

## 五之二、与第五轮的一处冲突（待复核，不擅自覆盖）

第五轮把 `IQ+0xc` 定成 `eFOCUS_MODE`，依据是 `eFOCUS_MODE_*` 有 4 个相邻字符串、值域 4 档、且 `0x2c10c8` 用 `(v−1) ≤ 3` 查一张 4 项表。第五轮自己也写明「数值与名字的绑定是按定义顺序 1 基的假设」。

本轮的字段图给出另一个读法：**`+0xc` = id 2 = `eIQ_ID_AF_AREA`**，而 `0x2c10c8` 那张 4 项表正是**按 AF 区域**索引的。同簇的 5 个槽（`0x1fc–0x20c`）依次读 `AF_MODE / AF_MOVIE_MODE / AF_AREA / AF_MF_ASSIST_MODE / AF_ASSIST_LAMP`，顺序完全自洽。

也就是说：

- 「4 项表」这个观测没错，但它索引的字段是 AF 区域，不是对焦模式
- 对焦模式（单次/连续/手动/自动）更可能住在 **`+0x04` = `eIQ_ID_AF_MODE`**，那一槽的 `0x2c1084` 用的是 3 项表

`0x30007` 那个「三档派生」的**取值结论**不受影响（0/1/2 是硬读出来的），但它的**行标签**（`eFOCUS_MODE_*`）需要重新对一遍。这一条留作待复核，不直接改写第五轮。

## 六、NX500 上的语义推论

`eIQ_ID_3D_MODE` 构造函数清零后**没有任何写入点**——不是编译器删了，是这台机器没有 3D 镜头。所以：

- `0x2c0edc`（`3D_AUTO_MODE == 0 && 3D_MODE == 1`）永远走 else 分支
- `0x2c1008`（`APP_MODE == 0x16 && 3D_MODE == 1`）永远返回 0
- 28 项分派里那 5 个被 `+0x1ec` 翻转的条目永远返回非 3D 值

但**代码是活的**：全镜像有 17 处构造常量 `0x7a` 去查询 `3D_MODE`。这是 NX1 共享代码在 NX500 上的自然结果，不是死代码残留。同理 `APP_MODE` 有 22 处常量 `0x6f` 构造点。

## 七、诱饵：`0x3b1858` 的 `str r1, [r4, #0x1c0]`

这是全镜像里唯一一处「看起来像 `+0x1c0` 生产者」的指令，而且同一个函数还写 `+0x304 / +0x30c / +0x318`，几乎是照着第六轮字段表来的。**它不是。**

- `r4` 是**第二个参数**（`0x3b12f4` 的 `mov r4, r1`），不是 `this`
- 该函数是 `CIQ_ParamInfo_NX1`（vtable `0x805dea00`）的槽 `0x2c`，和 `CIQ_SysDataIF_NX1` 的槽 `0x2c`（`0x2c0468`）是两个不同函数
- `+0x1bc..+0x1c8` 是它自己 `+0xd0..+0xdc` 的**取反镜像**：`0x100−a, −b, −c, 0x100−d`
- 它的 `+0x1ec = 0xb` 是立即数（`0x3b19dc` 的 `mov r3, #0xb`），不是 `3D_MODE`

⇒ 以后见到「偏移对得上」的写入点，先确认基址寄存器来自 `this` 还是参数。
