**NX500 对焦静态逆向第三轮：执行器门控、回退计数生命周期与视频相位分支 · 2026-10-26**

本轮把上一轮三个未知项向前推进：**相位序列的镜头许可来自执行器类型；相位回退计数会在 AF 启动/重启相关公共路径清零；视频有独立的相位方向检查和直接驱动分支。** 这些结果使优化候选从“强制相位优先”收敛到具体的许可条件、复位边界和分模式切换策略。

仍为纯本地静态分析，没有访问机身、执行相机命令、生成补丁或刷写。沿用官方 v1.12 p7，SHA-256：`f8e417cb5b55768851ba7e2b8017d3a98dc0b0c8444cc0a5061265cc08dbbf7f`。短地址均是 p7 chunk 内文件偏移；`GAF` 仍表示代码引用的运行时全局对象 `0x81550408`。字段名为分析标签或固件日志名，不是公开 ABI。

**1. “相位序列可用镜头”标志：实际读取 LensActuatorType**

已打通的数据链：

```text
镜头属性读取包装 0x2ff954
    ↓ 输出缓冲区首字节
CAFDataLensSpec::更新路径 0x3b5de0
    ↓ 0x3b5f24–0x3b5f34：写数据项 0x10004
CAFSequenceNxRoughFineScan::Initialize 0x34a13c
    ↓ 0x34a3bc–0x34a3d0：读取 0x10004，非零转成 1
对象 +0x10c（0x34a3dc 写入）
    ↓
相位初始决策、反差扫描中切回相位的条件
```

`0x10004` 的含义不是仅凭消费者猜测：同一个 `CAFDataLensSpec` 更新函数在 `0x3b63c4–0x3b63e8` 读取此项并输出 `LensActuatorType:%d`。该类的当前 vptr `0x8063b958`、RTTI `15CAFDataLensSpec`、更新虚函数槽 `+8 → 0x3b5de0` 均已解析。

这将上一轮“镜头许可标志”的描述细化为：

```c
// 概念重写，不是原厂源码。
rough_fine_object.phase_only_possible = (LensActuatorType != 0);
```

固件日志把消费者称作 `m_bPhaseAfOnlyPossibleLens`，但它在这个初始化位置并没有逐个比较镜头型号。当前证据指向镜头属性驱动的门控。仍未建立执行器类型 `0/1/…` 对应的物理结构及各镜头值，不能把改成恒真视为已验证的优化。

该布尔值还不是全部许可条件。例如 `0x3480f0` 的初始决策还会检查当前阶段和其他标志；部分条件可以走替代分支。因此 `LensActuatorType == 0` 也不能被扩展解释为机身完全不使用该镜头的相位信息。

**2. 0x60084：分层许可结果，读取时还可被覆盖**

上一轮已经确认 `0x60084` 控制部分相位入口。本轮追到其普通生产者：

```text
0x2f0ce4 计算许可
  → 0x2f2170 调用
  → 0x2f2174–0x2f2188 写入数据项 0x60084
```

普通路径返回允许，需要同时满足下列检查：

| 输入 | 当前机器码中的条件 | 语义边界 |
|---|---|---|
| AF 控制对象 `+0x110` 字节 | 非零 | 控制对象中的许可字段，尚未追完所有写入者 |
| `0x31e754` 返回的全局许可字节 | 非零 | 尚不把它命名为校准成功或硬件支持位 |
| `0x31e784` | 镜头分类映射结果不为 `-1` | 内部镜头分类的全部枚举仍未映射 |
| 镜头数据项 `0x1001e` | 为零 | 具体属性语义未确定 |
| 数据项 `0x30006` | 不等于 `6` | 不能仅凭数字命名为某种 AF 或曝光模式 |
| `GAF+0xc98` | 大于 `1`；或等于 `1` 且 `0x60083 == 0` | 该策略字段的完整生产链尚未定位 |

而读函数 `0x332948` 对 `0x60084` 有特殊覆盖，优先级如下：

```c
// 只重写 0x60084 的读取分支，其他 ID 不适用。
if (GAF.byte0 & 0x01) return 0;
if (GAF.byte0 & 0x02) return 1;
return ordinary_parameter_lookup(0x60084);
```

`0x332950–0x332964` 检查 bit0 并返回零；`0x332994–0x3329b8` 检查 bit1 并返回一。因此两个标志同时为一时，这个读取分支返回零。bit0 还在诊断路径中与 `NX-MINI` / `PAF SUPPORTED` 模式日志相关；没有证据把它们等同于普通用户菜单。

这证明 `0x60084` 不是单一的“相位权重”数值。修改普通数据项也可能被读取层覆盖；直接强制返回一，则会绕过上游多个许可检查。

**3. 两个重试计数的生命周期已经分开**

| 字段 | 已确认的用途 | 已确认的复位 |
|---|---|---|
| `GAF+0x1f30` | 多条相位转反差分支递增；初始相位入口及扫描中切回检查以 `<2` 作为条件 | `0x2adac8` 公共复位函数在 `0x2adb54` 清零 |
| 粗细扫描对象 `+0x8c` | `0x3406dc` 递增；某个 WAIT PEAK 分支计数达到 `3` 后改用反差 | 构造函数清零；`Initialize` 在 `0x34a2a0` 清零 |

`GAF+0x1f30` 清零有一个重要细节：公共复位函数的参数 `r1` 控制一组较完整的清理，但无论 `r1` 是否为零，都会进入 `0x2adb14` 以后的公共部分，执行 `0x2adb54`。所以不能只看“全复位”条件判断它是否清零。

当前官方机器码中，已找到以下对公共复位函数的直接分支引用：

- `0x2addb0`：允许进行 AF restart 的路径，传入 `r1=0`，仍清零此计数。
- `0x2adec8`：`0x2ade84` 公共启动路径；已知 `onStartSlowAF`、`onStartS0AF` 都会调用该启动函数。
- `0x2ae2ec`：另一条保留部分标志和计数后再恢复的复位包装；本轮未命名其完整用途。
- `0x2ae350`：`onStartS1` 内的复位调用。
- `0x2ae564`：初始化清理函数的尾调用；此前还清零整个 GAF。

因此，“两次回退后永远不用相位”可以排除。较准确的描述是：**它限制的是公共复位之间的部分相位重入机会。** 静态分析尚未建立每次实际拍摄会经过多少次公共复位，也未把计数单位证明为帧数。

对象 `+0x8c` 的三次等待与全局 `+0x1f30` 的两次门限属于不同计数。当前证据也不能把“状态回到 0”直接等同于再次调用 `Initialize` 或公共复位函数；调试时需要区分这三件事。

**4. 原先未知的几个“模式 ID”实际是执行标志**

在 `0x2f35a4` 中，代码读取数据项、保存返回寄存器，再把它们按固定顺序传给日志：

```text
CAF::Seq[%s] isS0AF[%d] isRestart[%d] isMovie[%d] isStart[%d] wobb_possi[%d]
```

当前机器码的寄存器和栈参数对应关系确认如下：

| 数据项 | 日志语义 | 返回值保存与日志参数 |
|---|---|---|
| `0x40001` | `isS0AF` | `r8`，第一项布尔参数 |
| `0x40003` | `isRestart` | `sl`，第二项布尔参数 |
| `0x40005` | `isMovie` | `r6`，第三项布尔参数 |
| `0x40002` | `isStart` | `sb`，第四项布尔参数 |
| `0x1000f` | `wobb_possi` | 单独的镜头属性；最后一项布尔参数 |

这些不是 AF-S/AF-C 枚举。这样，`proIDSPafInitial` 中的一组条件可以进一步解释为：`isStart == 1`、`isMovie == 0`、`isS0AF != 1`、`isRestart != 1`。该条件参与在普通相位初始化不适用时，是否利用已有相位方向/位置调用 `proIDSPafInitialMainJudgeOnly`。它不是整台相机唯一的相位许可条件。

**5. 视频使用独立序列，也有相位方向检查和直接驱动**

从构造函数写入的 vptr 和 RTTI 得到：

| 序列 | RTTI | Initialize | ExecuteMain |
|---|---|---|---|
| 普通粗细扫描 | `26CAFSequenceNxRoughFineScan` | `0x34a13c` | `0x349930` |
| 视频粗细扫描 | `31CAFSequenceNxRoughFineScanMovie` | `0x368b58` | `0x3686e8` |

二者分别调用共同基类构造函数，具有各自的对象布局与处理函数。本轮没有把它们当作同一个状态机。

视频中的一条当前控制流已追到：

```text
Movie ExecuteMain 0x3686e8，状态 0x10c
  → 0x367c74
  → 读取 0x60084
  → 非零时调用 0x366e90，执行附加条件检查
       ├─ 尾调用 0x366d08：processPafDirCheck_Start，状态 0x121
       └─ 尾调用 0x366dc4：processPafDrive_Start，状态 0x120
                              → 0x366e30 调用驱动包装 0x33baec
```

这比字符串存在更强：有视频虚函数分派、许可读取、条件分支和实际驱动调用。它确认视频路径具备相位直接驱动，尚不能证明所有视频分辨率、帧率、裁切模式都会选择这条序列，也不能把普通粗细扫描的 `<2` 门限直接套在视频上。

本轮还复核到历史反编译的尾调用展开：`0x366e90` 的伪代码包含 `0x366d08`、`0x366dc4` 的效果，历史 size hint 又覆盖到后继函数。因此重新用明确跨度 `0xc0` 导出 `0x366e90`，并单独导出两个尾调用目标。输出跨度仅供检查，不是可写补丁范围。

**优化判断的更新**

现阶段更具体的静态候选是：

1. 保留执行器分类门控，继续追 `LensActuatorType` 的枚举及属性来源，再判断哪些镜头分支可调整。
2. 把全局回退计数与对象等待计数分开，先追复位频率和各失败出口，再评估调整门限是否会造成反复重入。
3. 分别分析普通与视频序列；视频已有方向检查与直接驱动出口，后续重点应是两者之间的选择及退出条件。

目前没有实机耗时、失焦率或镜头动作数据，因此本轮没有把任何候选标成已验证有效的补丁。AF-S/AF-C 菜单值的完整映射、视频规格到序列选择的映射、`GAF+0xc98` 的生产链仍待继续。
