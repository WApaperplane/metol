## 一句话结论

**「主体保持」不需要新造——固件里已经实现了一套完整的 face-box hold（冻结整个 0x444 人脸载荷，AF 区域自动切到冻结副本），由 `C3AStateLock*` 状态机在 11 个点启停；「眼部 AF」则是纯缺口——双眼结果有、实时调用链有，但 AF 侧一处都不读，必须新增两段代码。**

两条结论方向相反，但都收窄了改动面：前者是**策略问题**（什么时候该保持、保持多久），后者是**接线问题**（谁去跑眼部、谁去用眼框）。

## 一、数据结构先对齐：一份 0x444 的载荷，两个消费者

第二轮给出的脸信息布局（`0x444` 字节，最多 10 条，记录步长 `0x14`）这一轮补上了它的两个持有者：

| 持有者 | 地址 | 说明 |
|---|---|---|
| CFDTask 内载荷 | `this+0x54`（第二份 `this+0x4d4`） | 检测任务写、眼部算法读；`0x142f08/0x142f0c` 调 `0x50a114(this+0x54, 0, 0x444)` 清空 |
| 静态 face-info 单例 | `0x81459b94`，载荷在 `+0x468` | `0x140b88` 返回；`0x141a80` 的两条路径分别读它和 CFDTask 载荷 |

AF 侧只通过两个虚函数取数据（`CIQ_SysDataIF_NX1` 的 vtable `0x805de008`）：

| 槽 | thunk | 实现 | 作用 |
|---|---|---|---|
| `0x240` | `0x2c13b8` | `0x141a80` | 取主脸区域（6 个字：x,y,w,h,src_w,src_h） |
| `0x244` | `0x2c150c` | `0x14201c` | 取有效脸数 |

这两个函数的返回值就是 AF 侧对「主体」的全部认知——它们读什么，AF 就只认什么。

## 二、主体保持：固件里已经有的 hold，以及它到底保持什么

### 2.1 机制本体

`0x141a80` 的第一条分支就是开关：

```c
// 0x141a80(faceInfo, out6, outAngle, outCount)
if (faceInfo->hold == 0) {           // ldrb r1,[r4,#0x20]
    payload = getFaceManager()->vtable[0x28]();   // 0x147064 → 活载荷
    rect = payload + 0x14*i;  angle = payload + 0x258 + 4*i;
} else {
    rect = faceInfo + 0x24 + 0x14*i;  angle = faceInfo + 0x27c + 4*i;
    count = faceInfo->holdCount;  main = faceInfo->holdMain;
}
```

`hold` 打开后，取数完全走单例里的副本；`0x14201c` 同样切换（`+0x3c0` 而不是载荷 `+0x39c`）。也就是说 **hold 一旦生效，AF 的区域来源就和检测结果脱钩了**。

副本从哪来：

```c
// UpdateHoldFaceBox  0x141f20
if (0x141ecc(this) == 0) { holdCount = 0; holdMain = 0; return 0; }
payload = getFaceManager()->vtable[0x28]();
memcpy(this + 0x24, payload, 0x444);      // 0x141fe4..0x141ff0
```

**注意副本是整份 0x444**——脸框、角度、双眼数组、主脸索引、脸数全在里面。这不是"只冻一个框"，是"冻一帧检测结果"。

### 2.2 谁在启停它

`SetHoldFaceBox` 的真正入口是 `0x140de8`（不是 `0x140df0`——后者是函数体中段那条 trace 调用，只按反汇编标号看很容易当成入口；全镜像没有任何数据指针指向 `0x140df0`）。它共有 **11 个调用点**，全部属于 3A 状态机：

| 方向 | 调用点 | 所在函数（日志串实证） |
|---|---|---|
| 开 | `0xaa178` | `virtual int C3AStateLock::enter()`，同函数日志 `Draw Face dection box` |
| 开 | `0xaac38` | `C3AStateLockCAF::RestartAF(StartAF)` 的锁态分支（`state_byte ∈ {2,3}`） |
| 开 | `0xaaca0` | 同一函数，属性 `8 == 0x80003` 分支，随后立刻 `UpdateHoldFaceBox` |
| 开 | `0xadf5c` | `void C3AStateScanAF::startScanAF()`，要求属性 `9 == 0x90001` 且 `8 == 0x80003` |
| 关 | `0xaab8c` | `C3AStateLockCAF::RestartAF` 的非锁态分支（`state_byte ∉ {2,3}`） |
| 关 | `0xab448` | `C3AStateLockCAF::onAFCompleteDriving` |
| 关 | `0xbb45c` | `CCmdCancelS1::handlerBody`（3A unlock done 回调） |
| 关 | `0xbf2b0` | `CCmdAutoShutter::stopAutoShutterMode` |
| 关 | `0xc11ac` | `CResAECompletion::onAECancelLocking` |
| 变量 | `0xa58a0` | `C3AController::Handle(CPacketNX1*)` |
| 变量 | `0xc5f90` | `CPostStartLiveview::execute` |

所以 NX500 的"保持"是**对焦锁定期间的取景框冻结**（合焦→锁框→重构图；AF 驱动完成/解锁/AE 取消即释放）。这是 focus-and-recompose 语义，不是追焦语义。

### 2.3 它没有解决的问题

1. **保持的是"框"，不是"人"**。主脸选择仍是第二轮那套 `6×中心名次 + 3×面积名次`（`0x143740`），没有身份项、没有历史主脸偏置。锁定窗口之外，谁离中心近、谁面积大名次高，框就可能换人。
2. **释放点太早**。`onAFCompleteDriving` 一到就清标志；CAF 下一次 re-drive 期间框重新跟着检测跑。想在「半按—重新构图—再半按」之间守住同一张脸，需要把 hold 跨过这个窗口。
3. **hold 与"跟随"互斥**。hold 生效时 AF 区域是冻结副本，主体动了框不动——这正好是追踪想要的反面。两者只能按时序切换，不能同时。

### 2.4 FD 区域的去抖：一个常量两个方向

`0x2f6c48` 是人脸区域的准入门（第三轮/第二轮已定位），这一轮把它拆到寄存器级：

```asm
2f6c88  cmp  r2, #2          ; r2 = GAF[0x5c] 内部执行阶段
2f6c8c  movne r8, #0x320     ; 800
2f6c90  moveq r8, r5         ; 阶段 2（S0-AF）→ 0
...
2f6cfc  cmp  r8, r2          ; 获得方向：800 > now - GAF[0xa0] → 继续等
2f6dd4  cmp  r8, r2          ; 丢失方向：同一寄存器、同一常量
```

**一个寄存器同时喂"新脸确认"和"旧脸释放"**，所以现在没法做非对称等待——要改必须先把 `r8` 拆成两个来源（比如在 `0x2f6dd4` 前换用另一个常量寄存器），否则动一处两边一起变。

时间单位这一轮也定了：`0x4dd064` = `0x2ba9c() / 1000`，而 `0x2ba9c` 读 `0x06002060/64` 的 64 位计数器后 **先除 26**。也就是说固件自己按 26 MHz 计时源把它折成毫秒，`0x320` 即 **800 ms**（阶段 2 为 0 ms）。这个 800 ms 是双向共用的。

### 2.5 数据出口：AF 区域最后落在哪

```
GetMainFaceArea(0x141a80)
  → 0x2f6c48 准入/去抖（800 ms）
  → 0x2f6ae0 发布到 GAF+0x29f0..0x2a04（x,y,w,h,src_w,src_h）
  → 0x2f7730 写入 CAFData Sequence[0x13..0x1a]
       0x60011=脸数 0x60012=状态字（来源寄存器未定名） 0x60013..0x6001a=六个区域字
```

这是**第一次把"人脸框 → AF 区域"的完整总线写清**。它的意义是：无论改哪一端（检测、hold、还是眼部），只要落在这条总线的上游，下游 AF 无需改动。

## 三、眼部 AF：全链路都在，只差最后一根线

### 3.1 眼部结果长什么样

`0x3dc910`（`CEyeDetectionIf` 一族）对每张脸算一次，写进同一份 0x444 载荷：

| 字段 | 偏移 | 说明 |
|---|---|---|
| 眼 A 矩形 | `0xc8 + 0x14*i`（x,y,w,h 在 +0,+4,+8,+0xc） | **正方形**：`h = w`（`0x3dcc64/0x3dcc68` 同为 r3） |
| 眼 A 有效 | `0xd8 + 0x14*i` | 字节 |
| 眼 B 矩形 | `0x190 + 0x14*i` | 同样正方形（`0x3dcc50/0x3dcc54` 同为 r2） |
| 眼 B 有效 | `0x1a0 + 0x14*i` | 字节 |

结果码 `r7`（来自 `0x3dbc70`）决定写哪只眼：

| `r7` | 含义 | 指令 |
|---|---|---|
| 1 | 两眼都有效 | `0x3dcb08` 置 B、`0x3dcb10` 置 A |
| 2 | 只有眼 B 有效 | `bic r7,r7,#2` 后 A 分支不成立 |
| 其它 | 两眼都无效 | `0x3dcab4/0x3dcab8` 先清零 |

**每张脸每次尝试前都先清两个有效字节**（`0x3dcab4`、`0x3dcab8`），所以"载荷里有眼框数组"不等于"这一帧有有效眼框"——第二轮的这个警告这次有了指令级依据。

### 3.2 它只在三种场合被调用

| 场合 | 入口 | 条件 |
|---|---|---|
| 取景 · 笑脸 | `0x1430ec` → `0x177da0(image, w, h, this+0x54)` | CFDTask `[this+0x918] == 3` |
| 取景 · 眨眼 | `0x143230` → 同上 | `[this+0x918] == 4` |
| 拍后处理 | `0x14515c`、`0x145544` | 美颜/表情后处理链 |

任务模式由 `0x142224` 设置，App 侧映射在 `0xfcc98`：`1→1、2→3（笑脸）、3→4（眨眼）、其它→0`。**普通人脸模式（1）不跑眼部**——这是眼部门控的全部内容。

### 3.3 AF 侧一处都不读

用"同时访问两条眼记录 + 载荷脸数 `0x39c`"作为签名，全镜像筛出的函数集是：

```
0x389104 0x3d413c 0x3da3d0 0x3dc5ac 0x3dc910
0x3e14b0 0x3e27cc 0x3e2a80 0x3e3728 0x3e38bc
```

全部落在 `0x3dxxxx–0x3exxxx` 的脸部子系统（检测、清理、结果转换），**AF 代码区 `0x2f0000–0x375000` 内零命中**。另有一条更硬的负结果：`0x141a80` 整个函数体里没有任何一处访问 `0xc8/0xd8/0x190/0x1a0`（断言覆盖 `0x141a80–0x141bbc`）。AF 只读 `+0x14*i` 的框和 `+0x258+4*i` 的角度。

也就是说：**眼坐标 → AF 区域这条线在 v1.12 里不存在，不是被开关关掉，是从来没接。**

### 3.4 要接的话，最小改动面

两点，都在既有函数里，不新增模块：

**P1 · 让眼部在普通模式跑起来**
在 `CFDTask::EventHandler` 调完 `0x143d30`（`0x1442e8`）之后、`0x1442ec` 之前插一段：
```
if ([this+0x918] == 1 && [this+0x3f0] > 0)          // 普通脸模式且检到脸
    0x177da0([this+0x18], [this+0x2e], [this+0x30], this+0x54);
```
`0x3f0 = 0x54 + 0x39c`，就是载荷脸数；三个参数与笑脸路径完全一致，可直接照抄 `0x143120–0x143134`。

**P2 · 让 AF 用眼框**
在 `0x141a80` 复制矩形处（活载荷路径 `0x141b2c` 之后、hold 路径 `0x141b8c` 之后）插入：
```
if (rec[0x10 + EYE_A_VALID] != 0)       // rec = 记录基址
    use rec[EYE_A .. EYE_A+0xc] 并扩到最小 ROI
else if (rec[0x10 + EYE_B_VALID] != 0)
    use rec[EYE_B ..]
else
    use rec[0..0xc]                     // 原脸框
```
两条路径的记录基址差 0x24，但**眼字段相对记录基址的偏移相同**（`0xc8/0xd8`、`0x190/0x1a0`），所以一套判断可以同时服务活载荷和 hold 副本——只要把基址算对。

三点必须保留：① 眼框是正方形小框，直接当 AF 区域会小于反差测量的可用窗口，需要按脸宽比例设下限；② 坐标域与脸框相同（眼部算法就是用脸框裁剪的），src_w/src_h 由 `0x141a80` 一并返回，下游不用改；③ 无有效眼框时必须回退脸框，不能让 `0x2c13b8` 的正数校验失败。

### 3.5 三条必须先想清的代价

1. **hold 会冻结眼框**。`UpdateHoldFaceBox` 复制整份 0x444，眼睛也在里面。hold 生效期间再取眼框，拿到的是冻结那一刻的眼位。眼 AF 与 hold 只能二选一，或者让 hold 只冻脸框不冻眼（那就要拆 memcpy）。
2. **算力**。`0x3dc910` 每张脸要 `operator new` 两次（`0x11f24`）并做裁剪/缩放，机身单核本来就饱和。这是它被关在笑脸/眨眼里的最可能原因，开之前必须实测帧率与 AF 响应。
3. **小脸/侧脸**。算法在脸框内做缩放/旋转（`0x3e00c0`、`0x3e1260`），输入是脸框内的正方形区域；脸太小的时候眼框会退化到几个像素，AF 反差窗口无意义。回退阈值要按像素定，不能按比例。
