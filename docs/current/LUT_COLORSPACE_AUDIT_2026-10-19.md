## 为什么灰表会变绿、白表会变粉

在带 128 色度偏置的 YCbCr 中，无彩色需要 `Cb=Cr=128`，亮度可以变化。[ITU-R BT.601-7](https://www.itu.int/rec/r-rec-bt.601-7-201103-i/en) 给出亮度和色差信号的定义。

仅作反例，采用 BT.601 系数的全幅模型，并假设三个字节为 `(Cb,Cr,Y)`：

| 写入三个字节 | 模型解码到 RGB（截断至 0..255） | 含义 |
|---|---|---|
| `(0,0,0)` | `(0,135,0)` | 绿 |
| `(64,64,64)` | `(0,132,0)` | 绿 |
| `(128,128,128)` | `(128,128,128)` | 中性灰 |
| `(255,255,255)` | `(255,121,255)` | 粉/品红 |
| `(128,128,255)` | `(255,255,255)` | 白 |

因为两条色度在这些例子中相等，交换 Cb/Cr 不改变结果。此表是**数学反例和诊断预测，不是相机矩阵或现场像素测量**；相机实际使用 BT.601/709、全幅/限幅等仍待确认。

本地 `bw_acros100.bin` 每项三字节相等，只能证明它是 **RGB 灰表**。若消费者按色度/亮度解读，它就不再保证灰色。换回原厂字节立刻正常，同样与这个解释相容，不能排除色彩语义错误。

## 对现行实现的影响

- `scripts/lut.sh` 的 `.bin` 分支直接写源文件，不更新 `state/current.bin`。后者可能仍是上一张 `.cube` 的转换结果，不能拿它当“当前实际应用的表”。这也解释分享中曾把上一张 Velvia 当作黑白表写入的实验混淆。
- 双槽与单槽都不能修正错误的 RGB/YCC 坐标。当前“固定 A18 是唯一即时生效路线”的注释超出了证据：当时连取景器选中的登记项都没命中。
- 给 `patch1` 接一行 apply 仍不足以交付。应先确认消费分支和正确色彩探针，再决定单项跟随或多项重定向；恢复必须对称覆盖实际修改的登记项。
- 若最终确认为 YCC，`.cube` 转换需要同时处理 **输入格点 YCC→RGB → RGB LUT 采样 → 输出 RGB→YCC**；只在输出端换字节或转换三个值不够。
- 旧 `filmsim/rgb2ycc.py` 使用 6B/项、Y 最快的另一套假说，与已验证的 4B/项布局不同，不能直接复用为修复。
