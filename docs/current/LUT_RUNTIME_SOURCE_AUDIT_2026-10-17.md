## 1. 结论与路线选择

**已补上此前真正缺失的一环：镜像 LUT 数据如何进入运行时地址。** P7 启动代码把整段已初始化数据从镜像装载地址复制到运行地址，42 个候选槽均落在这段复制范围内。逐槽搜索常量引用找不到来源，并不代表不存在填充者。

长期方向仍是 **C3：让 P7 正常选表、重载和拍摄流程使用导入表**。C1 保留为一次一槽的机制实验；R-B（LUT1 + 守护）保留为已有实证的预览后端。当前无需继续扩大物理内存扫描，也无需另开 IPCC/CSIS 私有设备探测。

今天的直写负结果应记为“所测状态下，改 A12 对应内存后未观察到明确效果”。它不能单独证明地址错误，也不能否定全部运行时换表方案。C1 的“修改会被启动复制到目标 RAM”现在有代码和仿真证据；**预览/JPEG 是否消费该表仍需分别实测**。

## 3. 新证据：整段初始化复制

在 `p7_a2.bin` 中找到以下原指令（地址均为 P7 代码地址）：

```text
80011620  ldr     r1, [pc, #0x138]  ; literal @80011760 = 8079BDC0
80011624  ldr     r2, [pc, #0x138]  ; literal @80011764 = 81006000
80011628  ldr     r3, [pc, #0x138]  ; literal @80011768 = 813EE4C0
8001162C  pld     [r1, #0xC0]
80011630  vldmia  r1!, {d0-d7}
80011634  vstmia  r2!, {d0-d7}
80011638  cmp     r2, r3
8001163C  blo     8001162C
```

复制关系：

```text
镜像 file [0x79BDC0, 0xB84280)
  装载地址 [0x8079BDC0, 0x80B84280)
        -- 启动复制 0x3E84C0 = 4,097,216 字节 -->
  运行地址 [0x81006000, 0x813EE4C0)

runtime = 0x80000000 + file_offset + 0x86A240
```

这不是推测的逐表复制，也不是依赖 ELF 段表的加载：镜像里有直接执行的批量复制循环。旧 T4 的“无槽首地址引用、无 ELF 段表 ⇒ 填充者不在镜像内”推断作废。

三项独立核对：

1. **真实历史 dump**：`dram_pools_256k.bin` 的全部 262,144 字节，与 A2 镜像 `[0x885DC0, 0x8C5DC0)` 完全相同，diff=0；不限于四张表。
2. **原指令仿真**：在 Unicorn 中执行 `0x80011620..0x80011640`，完整复制 4,097,216 字节并到达预期出口，diff=0。仅开启 VFP 并映射 RAM，无外部调用桩、无 MMIO；没有模拟全启动、缓存或 DMA。
3. **既有 C1 候选**：与 A2 仅 A12 槽内 13,901 字节不同；同样执行复制后，`0x810FD100` 的整槽 md5 为 `235ad45324c042d0bd4233513e1fca52`（候选 identity）。这证明候选在该复制流程下进入目标 RAM，不证明真机画面效果。

## 4. 修正 View / Still 调用链

T4 把 View 静态四档的转发链接到了 Still 条件选表。重新逐个核对尾跳转：

```text
View 静态：8009A3E8 -> 802B03F4 -> 8029BAA4 -> 80381B2C -> 803837D0
Still：    8009A3C8 -> 802B03D4 -> 8029BA84 -> 80381ABC -> 80382B30
View 动态：8009A408 -> 802B0414 -> 8029BAC4 -> 80381B4C -> 80383800
```

`0x803837D0` 静态叶函数本身不做亮度阈值计算，其 `(r1,r2)` 四种输入对应：`(0,0)→skin`、`(1,0)→cine`、`(0,1)→mono`、`(1,1)→std`。本轮在 A2 与 C1 仿真 RAM 中各执行四次，8/8 返回预期地址；C1 仅 std 所选表变为 identity。

`CBackend_3dlut_View::_load` 在 `0x8011E268` 检查条件，在 `0x8011E27C` 调静态选择器或 `0x8011E2DC` 调动态选择器，之后在 `0x8011E2B8` 调 `0x80179314(table, sel=0, …)`。因此“名为标准的池”不等于该次取景必定选它；静态、动态分支和实际输入都应分开留证。两个选择参数不直接等同用户菜单名称。

## 5. 直写负结果能说明什么

本轮对原件重新核验：

| 文件 | 实际长度 | 相对对应镜像区的差异 |
|---|---:|---|
| `dram_pools_256k.bin` | 262,144B | 0 |
| `dram_pools_after.bin` | **196,608B** | 0（不能当完整 256KB） |
| `dram_chk.bin` | 262,144B | 14,748B，全部在 std/A12 槽内，整槽与 `neg_test.bin` 一致 |
| `dram_final.bin` | 262,144B | 0；**整个 256KB 与初始 dump 一致** |

这支持“写后的 CPU 侧映射可见，最终完整还原”，还不能证明硬件消费了写入内容。日志中的“负片无变化”“半按后仍无变化”为当时人工观察，本轮没有新的画面证据。

尚未排除：

- **未选中 A12**：历史寄存器记录常见 `0x81115200`（A17）；这不是今天实验当时的同步快照，但足以说明不能默认当前用 A12。
- **没有实际重新装载所写表**：镜像中装载通过地址寄存器和启动脉冲把数据送入硬件。仅改 RAM 不会自动执行这些动作；半按也不能代替“选中了该表且重载完成”的证据。`+0x00C` 是 Load 源地址登记，不应解释为硬件持续查 RAM 的指针；`+0x010` 是 Save 地址。
- **可见性/同步条件不明**：写入探针用 `/dev/mem` 的 `O_RDWR`，没有 `O_SYNC` 或设备侧完成证据。所获内核源码 `arch/arm/mm/mmu.c:548` 对有效 RAM 页会依据 `O_SYNC` 选择映射属性；原包配置启用了 `CONFIG_ARM_DMA_MEM_BUFFERABLE`。该源码不等于当前运行内核身份，但说明跨进程读回不能独自排除 CPU/设备缓存可见性问题。
- 该次管线可能未启用/未选中相应 LUT bank。没有同场 OnOff/Cfg 与成功重载记录，无法由“没变化”区分这些情况。

故不采用“写入没效果 ⇒ 同值 PA 一定是副本 ⇒ 真表必在 CMA”的推理。启动 MMU 代码也包含初始 identity 映射；若要提出运行时 VA/PA 不同，需另给转换证据。CMA 第一区的表头扫描未命中，不能裁决这个问题：旧扫描器会静默跳过 mmap 失败区，也漏掉块边界匹配，且未记录完整扫描覆盖率。

## 6. 下一轮实验：先证实选表，再决定是否写

| 顺序 | 动作和产物 | 推进条件 / 判据 |
|---|---|---|
| 1 | 使用已有验证过的只读采集路径，固定场景记录 OnOff/Cfg/Load 源地址、PW 状态、四池哈希；分别记录静置、半按及正常切模式后的结果 | 网络可达、进程存活、实际画面分别记录；静态寄存器快照只说明快照时状态，不冒充已捕获瞬时 DMA |
| 2 | 据读到的地址和已补齐的源槽映射，选**一个实际被正常流程装载的槽**，并区分 View 和 Still | 若正常流程用 A17，原 C1/A12 包就不是命中该状态的单槽实验；不能以 A12 无变化宣布 C1 失败 |
| 3 | C1 机制实验仍以现有一槽包为候选；执行前明确 A12 可达的操作条件，否则重新准备实际目标的一槽诊断件 | 刷前/刷后固件身份、目标 RAM 表变化、预览效果、JPEG 效果四层分别验收；identity 仅作诊断，不保证是最强视觉差异 |
| 4 | 按下面结果选择 C3 接入点 | 导入时修改的数据必须位于 P7 实际选用的表或其受控替代缓冲；提交需使用正常加载时机，不能只做裸 memcpy |

阶段判定：

- **C1 固件身份正确，RAM 仍是原表**：先查启动/恢复/再初始化是否经过已找到的复制循环；不推断管线支持与否。
- **RAM 为新表，当前选择的是另一张表**：修正实验目标或选择条件，不能裁决 C1/C3。
- **已确认新表被所测管线成功装载，预览变化而 JPEG 不变**：继续追 Still 的选表/重载路径，保留 E4 的既有负结果。
- **预览/JPEG 都随同一修改发生可复现变化**：机制通过，再进入受控运行时导入设计。

### C3 的最小设计约束

输入带目标槽、表体/整槽长度、内容哈希与提交序号。先在有明确所有权的缓冲里完整准备表，再在 P7 已知的加载时机提交；失败保持旧表，并保存每槽原始基线。20KB 复制、CPU/设备可见性、DMA 完成、半按/全按后的再次选表必须分别验证。不能由 A2 标量通道成功直接推定大表交换可行。

R-B 的修复版 T5 尚需核对机端脚本及真实 `--ch1` 调用后回归；已有 E1/E3 证据保留，成片不提前承诺。现有 NXUI 可日后调用该后端，但在来源/装载验收完成前不扩展 LUT UI。
