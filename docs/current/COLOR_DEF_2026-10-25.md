# 三星色彩的定义 & 冷暖设计复盘（2026-10-25）

> 方法：`tools/lutgen/color_def.py`（新增，纯标准库）。全部度量在 CIELAB(D65) 里做。
> 冷暖有严格定义：**b\* > 0 黄（暖），b\* < 0 蓝（冷）**。用 R/G 比值判冷暖必然把饱和度
> 误判成色温——这正是 `audit.py` 的 `warm_red` 只能当粗筛的原因。
> 基准表：`.tmp/cube_regression_2026-10-19/samsung_a0*.bin`
> （md5 `134909c7` / `69a4ac46` / `3ac93837`，与机身槽一致）。

## 0. 结论

三星的色彩定义不是「加蓝减红」，是四件事的组合，且**四件事互相咬合**：

| # | 手段 | 量级 | 我们有没有 |
|---|---|---|---|
| 1 | 白点压到 L\*76–77 且蓝顶满 | (182,182,254) | ❌ 白点 L\*=100 |
| 2 | 灰轴三段分离色调（暗冷／中暖／高极冷） | b\* −14 / −5 / −39 | ❌ 只有单一 fog 偏色 |
| 3 | 色相环大幅重排，**且旋转量随明度衰减** | 暗部极差 71°，亮部 12° | ❌ 暗/亮梯度 0.7–1.2（反了） |
| 4 | 蓝通道仿射注入：R/G ← 0.29 + 0.42·R/G | (0,0,255)→(74,74,254) | ⚠️ 只在纯蓝角点对上，中间调全漏 |

第 4 条尤其关键：**它是 RGB 空间的仿射，不是 HSV 的饱和封顶**。我们的 `cool_guard`
在 (0,0,255) 上和原厂差不到 3 个 8bit 级，但 (100,100,255) 原厂出 (116,116,255)，
我们原样输出——所以「蓝角点对了、蓝天还是不对」。

## 1. 三星的四件事

### 1.1 白点不是白

| 表 | 输入 (255,255,255) → | L\* | 说明 |
|---|---|---|---|
| samsung_a00 | (182,182,254) | 76.4 | B 顶满，R/G 压到 0.71 |
| samsung_a01 | (178,178,254) | 75.1 | 同上，更狠 |
| samsung_a02 | (185,185,254) | 77.4 | 同上，略轻 |

三张表**全部**放弃纯白。这不是限幅失误——L\* 在 224 格点达到峰值（a00 80.5 / a02 87），
输入 255 时**反而降回 76–77**。即高光是「滚降 + 降温」的双重处理。

后果：画面没有刺眼的白，高光带蓝，整体像蒙一层极薄的冷雾。

### 1.2 灰轴三段分离色调

samsung_a02 的灰轴 b\*（按 L\* 分段）：

```
L* 0-37   b*  0 → -6     暗部：缓冷
L* 46-85  b* -3 → +5 → +2  中间调：暖
L* 87-77  b* -3 → -34     高光：断崖式极冷
```

a00 更极端：暗部 b\* 到 **−14**，高光 **−39**，中间调只回到 −5。

**这是「warm midtones / cool highlights」的电影调色手法**，而且暗部也冷——三段并非常见的
「暗冷高暖」二分，而是「冷—暖—极冷」的夹心。肤色落在中间调，所以被单独烘暖。

### 1.3 色相环：大幅重排 + 明度衰减

samsung_a00 在 24 个色相上的 dHue（度），四组明度/饱和条件：

```
条件(s,v)      极差   峰值位置   dHue(h=0)  dHue(h=150)
lo-dark .40/.35  71°    h=150 +40    -25        +40
hi-dark .85/.35  30°    h=150 +18     -8        +18
lo-lit  .40/.80  26°    h=180 +13     -4        +11
hi-lit  .85/.80  12°    h=195 +6      -3         +4
```

两个规律：

1. **旋转量随明度单调衰减**：暗部 71° → 亮部 12°，比值 **5.9×**。
   物理上合理——暗部色相辨识阈值高，重排不易察觉；亮部高饱和色相一转就「变味」。
2. **曲线是一阶谐波**（峰值 h=150 绿青、谷值 h=15 橙红），近似
   `dHue ≈ 35·sin(h − 60) + 5`。这在色彩学上等于**把色相环椭圆化**：
   绿青段被拉伸（dh'/dh ≈ 1.6），品红-红段被压缩（≈ 0.4）。

a02 是克制版：暗部极差 26°、亮部 10°，且**低饱和亮部只给暖色加味**
（h=15 处 dS +0.07、dB\* +8，冷色一处不动）。这就是「人像档」——环境不染色，只暖皮肤。

### 1.4 蓝通道是仿射注入，不是饱和封顶

原厂三个蓝端角点的输出：

| 输入 | → a00 | → a02 |
|---|---|---|
| C (0,255,255) | (74,182,254) | (70,185,254) |
| M (255,0,255) | (182,74,254) | (185,70,254) |
| B (0,0,255) | (74,74,254) | (70,70,254) |

拟合出 **R_out = 74 + 0.424·R_in，G_out = 74 + 0.424·G_in，B_out ≈ B_in**。
C 与 M 的 dHue 恰好 ±24.0°（a00）/ ±22.5°（a02），**对称是必然的**——它就是同一条
仿射在 R、G 两轴上的两面。

含义：给蓝通道注入一个 0.29 的红/绿基底，并把斜率从 1.0 降到 0.42。这模拟胶片蓝色层
里的品红耦合（dye crosstalk），同时把 L\* 抬 11 级。所以三星的蓝是**亮、灰、偏青**的，
不是深蓝。`s_max` 全段仍是 0.93–1.00——**原厂从不压低色域天花板**。

### 1.5 原厂不压红

| 表 | R (255,0,0) → | dL\* |
|---|---|---|
| a00 | (248, 8, 16) | −1.2 |
| a01 | (240, 16, 16) | −2.6 |
| a02 | (254, 1, 1) | −0.2 |

红色角点几乎原样保留，只做 −0.03~−0.07 的去饱和。**「三星偏红」在数据上不成立。**

## 2. filmlab 线的结构性缺陷

`scripts/filmlab/recipes.json` → PW 七维：`R_COLOR/G_COLOR/B_COLOR`（100 中性）
`+ HUE/SATURATION/SHARPNESS/CONTRAST`（10 中性）。

文档已定性：**「7 维 = 逐像素同值的全局向量」**。这句话就是判决书——

- 没有色相选择性这个维度。上表 1.3 的 71° 正弦重排、1.2 的三段分离色调，
  在 PW 坐标系里**不存在实现路径**，无论参数怎么调。
- `HUE` 是全局旋转，转 1 格所有色相一起动。红变橙的同时青必须变蓝。
- `R/G/B_COLOR` 是通道增益，落在 sensor RGB 域，**与场景白平衡耦合**：
  用户改机内 WB，配方的冷暖就漂。

实测配方 HUE 全部落在 9–13（中性 10），即「整体转 +1~+3 格」，与色相无关。

结论：**filmlab 只能做「整体偏色 + 整体浓淡」，做不到色彩定义。它是 3D LUT 的降级备份，
不是替代品。** 冷暖设计不该在 filmlab 里投入。

## 3. LUT 线的四个缺陷

### 3.1 cool_guard 是硬截断，原厂是软压缩

h=230、v=0.70 时输入饱和 → 输出饱和：

| 输入 s | 0.70 | 0.75 | 0.80 | 0.85 | 0.90 | 0.95 | 1.00 |
|---|---|---|---|---|---|---|---|
| **原厂 a00** | 0.71 | 0.76 | 0.80 | 0.85 | 0.89 | 0.93 | 0.96 |
| kodak_portra400 | 0.58 | 0.63 | 0.68 | **0.70** | **0.70** | **0.70** | **0.70** |
| cool_blue | 0.70 | **0.70** | **0.70** | **0.70** | **0.70** | **0.70** | **0.70** |

原厂是单调 1:1 映射，只在顶端软拐。我们 0.85 以上**全部塌到同一个值**：蓝区 s>0.60
的输出饱和取值数，原厂 39 个，portra400 11 个，cool_blue 13 个。

**30% 的饱和自由度被抹掉** ⇒ 蓝天渐变、蓝色物体的明暗层次全部压成一块平色。这是
「蓝色看着怪」的第二层原因（第一层是 blue hue 本身偏紫，已在 10-25 修过角点）。

另外 `COOL_HMIN/HMAX = 190/270` 漏掉了青（h=180）。`cool_cyan` 的 s_max 在 h180 是 0.94，
等于没管。

### 3.2 warm_guard 是开环常数，方向各表不同

`WARM_GUARD=0.45` 对所有表一律生效。实测肤色点 (180,110,70)：

| 表 | wg=0 的 dHue | wg=0.45 的 dHue | wg=0.45 的 dL\* |
|---|---|---|---|
| canon_portrait | **+0.7°** | +3.6° | **−1.6** |
| leica_m9 | **+3.8°** | +7.0° | −0.7 |
| kodak_portra400 | −1.2° | +1.4° | −3.0 |
| fuji_velvia50 | −3.4° | −0.1° | −11.7 |

只有 velvia50 这类「本身往红偏 3°+」的表被修对了。`canon_portrait` 在 wg=0 时本来
完全不偏红，**是 warm_guard 自己制造了 +3.6° 的黄偏和 2.4 级压暗**——一张肖像表把
脸色推黄，方向是反的。

根因：`cut = (r − g) · wg · w` 是**减法**，削 R 不减 G ⇒ 色相必然向黄移、v 必然下降。
而原厂处理暖色的方式是**降饱和 + 降 L\***（R 角点 dS −0.04、dL\* −1~−3），色相不动。

「厚而稳的红」和「削掉的红」在数据上差得很远，观感上更远。

`warm_lift=0.51`（削幅还给 G）实测过冲更狠：leica_m9 到 **+12.1°**、canon_portrait +7.6°。
默认关是对的。

### 3.3 坐标系三套混用

一个像素现在依次经过：linear（WB）→ gamma → RGB clamp → HSV（sat/rot）
→ RGB（warm_guard 削 R）→ 8bit 量化 → **再回 HSV**（cool_guard）。

四个算子的空间不统一，效果不可叠加预测。例如 warm_guard 削完 R 会改变 HSV 的 h，
cool_guard 又在 8bit 域的 h 上判断——同一像素被两套色相定义各判一次。

### 3.4 8 锚点撑不起色相维度

`hue_lookup` 用 σ=38° 高斯对 8 个锚点归一化插值。在 h=30，锚点 30 的自身权重只有
**36%**（其余来自 0/60/330/120 的溢出）。8 个锚点实际只有 3–4 个有效自由度。

原厂的曲线在 h=150 达到 +40°，而 150 不在任何锚点上。**这套参数化在原理上做不出那条曲线。**

## 5. 改法

按投入产出排序。

**P0 修数据**：恢复 `looks/samsung_a0*.bin` 为真镜像；`retune_legacy.py` 的排除名单加
`samsung_`；`audit.py` 的 FACTORY 判定改成**校验 md5**而不是校验文件名——否则豁免逻辑
会一直为一张假表服务。

**P1 饱和改软拐点**：`cool_guard` 从 `s = min(s, CAP)` 改成
`s = CAP + (1−CAP)·(1 − exp(−(s−CAP)/k))` 之类，保证单调且只在顶端压缩。
原厂的实测曲线（1.3 表）直接当标定目标。同时把窗口从 190–270 扩到 175–300。

**P2 warm_guard 改闭环**：不设全局常数，每张表先测自己的 `dHue_skin`，然后按
`target − current` 反算强度。目标值取 0（原厂 a00/a01 是 −3.5°，但那是冷调档；
中性档应该 0）。`warm_lift` 保持 0。

**P3 色相环参数化换掉 8 锚点**：改成
`dHue(h) = A·sin(h − φ) + C`，三个参数 (A, φ, C)，另加明度权重
`W(v) = 1 − k·v`（原厂 k≈0.83，即暗部 100%、亮部 17%）。这一条能把「暗部优先」的
结构做出来——现在全库 60+ 张表的暗/亮旋转梯度都在 0.7–1.2，而原厂是 2.5–2.7。

**P4 白点/黑点/高光滚降进主流程**：目前 `shoulder` 只压高光不改色，白点恒为 255。
原厂的「高光降温 + L\* 滚降」需要单独一层：`L*(v)` 在 v>0.87 段回勾，同时 b\* 向下拉。
这一层要**按档位可选**（原厂那种 L\*79 的白点不适合日常拍摄，只适合做「电影档」）。

**不建议动**：饱和增益 `sat`、对比 `contrast`、`crosstalk` 这几个全局量——它们不是
冷暖设计的问题所在，改了只会让已有的表全部漂移。

## 6. 实施记录（同日，已落盘 looks/）

用户反馈「经典胶片色调基本没有复刻成功」。做了对点测试，抓到三个**结构性 bug**（不是参数没调好）：
参数怎么填都看不出效果，因为管线把它们吃掉了。

### 6.1 修的三个 bug

| # | 位置 | 症状 | 根因 | 修法 |
|---|---|---|---|---|
| 1 | 第 10 步 `cool_guard` | 蓝天渐变塌成一块平色 | `s = min(s, 0.70)` 是 v 无关的硬截断，内部点也压 | 换 `sat_ceiling(h,v,s)`，标定自原厂实测 |
| 2 | `hue_lookup` | `hue_rot {120:-3}` 在 h=220 的蓝区也加 −3° | 归一化让单锚点表整圈生效（Portra 天空因此无端偏暖 dB\* +2.2） | 拆出 `hue_shift()`，不做归一化、70° 外权重 <0.05 截断 |
| 3 | `hue_weight` σ=38 | 填 ±5° 出来只有 ±1.5° | h=30 处锚点 30 自身权重仅 36% | σ→20（自身权重 60%） |

**`sat_ceiling` 的标定**（原厂 a00 在 h=230 的实测 → 模型）：

```
         s=0.70  0.80  0.90  0.95  1.00
v=1.00    0.58  0.62  0.67  0.69  0.71     模型误差 ≤0.023
v=0.85    0.67  0.74  0.81  0.84  0.87     模型误差 ≤0.025
v=0.70    0.74  0.83  0.91  0.94  0.98     模型误差 ≤0.042
```

`s_out = s·(1 − A·w·s)`，`w = ((v−0.65)/0.35)^1.3`，`A = 0.29`（h∈150–330）/ `0.036`（红绿）。
三个蓝端角点全部落在 .715（原厂 .709），红绿 .964（原厂 .968）。

### 6.2 参数化改造

**`split` 取代 `shadow`/`high`/`fog`**：Lab 域的分离色调，参数即目标：

```json
"split": [b*暗部, b*高光, a*暗部, a*高光]
```

依据是胶片物理：彩色负片有橙 mask ⇒ 暗部暖；反转片无 mask ⇒ 中性偏冷；Kodachrome 的
K-14 暖棕；Eterna 青绿阴影。28 张胶片表全部重设，23 处 `fog` 删除（全局偏色已由 split
承担，两层叠加方向会打架）。

**`hue_rot` 方向重设**：原来的参数把 **Fuji 的绿做成了偏黄**。Kodak 绿偏黄、Fuji 绿偏青
是两家最标志性的差异，而修复前两家平均 dHue 是 −1.3 与 −2.3，**全在偏黄同一侧，根本分不开**。

## 7. 推送批次（47 张，待上机）

### 7.1 又抓到一个致命 bug：`hue_lookup` 把饱和度归零

```python
if den < 1e-9:
    return 0.0      # ← 这是乘数（基线 1.0），返回 0 等于把饱和度清零
```

σ 从 38 降到 20 之后必然触发：h=12° 的橙色到蓝锚点 240° 距离 228°，
`exp(−228²/800)` 浮点下溢 ⇒ den=0 ⇒ 返回 0 ⇒ **`(255,48,0)` 输出成 `(249,249,249)` 纯白**。
`cool_blue` 有 204 个格点对因此跳变 200+ 级，audit 里 5 张 `BAD:jump_ratio` 全是它。

这就是「大块橙色/肤色变灰白」的原因，也是 `Portra` 输出糟糕的嫌疑之一 ——
只要一张表有蓝区锚点，它的橙色就可能被掐死。

顺带修掉第二个语义错误：朴素归一化让**单锚点表在整圈色相上给满值**
（`{240:1.18}` 在 h=12 也给 1.18）。改成 `1 + Σw(v−1)/max(1,Σw)`：
