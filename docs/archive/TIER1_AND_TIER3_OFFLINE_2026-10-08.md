## 1. U04 · p7 地址模型精确重建（★ 修正一处、开出一条新实验）

### 1.1 Reset 的 MMU 建立过程（`FUN_00000140`，逐条解出）

```c
uVar2 = DAT_00000240;              // = 0x402
uVar4 = 0;
puVar3 = (uint *)&DAT_81000000;    // ★ L1 页表基址 = 0x81000000
do {
    *puVar3 = uVar4 | uVar2;       // PTE[i] = i*1MB | 0x402
    uVar4 += 0x100000;
    puVar3 += 1;
} while (uVar4 != 0);              // ★★ 4096 次 —— 覆盖整个 4GB！

puVar5 = 0x80000000;
puVar3 = DAT_00000244;             // = 0x81002000  ← 同一张表的第 2048 项
do {
    *puVar3 = (uint)puVar5 | DAT_00000248;   // | 0x1c0e
    puVar5 += 0x100000;
    puVar3 += 1;
} while (puVar5 != &DAT_81000000); // ★ 16 次 —— 只改 VA 0x80000000-0x80FFFFFF

coproc_moveto_Translation_table_base_0(DAT_0000024c);   // TTBR0 = 0x81000009 → base 0x81000000
coproc_moveto_Translation_table_base_1(DAT_0000024c);   // TTBR1 = 同
```

★ `0x81002000 = 0x81000000 + 2048*4`，而 `0x80000000>>20 = 2048` ⇒ **两个循环写的是同一张 L1 表**：
- 循环 1 建**全 4GB 的 identity map**，flags `0x402`（非缓存、仅 PL1 可访问 —— 引导期的保守映射）
- 循环 2 把 **VA 0x80000000–0x80FFFFFF 那 16 项**升级成 flags `0x1c0e`（**缓存写回、可执行、PL1/PL0 可读**）

位域复核（我第一遍读错、已修正）：`0x80001c0e` 的 **bits[31:20] = 0x800 ⇒ PA = 0x80000000**，
**是 1:1，不是我一度以为的 +0x1000**。

### 1.2 ★★ 「VA ↔ 文件偏移 = 1:1」的实测判决

用一个可证伪的统计：扫全镜像所有 4 字节对齐的 `0x8xxxxxxx` 值，看按哪种模型换算后**正好落在 Ghidra 的函数起点**上。

| 模型 | 命中函数起点数 |
|---|---|
| **1:1（`file = VA - 0x80000000`）** | ★ **3969** |
| +0x1000（`file = VA - 0x80001000`） | 595 |

⇒ ★★★ **1:1 成立（6.7 倍差距）**，与项目现有换算一致，`50_virt2file.txt` 无需改动。

### 1.3 ★★ 因此要修正 README 里的一句话

| 原文 | 实际 |
|---|---|
| 「p7 页表只覆盖 `0x80000000..0x80ffffff`」 | ❌ **p7 页表覆盖整个 4GB**；16 项窗口只是给代码段做**缓存/可执行属性升级** |
| 「那 4 个 LUT 缓冲在 `0x81xxxxxx`，**超出 Linux `mem=512M`**」 | ⚠️ **算术上站不住**：若 Linux DRAM 基址是 0x80000000，`0x810fd100` 距基址只有 ~17MB，是**窗口内**，不是"超出" |

⇒ ★ 所以 **补一个此前没做过的实验（详见 §1.4）**；同时把 p7 侧结论改写成正确的形式：

> **p7 完全看得见 `0x810fd100 / 0x81106b00 / 0x81115200 / 0x81101e00` 四个 LUT 缓冲
> （identity、非缓存、PL1 可访问），L1 页表本身也住在 `0x81000000`（= p7 的堆区起点）。**

### 1.4 ★★★★ 由此开出的**零风险新实验**（最高性价比）

已有硬事实（`raw8/sma_live_probe.txt`，相机自己的 dmesg）：

```
cma: CMA: reserved 288 MiB at 94000000
cma: CMA: reserved  72 MiB at 8f800000
PM: Registered nosave memory: 0x94000000 - 0xa6000000
```
并且当时的探针 **是用 `dd if=/dev/mem` 读 0x94000000 成功的** ——
⇒ ★★★ **`/dev/mem` 在这台机器上能读 DRAM**（HANDOVER 说的"整体不可用"只对 `0x2082b000` 那类**设备寄存器区**成立）。

⇒ ⇒ **这两个事实合起来给出一个从未试过、只读、零风险的实验：**

```bash
dd if=/dev/mem bs=256 count=1 skip=$((0x810fd100/256)) 2>&1 | od -An -tx1 | head -4
```

| 结果 | 含义 | 后续 |
|---|---|---|
| **读得到数据** | 那 4 张三星内置 LUT 表**能从 Linux 侧直接读出来** | ★★★★★ **把 U11（3D LUT 表格式 —— 唯一挡住打印级画色的未知）从"要改 p7"降级为"读一张已知内容的表做差分"** |
| `Bad address` / EFAULT | p7 的 `0x81xxxxxx` 堆区**不在 Linux 的 DRAM bank 内**（两核 DRAM 不相交） | 固化"Linux 永远读不到"，但理由换成正确的那个 |

★ 顺带把 `/dev/mem` 的能力边界也测一次（一次只读会话内可合并，铁律 87）：
`0x2082b000`（已知失败）、`0x810fd100`、`0x81115200`、`0x94000000`（已知成功）四点对照。

### 2.1 方法（自建，不依赖 Ghidra 的引用数据库）

```
① 04_strings.txt 里 0x6edb88..0x733578 是连续 .rodata.str1.1，链接器按目标文件顺序排

   LDR Rt,[PC,#imm] → 解引用池槽 / ADD Rd,PC,#imm / MOVW+MOVT 配对）

③ 指令地址 → 所属函数（52_pseudocode_index 二分）→ 引用串所在模块 = 该函数的模块（多数票）
```

**用铁律 116 自己点名的地址做决定性检验**（`ERROR_CORRECTIONS §7` E2 声称"全部 0 命中"）：

| 地址 | 字符串 | 我们的扫描 | 所属函数 |
|---|---|---|---|
| `0x584cd0` | `SetLiveviewParam2Monitor` | ★ **refs=1** | `FUN_0013a180` |

（已逐条验证是真 LDR 指令、落在真函数内、池槽内容真等于该字符串 VA。）

**根因**：Ghidra 以 **base 0x0** 分析，代码里的指针是 **`0x8xxxxxxx` 虚拟地址**，
**落在程序地址空间（0x0–0xc3ffff）之外** ⇒ Ghidra 无法为其建立引用 ⇒ 引用数据库**系统性地看不见全部此类指针**。

**★★★ 而项目自己的对照组当时就报了失灵却没被采纳** —— `10_control.txt` 原文：

```
=== 对照组: 确认 Ghidra 引用机制有效 ===
如果这些"早期字符串"(0x8494COMPARE 等)有引用 => 机制有效
如果连它们都0 => Ghidra 没建立引用, 是工具问题而非目标问题
COMPARE                        NOT FOUND
Call stack dump                NOT FOUND
A7 core's log                  NOT FOUND          ← ★ 全是"该有引用却 0"
```
⇒ 对照组的**判据文**明确写了"连它们都 0 ⇒ 是工具问题"，但主结论仍然按"机制有效"下了。
这正是铁律 32/116 想防的那种错 —— **"找不到 X" 未先证明搜索通路有效**。

**结论与边界（不夸大）**：

| 项 | 状态 |
|---|---|
| 「符号区零引用 ⇒ 是死数据」 | ❌ **判据撤销**（E1/E2 无效） |
| 「不能用 A 区名字推导注入点」 | ⚠️ **操作建议仍成立，但理由要换** —— 依据应是 §7.3 的 **B 区格式串证据**（`SetLiveviewParam2Monitor` 伴有 `Set Display Count %d` / `[PARAM MON] Run Still Param Monitor!!` ⇒ 它是**监控器/打印器**），而不是"零引用" |
| 新增可做事 | ★ **A 区那 3490 个"有引用的类名"现在可以用了** —— 它们能给出**类→函数的对应**，是补全 U01 地图（当前只覆盖 23%）的最直接燃料 |

## 8. U01 扩展（后续补做）· 类结构地图 + 调用图传播 → 覆盖率 23% → 43.75%

> §2 留下的缺口：U01 只覆盖 23%，因为 A 区那 4354 个类名**没有 `__FILE__` 段可依**。

### 8.1 类结构地图：RTTI 三跳（`test_server/isp/p7_class_map.py`）

A 区字符串里有一批 **Itanium 未修饰类型名**（形如 `17CBackend_Ldc_Base`，**前缀十进制数 = 名字长度**，
自洽校验通过 565 个）。对它们做三跳数据流：

```
跳1  字符串 VA 被某数据字指向      → typeinfo+4 的 name 指针
跳2  typeinfo VA 被某数据字指向    → vtable-4 的 typeinfo 指针     ★ 跳2 为空即否决跳1
跳3  从 vtable 起连读 0x8xxxxxxx   → 方法函数 VA → 文件偏移 → Ghidra 函数名
```

**结果**：**565 个类全部解出 vtable**；**1198 个函数被归属到类**（其中 **757 个是模块地图没覆盖的**）。
样本：`CIQ_SysDataIF_NX1`(64 方法)、`CJoshuaVb1Driver`(61)、`CDriveBracket`(55)、
`CDriveAFContinuous`(54)、`CFrontEndServiceNx`(45)、`CMaterial_PP_Core_Liveview*`(31–35)。

★ **这条路径同时是对铁律 116 的第二次证伪**：那批被叫做"mangled 裁剪残骸、整体零指针引用"的名字，
**不仅能被引用，而且引用它的就是完整的 C++ RTTI/vtable 结构**。
