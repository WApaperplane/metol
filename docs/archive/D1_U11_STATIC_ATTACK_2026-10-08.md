# D1 · U11「3D LUT 表格式」静态攻坚（2026-10-08）

> 工作流总表 **D1** 交付物。入口来自 `OFFLINE_VERIFICATION_2026-10-08.md` §3.2：
> 「VA `0x803837D0` = 四缓冲选择器、VA `0x80383800` = 消费函数（prologue `push {r4-r11,lr}`）」。
> 本篇把这**两条推断**拿去做三条独立判据的复核，结果**全部不成立**；
> 同时用**引用面证据**找到了真正的引用点，并给出**可证伪的表格式假设**。
> 全程离线，未触碰相机。

---

## 0. 一句话结论

> ★★★ **旧入口是误判。** `0x803837D0` / `0x80383800` 在全镜像 39499 个 BL + 31 个 BLX 目标里
> **没有任何调用者**，也**不作为 32 位指针出现**，Ghidra 函数表把该段判为**非函数**。
> 所谓"选择器 + 消费函数"只是**一段数据 + 紧邻坐标数**被 `objdump -D` 强行反汇编的产物
> （铁律 118/119 的又一次实例：**prologue 匹配不能当函数判据**）。
>
> ★★ **真正的引用面找到了**：4 个 LUT 缓冲地址各出现 2 次，分别落在
> **两张位于数据区的指针表**里（`0x80382B00` 12 项 / `0x80382C5C` 6 项）；
> 其中表 1 的真消费函数是 **`FUN_003829a4`**（按 BV/ISO 档位从表里选指针，并把档位写 `[obj+0xd8]`）。
> 这 4 个缓冲**等距 `0x4D00`**（第 3→第 4 跨 3 个槽）⇒ 给出**可证伪的表长假设**（§3）。
>
> ★ **类归属**：这几处代码**不属于任何 C++ 类**（`p7_class_map.tsv` 里 0 条 `FUN_0038*` 方法）。
> p7 的 3DLUT **类**（`CBackend_3dlut*` / `CMaterial_NX1_*_3dlut_*`）vtable 全在 `0x58xxxx`、
> 方法全在 `0x11xxxx / 0x16xxxx / 0x19xxxx / 0x1Bxxxx` 区 —— 与 `0x38xxxx` 区**分属不同模块**。

## 1. 硬证据：旧入口三条判据全否

| 判据 | `0x803837D0` | `0x80383800` |
|---|---|---|
| **① 有 BL 调用者？**（全镜像 39499 个 BL 目标） | ❌ 0 | ❌ 0 |
| **①′ 有 BLX 调用者？**（全镜像 31 个 BLX 目标） | ❌ 0 | ❌ 0 |
| **② 作为 32 位指针出现？** | ❌ 0 次 | ❌ 0 次 |
| **③ Ghidra 函数表判定**（`02_functions.txt`，16468 函数） | ❌ 落在**数据区** `0x38374C–0x383A88`（前一个函数 `FUN_00383380` 起 972 B 结束于 `0x38374C`；下一个函数是 `0x383A88`） | ❌ 同左 |

**为什么旧结论会出错**：`0x803837D0..EC` 的字节确实能反汇编成
`cmp r2,#1 / ldreq / ldrene / cmp r1,#1 / moveq / bx lr`，紧随其后的 `0x803837F0..FC`
正好是 4 个 `0x81xxxxxx` 指针 —— 形态上极像"选择器 + 字面量池"。
但**没有任何入口指向它**，而其后 `0x80383800` 起那段代码实际在调用
**曝光族辅助函数**（`0x802aebd8` / `0x802b0000` / `0x802aff3c` / `0x802b0078`）并做
`mul r3,#100 / sub #8000 / asr #4` 的**BV 计算**，还发 MCB 命令号 `0xb6` —— 与 LUT 无关。

> ★★ **判据权重说明（R3：硬证据 / 推断分栏）**：
> **主判据 = ① ①′ ②（无 BL/BLX 调用者、不作为指针出现）** —— 这两条是**穷举式、不依赖任何模型**的，
> 且本轮实测：全镜像 39499 个 BL 目标 + 31 个 BLX 目标、以及 12,845,056 B 内的字面量全扫过。
> **判据 ③（Ghidra 判为数据）只是旁证** —— 因为本报告 §2.2 已实测 **Ghidra 在这一带确有漏识别**
> （`0x80382C50` 是真的 `bl 0x803829a4`，却在 Ghidra 的数据段内）。
> 换句话说：**③ 不可单独否证一个函数；①② 可以。**

> ★ 记录一条方法论：**`objdump -D` 对数据区也会给出"看起来很合理"的指令流**；
> 判"这里是不是函数"必须用**入口证据**（BL/BLX 指向、指针表、Ghidra 函数表），
> 不能用"指令看着像"。本次旧结论错在只用了 prologue 形态。

## 2. 硬证据：4 个缓冲的真实引用面

4 个缓冲地址在镜像里**各出现 2 次**（`raw8/p7/u11_static_report.txt`）：

| 缓冲 | 出现位置 A（数据区表） | 出现位置 B |
|---|---|---|
| `0x810FD100` | off `0x382B14` | off `0x3837F0`（**旧"选择器"的字面量池**） |
| `0x81101E00` | off `0x382B1C` | off `0x3837F4` |
| `0x81106B00` | off `0x382C6C` | off `0x3837F8` |
| `0x81115200` | off `0x382C60` | off `0x3837FC` |

### 2.1 表 1 @ `0x80382B00`（12 项指针）

```
0x80382B00: 0x8116C000 0x81175A00 0x81167300 0x81170D00
0x80382B10: 0x81184100 0x810FD100 0x81188E00 0x81101E00
0x80382B20: 0x8115D900 0x8117A700 0x81162600 0x8117F400
0x80382B30: (代码开始) E92D40F8 = push {r4-r7,lr}
```

**真引用**：`LDR @ 0x80382A8C (r0)`、`LDR @ 0x80382AB8 (r0)` —— 两条都在
**`FUN_003829a4`（`0x3829A4`，348 B）的函数体内**（Ghidra 函数表确认）。

### 2.2 表 2 @ `0x80382C5C`（6 项指针）

```
0x80382C5C: 0x81119F00 0x81115200 0x8111EC00 0x8110B800 0x81106B00 0x81110500
```

**引用**：`LDR @ 0x80382BDC (r5)`、`LDR @ 0x80382C38 (r5)`。
⚠️ 这两个地址落在 Ghidra 判为"数据"的段内 —— 但**该段实际含代码**
（`0x80382C50: bl 0x803829a4` 是有效调用），说明 **Ghidra 在此区有漏识别**。
故这一条归为**硬证据（指令确实存在）但函数归属未定**。

### 2.3 消费函数 `FUN_003829a4` 的行为（反汇编实读）

```asm
3829a4  push {r4,r5,r6,lr}
3829b0  bl 0x802aebd8 / 0x802b0000 / 0x802aff3c / 0x802b0078   ; 取三路测量值
3829d0  mov  r3,#100 ; mul r3,r3,r0 ; sub r3,#8000 ; asr r4,r3,#4   ; ← BV/曝光值计算
3829f8  cmp  r5,#0 / cmp r0,#143 / cmp r4,#600 / cmp r4,#280
382a20  ldrcc r0,[pc,#216]  @ 0x80382B00   ┐ 从表 1 按 (r0>143?, r4 vs 600/280)
382a2c  ldrcs r0,[pc,#208]  @ 0x80382B04   │ 选出 **一个缓冲指针**
...                                        │
382a8c  ldrcs r0,[pc,#128]  @ 0x80382B14   ← = 0x810FD100（第 6 项）
382ab8  ldrcs r0,[pc,#92]   @ 0x80382B1C   ← = 0x81101E00（第 8 项）
382a24  strcc r3,[r6,#216]  @ +0xd8        ; ★ 把"档位编号"(1..12) 存进对象 +0xd8
```

⇒ ★ **它选的不只是一个缓冲指针，还同时写一个 1..12 的档位编号**。
表 1 的 12 项 **一对一对应档位 1..12**。这表明表 1 是
**"画质/曝光档 → 缓冲指针"的映射表**，而不是"4 个 LUT 通道"。
（`0x810FD100` = 第 6 项、`0x81101E00` = 第 8 项，只是其中两项恰好也是 LUT 缓冲。）

## 3. ★ 可证伪假设（本项要求的核心产出）

### 3.1 表长 / 维度

**硬证据**：4 个缓冲**等距 `0x4D00`**：

```
0x81101E00 - 0x810FD100 = 0x4D00 = 19712
0x81106B00 - 0x81101E00 = 0x4D00 = 19712
0x81115200 - 0x81106B00 = 0xE700 = 59136 = 3 × 0x4D00   ← ★ 跨了 3 个槽
```

**假设 H-A（首选）**：
> 每个缓冲槽 = `0x4D00` = **19712 B = 60 B 头 + 19652 B**，
> 而 `19652 = 17³ × 4`（17 个网格点 / 轴，每点 4 B）。
> `19712 - 19652 = 60`，60 B 正好是一个小头（如 `{magic, dim=17, flags, ...}` 十几个 u32）。

**假设 H-B（备选）**：槽内含多个子表（如 1D+3D 组合），
`19712 = 4 × 4928`，`4928 = 17³ + 15`。

**★ 证伪条件（任一成立即 H-A 错）**：
1. `/dev/mem` 读 `0x810FD100` 起 19712 B，在 `[60, 60+19652)` 区间**找不到** 17³ 的规则网格
   （判据：若为 RGB 16 位三通道表，则下标 `k = i*289 + j*17 + l` 的单调性、以及
   `(0,0,0)→近黑`、`(16,16,16)→近白` 应成立；若为 identity 表，应近似线性）；
2. 头 60 B 里读不出合理的 `dim` 字段（如 17 或 16/33）；
3. 槽实际大小可从 `0x810FD100` 与 `0x81101E00` 之间的**间隙内容**判定
   （若中间有独立的表/头，则 H-A 的"单槽 19712"不成立）。

> ★ 注意与旧结论的关系：U11 曾**否证过**"表长 19652/29478"——但那是针对
> **寄存器里的长度字段 / API 传入长度**。H-A 说的是**缓冲槽的物理尺寸**，两者不同层，不冲突。

### 3.2 「中点非中性色」的可证伪解释

**硬证据（mod 侧观测）**：写 `0x0000→粉红`｜`0x8000→品红`（中点非中性）｜`0xFFFF→青绿`。

| 假设 | 内容 | 证伪条件 |
|---|---|---|
| **H-C 通道序/字节序错配** | 写入侧按 `RGBA` 布局，ISP 侧按 `BGRA`（或反之）；或 16 位高低字节交换 | 按另一种通道序重写一张 identity 表 ⇒ 中点应回中性；若仍偏，H-C 错 |
| **H-D `0x8000` 不是几何中点** | 若表按**12 位左对齐**存于 16 位字，则几何中点是 `0x0800`(高 12 位 0x800)，`0x8000` 只有 1/8 ⇒ **任何单调表在中点测试点都会偏色** | 用 `0x0800` 试探；若 `0x0800→中性` 而 `0x8000` 偏，H-D 成立 |
| **H-E 第 4 字节不是 alpha** | 19652÷17³ 说明 4 B/点；若第 4 B 是 X/Z 分量而非 padding/alpha，则"每点 3 通道"的前提错，颜色映射必然错 | 把第 4 B 置 0 与置 0xFF 各测一次，若输出不同 ⇒ 该字节被消费（不是 alpha/padding） |

**三者互斥性**：H-D 与 H-C 可同时成立；H-E 独立。
