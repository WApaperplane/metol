## 0. 一句话结论

**"正式进入固件开发层"这个判断我要修正：现在进入的是错误的层。**
真正该进入的是**原生 UI 层**——它的地基已经全部就位，而且是固件能力能否被用上的唯一瓶颈。

固件层不是"不该做"，是**准入门槛没到**。门槛不是"会不会改 p7"，而是**改完能不能判断生效**。

### 事实 2 ★ mod_gui 的天花板是**源码级**的，不是"暂时没做"

反汇编 `scripts/mod_gui`（14130B，Thumb，54 个未定义符号）得到确证：

| 事实 | 证据 |

| 只能跑命令，不能调参 | 全部动作是 `system("%s &")` |
| 状态靠文件 | `%s/off_%s`、`%s/auto/%s`、`mod_gui.cfg.` |

★ **关键项**（★ 2026-10-07 用 capstone 复核二进制后更正）：
`key_down_callback` **只认 4 个 X11 keysym**：`Super_L` / `Super_R` / `Menu` / `XF86PowerOff`
（rodata `0xa9f8/0xaa00/0xaa08/0xaa10`，8 字节等距 = 硬编码比较数组）。
方向键与 JOG1_CW/CCW 全部落进 else 分支 → `quit_app()`。
> ★★ **旧档写"只认 13 键（F6~F10/KP_Home/Scroll_Lock/Hiragana…）"是错的** ——

> 详见 [`ERROR_CORRECTIONS_2026-10-07.md`](ERROR_CORRECTIONS_2026-10-07.md) C1/C2。
> ⇒ ★ 但**波轮是否发 Super_L/Super_R 事件尚未实测**，属待上机项，不再是"已证铁壁"。

⇒ **"迭代 mod_gui"在语义上不成立**：共振滑块、实时预览、以及"改配置/加参数/调布局"这些
mod_gui 结构上做不到（只 4 控件 / 点击即退 / 动作只能 `system()`）。
⇒ **正确动作是"用原生 EFL 视图取代它"，mod_gui 降级为兜底/高危操作入口。**

### 事实 4 ★★ 固件层的真实阻塞是「可观测性」，不是「改写能力」

## 2. ★★ 核心分歧：准入门槛，不是能力门槛

我的主张：**固件层开发必须先补观测通道，且这个"补"本身就在 Linux 侧。**

```
现状：  用户态改参数 → iqr 能看见 → 判定生效✅
       固件改参数 → iqr 看不见 → 判定不了 ❌
```

**门槛（必须全部满足才允许动p7 固件）**：

| # | 门槛 | 当前状态 | 成本 |
|---|---|---|---|
| **T1** | ★ **单分区回滚实机验证**（改坏只回滚 p7，不整机） | ❌ 未验（G5） | 低（刷一次备份分区） |
| **T2** | ★★ **该参数的生效判据**（不靠"参数值变了"） | ❌ **不存在** | 中~高，取决于能否找到读回路径 |
| **T3** | 参数值表布局 | ❌ 未知 | 高（Ghidra 完整逆向） |
| **T4** | 只改 Still 路径不动取景器 | ⚠️ 路径已知（`CBackend_3dlut_Still.cpp`），未验证 | — |

★ **T1 和 T2 与 p7 无关，纯 Linux 侧可做** ⇒ **这就是现在该干的活。**
★ **T3 才是真正的"进入固件开发层"**，它是完整逆向 + 一次不可逆刷写，不是"填几个数"。

### 关于 T2 的一个思路（值得试，但不是现在）

`iqr` 不含 gamma ⇒ 可能的原因有二：① gamma 不走 `IQ` 参数总线，是寄存器直写；② 在 p7 内部消化不上报。
**这两种原因对应完全不同的可行性**，且都能低成本区分：
- 若① → 必须找到寄存器写点并建立"写入前后读回"判据
- 若 ② → 可能存在 EP 侧可读寄存器（EP mmap 已验证可读 4096B 3D LUT 区）
⇒ **建议：先把"gamma/color/NOG 在 EP 侧有没有可读寄存器"这个问题查一遍**，
   这是**零风险、Linux 侧**的动作，却能直接判定 T2 是否可解。

## 3. ★ 原生 UI 层的战略价值：它是「选择器」变「控制器」

这是"采用原生 UI 视图"的真正收益——**不是好看，是能力维度的跃迁**。

| | mod_gui（现状） | 原生 EFL 视图（目标） |
|---|---|---|
| PW 7 维 | 只能选一个**预设** | ★ **实时拖动滑块**（`elm_slider`） |
| 配方对比 | 选一个 → 关窗 → 看结果 | ★ **不关窗，连续对比**（已实现） |
| 参数输入 | 只能跑预设脚本 | ★ `elm_entry` 直接输数值 |
| 缩略图 | 不可能 | ★ `elm_image` + 已有 `.thumbcache` |
| 长列表 | 上限 24 按钮 | ★ `elm_list` + `elm_scroller` 无限项 |
| 波轮 | ★ **结构上不可能** | ★ `ecore` 全键捕获 |
| 反馈 | 关窗 | ★ 实时高亮 + 状态栏 |

⇒★ **这是从"选预设"升级为"调参数"。**
⇒ ★★ PW 7 维是**机身唯一实机验证过的调色通道**（8 配方已跑通）。
　 能实时拖动它，等于**把机身 PW 7 维的利用率从"预设库"提到"连续空间"**——
　 这是**在不动 p7 的前提下，用户能拿到的最大画质提升**。
⇒ ★★ 而且它**恰好补上 p7 做不到的那部分**：p7 侧 12916 个键只能填表，
　 用户态滑块能给的是**探索**，填表只能给**离散点**。

## 4. 路线：三阶段，每阶段有客观判据

### 阶段 1（★ 现在做）·把未上机的资产变成已验证资产

**唯一目标：让 `nxfilmui.arm` 上机，把"已编译"变成"已验证"。**

这一步的价值不在 UI 本身，在于**它同时验证 4 件一直悬着的事**：

| 验证项 | 为什么重要 |
|---|---|
| 波轮 keysym 到底叫什么 | 决定"波轮 = 一个动作"这条主交互能不能成立 |
| `elm_gengrid` 触摸回调在 1.7.99 是否触发 | 决定用gengrid 还是 list |
| **CJK 字体到底有没有** | 决定 UI 是ASCII 降级还是自绘字模 |
| EFL 窗口在单核上是否真不抢 CPU | 决定原生 UI 路线整体是否成立 |

★ **这 4 项全是静态不可判定的**（铁律：编译通过 ≠ 功能可用）。
★ **一次上机全部回答**，成本 = 一次部署 + 一次 `filmui.log` 回收。

**判据**：日志里出现 `ecore_event_handler_add resolved`（dlsym 成功）+
至少一个按键事件被记录 + 配方列表非空。

### 阶段 2·原生 UI 从"一个页面"扩到"一个系统"

`nxfilmui` 目前只做配方选择。要成为 mod 的主界面，需要补：

| 页面 | 控件 | 依赖 |
|---|---|---|
| 配方库 | `elm_list` | 阶段 1 通过 |
| ★ **参数实时调** | `elm_slider` ×7 | PW 通道（已通） |
| 内置色彩 4 档 | `elm_radio` | 3D LUT 档位（G3 待验） |
| 系统设置 | `elm_switch` | 替换现有 checkbox |
| ★ **诊断/固件页** | `elm_entry` + 二次确认 | **高危操作隔离在这里** |

★ **页面模型沿用现有菜单树的骨架**（`gui_tpl/gui_func/gui_focus/gui_settings` 四页结构），
只把"文本按钮"换成"控件"，**不重设计信息架构**。

### 阶段 3 · 此时才评估固件层

只有当阶段 1 的 T2 有答案（gamma/color/NOG 在 EP 侧有无可读寄存器），
才决定要不要动p7。**若 T2 判不可解，p7 层这条路应当关闭**，
项目形态就是"用户态胶片仿真 mod"，这也是一个完整的产品。

## 6. 铁律追加（本次新增）

**84**★★ **原生 UI 的 ABI 声明只能来自"真机跑通过的 ELF 的未定义符号白名单"**，
不得凭 EFL 版本记忆写。查证工具 `test_server/filmlab/src/check_abi.py`。
（已用它抓到 `elm_box_recalculate` 根本不存在。）

**85** ★★ **mod_gui 的能力天花板是源码级的**（只 4 种控件 + 点一下即退 + 波轮不认键），
⇒ **"改进 mod_gui"与"替换 mod_gui"要分开判断**。本项目走替换。

**86** ★★★ **固件层准入门槛 = 该参数必须先有生效判据**。
没有判据的固件修改 = 无法验证的不可逆操作 ⇒ **宁可不做**。
（推论：`iqr` 不含某参数 ⇒ 该参数的固件侧改动当前一律不得启动。）

**87** ★★ **一次上机验证多项静态不可判定的事**，把它们合并成一次部署，
而不是逐项试 —— 单核相机每一次上机都是稀缺资源。
