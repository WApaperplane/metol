> **10-16真机进展**：一项原生标签的运行时更新/恢复已由用户目视和驻留读回通过，见 [真机结果](ONDEVICE_NATIVE_LABEL_RESULT_2026-10-16.md)。新增候选只写已核验的私有MO数据，不是poker文本/代码注入先例，也不解除P5与App代码投递的限制；只覆盖标签首探，完整M1/M2及真实配方应用未验。

> 状态：规划，尚未实施新的 App 补丁或上机实验。
> 用户目标：功能进入三星原生 UI，沿用机身菜单、滚轮、触摸和拍摄状态；具备可扩展、可更新、可回退的能力。
> 基线：本地 `nxwa` 提交 `8920f10`；既有 `di-camera-app` 全量静态分析继续复用。本文细化 UI 路线，不重排 A2 根因任务。

## 1. 路线决策与交付边界

**主线：复用官方画面向导及菜单的数据源、事件和控件。第一版交付三个自定义槽的配方映射、名称显示和原生操作；随后增加原生配方浏览页。**

| 交付 | 用户实际看到/做到什么 | 不足以通过验收的证据 |
|---|---|---|
| M1 原生入口 | 从原有菜单进入，名称正确，滚轮/触摸/返回正常 | 独立程序画出的截图、`st app film` 命令可用 |
| M2 原生选择 | 三个自定义槽对应三份明确的配方，焦点与选择一致 | 后台配置写入成功、只改显示名称 |
| M3 一键效果 | 在原生界面确认一次即可看到效果，无需再手工进入自定义1刷新 | 返回码为0、varlist 改变、调用捕获桩命中 |
| M4 配方浏览 | 复用官方列表/子页浏览更多配方，原生输入与状态切换完整 | 增加一个“自定义4”枚举、另建全屏窗口 |

M1/M2 可先做 UI 模拟适配器并如实显示“未应用”；正式 M2 必须有已验证的槽内容映射。M3 依赖有效应用通道，但不限定必须是 A2：原厂 App 的选择/应用事务若可复用，也应列入候选。

“进程内 + 同 Canvas”是实现条件之一，仍需复用官方控件和状态处理才能满足本项目的原生交互目标。既有十页 rect/text 出图是布局资产，可用于文案和尺寸参考；不能视为原生页面已实现。

## 3. 架构与第一版交互

| 部分 | 职责 | 边界 |
|---|---|---|
| 原生菜单适配 | 官方菜单表/标签、回调、焦点、状态进入退出 | UI 线程只做短操作；不直接运行耗时 shell |
| 配方模型 | 稳定 recipe_id、名称、三个槽映射、选择状态、能力要求 | 显示名称不能用作命令；不把配方数扩成原厂槽枚举 |
| 应用适配 | 原厂 App 事务或已验证的后端通道，串行处理请求 | 参数提交与实际效果分别记录；不虚构成功回执 |
| 持久化与版本 | p14 中的配置、补丁/宿主、兼容性清单 | SD 可作导入源；启动及核心配置不依赖损坏/缺失的 SD |

第一版拟定体验：用户进入原厂画面向导，看到三个已映射的自定义槽；行内或现有详情区显示配方名。旋转滚轮移动焦点，OK/触摸确认，返回键按原厂语义退出。改变焦点不等于提交，第一版仅确认时应用；连续滚轮实时预览放到后续阶段。

同一项至少维护 `focused_recipe`、`requested_recipe`、`applied_recipe` 三个状态。成功显示“已应用”必须符合已定义的完成语义；若接口只能证明命令已接受，就只显示“已提交/效果待确认”。用户用原厂菜单手工改参后，旧配方应变为“已修改”，不能继续宣称精确匹配。

M4 拟在经验证的既有列表/子页模板内增加 FilmLab 配方浏览，支持分页、收藏和映射到3槽。具体挂在哪个菜单项、能否增加条目，需要 UI-R1 的结构证据后裁决；不会预先指定一个未证明可扩展的菜单数组。

### UI-R1 的定向逆向范围

使用现有 `dicam_*` 工具、已有 Ghidra 导出和 REA。REA 只补缺失的函数引用、调用形态、间接分发候选和结构访问点；不重做全量静态。

| 目标 | 已有起点 | 需要补的证据 |
|---|---|---|
| PW 项与文案 | 描述表 file `0x40c6a8`、`0x41754c`，已记录步长 `0x114` | 两份表分别被谁消费；名称是消息ID还是运行时文本；能否局部覆盖 |
| 官方菜单构建 | `setMenuList`、`getMenuItem`、`SetDrawInfo`、`tag_MENU_INFO` | 准确函数VA、字段布局、计数/边界、生命周期；不是仅凭 demangle 名猜签名 |
| 输入与模式 | Menu State 的 OK/滚轮/触摸/返回事件 | 活跃页面如何判别、事件是否已消费、拍摄/录像/回放时如何禁用或退出 |
| 应用事务 | 原厂 PW/custom 选择 handler，属性和持久化调用 | 选择、写槽、通知、保存与刷新是否同一线程；可复用的最小完整事务 |
| C4 候选 | `UI_Manage_Development_Menu_Info_By_GUI` | 调用前提、可达性及副作用；不优先启用开发/产线模式 |

每份补证必须记录样本SHA-256、查询地址空间、入口与调用点、原始结果或可复现命令、已知/推断/未决标记。间接调用未解析时不得用空引用图下“不存在”的结论。

## 5. 投递方式的选择任务

先证明最小入口和 ABI，再决定是否需要宿主；第一版不预设必须注入 `.so`。

| 候选 | 使用条件 | 首个验证 |
|---|---|---|
| A：poker 小范围数据补丁 | 固定数据/文字足够；原字节、目标区可写性和访问时机已证明；无需多步非原子改码 | 在菜单未持有旧数据时修改一项、只改可验证的完整字段；已知PID/映射/原值严格匹配 |
| B：受控加载单体宿主 | 动态配方列表/回调确需进程内代码；最小补丁不足 | constructor 仅做最小标记、无 EFL 调用；随后在已证明的主循环安全点接入 |
| C：离线 App 数据/小桩补丁 | 无合适运行时接入点，但固定补丁可证明 | 只处理匹配样本；正常关开机生效；核验实际执行文件身份 |

> ★ **2026-10-15 修订：投递候选重排 + 生效语义缺口**（依据 `MEM_INJECTION_EVAL_2026-10-15.md` / `CAMERA_ONLINE_PROBE_2026-10-13.md`）：
> 1. **候选 A（poker）降级**——先例面仅「写预编码值到固定数据地址」（比特率 9 组）；「访问时机/生命周期」恰为其短板（注入点晚于 App 启动 25s+，菜单数据届时已加载），文本类保留条件在当前证据下不可满足 ⇒ **退出 UI 投递主候选**，保留为参数级工具。
> 2. **候选 C 的「正常关开机生效」需先论证**——T2 的 mount 由 init.sh（boot+37.8s）建立，晚于 App exec（boot+12.2s）⇒ 冷启动时挂载赶不上本次 exec；且 `scripts/dicam/dicam_patch_install.sh` 第 4 步「立即生效」仍用 `systemctl restart`（已证卡死整机）。生效路径三候选**（★ 2026-10-15 裁决 = a：P5 前置）**：**(a ★已选)** unit 本体加 `ExecStartPre` 前置挂载（P5 式；实施件 `scripts/dicam/{t2_premount,dicam_p5_install,dicam_p5_rollback}.sh` 已就绪 + 详案 `T2_DELIVERY_REVISION_2026-10-15.md` §6）；**(b)** T1 就地补丁（无时序问题，接受刷机后重放）；**(c)** 上机实测生命周期（找「晚于 mount 的 App exec 时刻」）。候选 C 的首个验证据此修正为：只处理匹配样本；先定生效路径，再走「正常开关机」语义；核验实际执行文件身份。
> 3. 相应修订：T2 投递件去 `restart`；W-3/E-D4 演练判据（「restart 后画面正常」）改为「自然关机开机」路径。**该修订先于 UI-R3b 上机**（见 §9）。

B 的候选实现为持久的、仅作用于该服务的启动配置或启动守卫，需验证 systemd 208 语法及实际装载顺序。P5 unit 本体是已有候选；持久 drop-in 若采用，另行确认路径及优先级。两者都不能依靠晚到的 `/run` 配置即时生效。

选择 B/C 前，必须回答：

1. App 首次 exec 前，p14、宿主及必要库是否已经可读？休眠恢复是否跳过这次 exec？
2. 禁用标记在任何自定义代码载入之前是否能被判断？只在 constructor 内检查不能防止装载器/ABI错误。
3. 缺库、坏哈希、版本不匹配或上次未完成启动时，是否能转回原厂启动路径？守卫本身也需有可操作的恢复办法。
4. 拔SD、断网、缺配置时能否开机？不能把“拔卡”当作 p14/rootfs 改动的卸载方法。
5. 失败后，在机身不能联网的情况下能否撤销？恢复通道未验证前，不进入持久进程内代码实验。

poker 写运行中代码还涉及指令缓存、原子性、线程执行位置和内存权限；已有数据写入先例不能直接证明这些条件。首探优先数据修改，需要 trampoline 才能继续时，重新评估 B/C。★ 10-15 修订：即使是「数据修改」这一格也受生命周期/时机短板约束（见上方修订块点 1），离线补丁族（C/T1/T2）可全覆盖且更可控 ⇒ UI 语境下不再以 poker 为首探。

第一版宿主采用单体、静态功能表；加载正常且2–3项功能稳定后，再考虑模块 ABI 与热更新。所有 UI 对象只在已确认的 App UI 线程操作；不另启 `elm_run`，不保存跨销毁/休眠的裸 Canvas 指针。

## 6. 与 A2 的依赖和状态语义

| 工作 | 相机离线能否进行 | 必须等 A2 成功吗 |
|---|---|---|
| 菜单数据结构、原厂事务、资源/字体、交互设计 | 可以 | 不需要 |
| 配方模型、模拟后端、错误与取消逻辑、安装设计 | 可以 | 不需要 |
| 原生一项标签、输入、正常关开机回归 | 不能完全离线验收 | 不需要；须有可用机身基线 |
| 一键应用真实效果 | 不能 | 需要一个已验证应用通道；可以是原厂事务或经修正的 A2 |
| 配方页发布为“效果完整” | 不能 | 必须通过实机效果验收，不能只交UI截图 |

UI状态拟采用“选择→提交→完成/失败”；工作线程耗时操作通过有界队列执行，完成消息回到主循环。快速重复确认合并或拒绝为忙；模式变化/对象销毁后，不接受旧请求回写UI。

若用户已退出页面但后端写入已经发生，不能假定取消等于回滚；必须重读实际状态并标明。回滚参数也必须经过已验证的应用事务，不只恢复屏幕上的文字。

C-2 若继续使用，只作为命令桥；禁止 `f.sh → st app` 回到同一阻塞队列。任何调用最终可能走回 App 的后端，都要先画出线程/队列等待关系。UI主线程不调用同步 `system()`。

## 7. 离线测试与实机测试的分工

| 验证层 | 任务 | 能证明 | 不能证明 |
|---|---|---|---|
| 静态/REA | 结构、补丁点、调用和资源访问 | 指令/数据及可解析引用 | 活跃对象、线程安全、实时效果 |
| QEMU 用户态 | 真字节小桩、序列化、ABI、异常输入、模拟后端 | 分支和数据协议；须记录哪些原厂函数被替换 | 模拟桩等于原厂事务、真实Canvas可用 |
| QEMU 系统模式 | 正常启动/禁用路径、缺文件、配置加载等可模拟部分 | 通用 ARM 环境中的软件流程 | DRIMe5 板级、真实休眠、ISP与拍摄效果 |
| 真机 | 官方菜单入口、输入、预览/成片、模式切换、恢复 | 用户可感行为和真实生命周期 | 不能用单次成功推断所有固件/模式兼容 |

QEMU 长测试前台运行并显示结果。既有 A2 的13项测试替换了写槽和应用函数；不能把它直接计入 UI-R5b 或真实影像链通过。

## 8. 实机验收矩阵

实验开始时记录 App/固件状态、实际加载的补丁身份、模式、原厂菜单状态、负载和网络基线。网络不可达与机身不能启动分别记录。

| 场景 | 验收内容 |
|---|---|
| 进入/返回 | MENU进入，OK/触摸确认，返回逐级退出；原厂其它项保持原行为 |
| 滚轮/焦点 | 首尾、连续快速转动、返回后重入；焦点、选择和实际应用各自正确 |
| 三槽映射 | 三个不同配方逐一选择；显示名称与槽内容匹配；无第四槽越界 |
| 原厂手动改参 | 标签变为“已修改”或重新核对；不会静默覆盖用户新值 |
| 拍摄/录像/回放 | 半按/全按可用；录像及回放不抢键；不支持场景禁用并解释 |
| 预览/JPEG/RAW | 分开记录；同场景A/B对比；RAW不承诺被PW/LUT烘焙，不能用内嵌预览替代RAW结论 |
| 生命周期 | 正常关开机、已确认的休眠/唤醒路径、加载身份和状态恢复；不做服务强制restart |
| 资源/外设 | 无SD、坏配置、中文长名；HDMI有现成设备时测试，无设备则明确不宣称支持 |
| 性能 | 至少30秒持续交互及两轮负载；记录操作延时、常驻内存和原厂基线，不预填“无劣化” |
| 撤销 | 按投递方式恢复数据/文件/配置，正常关开机确认原版加载；验证离线恢复通道 |

## 9. 首批执行包与优先顺序
